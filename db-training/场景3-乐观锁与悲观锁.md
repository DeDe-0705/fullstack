# 场景 3：乐观锁 vs 悲观锁

> 目标：实测两种并发控制策略——悲观锁（FOR UPDATE 加锁）vs 乐观锁（version 字段 CAS），理解丢失更新与选型。

## 一、两种思想

- **悲观锁**：认为冲突**一定会**发生，先加锁独占，改完再释放。→ **先锁门**。
- **乐观锁**：认为冲突**很少**发生，不加锁直接改，提交时用版本号核对，冲突则重试。→ **事后核对**。

一句话：**悲观锁 = 先锁门，乐观锁 = 事后核对。一个怕冲突，一个信没冲突。**

## 二、悲观锁

流程：`FOR UPDATE` 锁行 → 读最新值 → 改 → `COMMIT`（别人全程排队）。

```sql
BEGIN;
SELECT * FROM products WHERE id = 1 FOR UPDATE;   -- 锁行
UPDATE products SET stock = stock - 1 WHERE id = 1;
COMMIT;
```

特点：阻塞等待、可能死锁、并发低，但强一致。

## 三、乐观锁

核心 SQL 模式：

```sql
UPDATE products
SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = 0;   -- 只有当 version 还是读到的值才更新
```

本质是 **CAS（Compare-And-Swap，比较并交换）**：比较 `version` 是否还是读到的值，是则交换（更新），不是则失败（影响 0 行）。

**重试链路**：读 → 更新失败(0 行) → 重读最新 → 重新更新。

```sql
-- 失败后重试
SELECT stock, version FROM products WHERE id = 1;   -- 重读
UPDATE products SET stock = stock - 1, version = version + 1 WHERE id = 1 AND version = 1;
```

特点：不阻塞、并发高、避免死锁，但冲突频繁时会出现重试风暴。

## 四、丢失更新（Lost Update）

两个事务同时读同一值、基于旧值更新，后提交的覆盖先提交的，导致一次更新丢失。

- 悲观锁用「加锁串行化」避免。
- 乐观锁用「版本核对 + 重试」避免。

一句话：**悲观锁用阻塞换一致，乐观锁用重试换一致，都在防丢失更新，策略相反。**

## 五、对比与选型

| | 悲观锁 | 乐观锁 |
|---|---|---|
| 假设 | 冲突一定发生 | 冲突很少发生 |
| 实现 | FOR UPDATE | version + CAS |
| 并发 | 低（阻塞） | 高（不阻塞） |
| 冲突处理 | 等锁 | 重试 |
| 缺点 | 阻塞、死锁 | 重试风暴 |

选型：

- 读多写少、冲突少 → **乐观锁**
- 写多、冲突频繁（热点、秒杀） → **悲观锁**或更复杂方案
- 强一致、必须串行 → **悲观锁**

## 六、实测记录（2026-09-03）

- 悲观锁：FOR UPDATE 锁行，另一会话阻塞，提交后读到最新 stock=9 ✅
- 乐观锁 CAS：A 更新 1 行，B 更新 0 行（冲突） ✅
- 乐观锁重试：B 重读 version=1，重新更新成功 ✅
