# 场景 5：索引与慢查询

> 目标：掌握 B+树索引、EXPLAIN 执行计划、联合索引最左前缀、回表/覆盖索引、慢查询定位。

## 一、索引基础（B+树）

B+树三个特点：

1. **矮胖多叉树**：一个节点存很多键，树很矮，3~4 层能存上千万行。
2. **数据全在叶子节点**：非叶子节点只存"指路用的键"。
3. **叶子节点用链表连接**：范围查询（`BETWEEN`、`> <`）也快。

**聚簇索引 vs 二级索引**：

| | 聚簇索引 | 二级索引（辅助索引） |
|---|---|---|
| 是什么 | 主键索引 | 自己建的普通索引 |
| 叶子节点存什么 | **整行数据** | **主键值**（不是数据） |

## 二、EXPLAIN 核心字段

| 字段 | 含义 |
|---|---|
| `type` | 访问类型，**从好到差**：`const` > `eq_ref` > `ref` > `range` > `index` > `ALL` |
| `key` | 实际用的索引（`NULL` = 没走索引） |
| `rows` | 估算扫描行数 |
| `Extra` | 额外信息 |

`type = ALL`（全表扫描）是最差的，是慢查询的起点。

## 三、联合索引 + 最左前缀

联合索引 `(a, b, c)`，查询必须**从最左列开始、且中间不断**才能用上索引：

| 查询条件 | 能否用索引 |
|---|---|
| `a` / `a,b` / `a,b,c` | ✅ 能用 |
| `a,c` | ⚠️ 只用 a（b 断了，c 用不上） |
| `b` / `c` / `b,c` | ❌ 全废 |

本质：索引按「最左列」建立顺序，跳过最左列顺序就没了。

## 四、回表 vs 覆盖索引

- **回表**：查询需要索引之外的列，拿着主键去聚簇索引再查一次整行（多一次 I/O）。
- **覆盖索引**：查询需要的列全在索引里，直接返回，`Extra` 显示 `Using index`。

优化手法：查询尽量只挑索引里有的列，省掉回表。

## 五、Extra 信号 + 慢查询定位

`Extra` 关键信号：

| 信号 | 含义 | 好坏 |
|---|---|---|
| `Using index` | 覆盖索引，不回表 | ✅ 好 |
| `Using where` | 回表后再过滤 | ⚠️ 一般 |
| `Using filesort` | 额外排序（ORDER BY 没走索引） | ❌ 要优化 |
| `Using temporary` | 用了临时表 | ❌ 要优化 |

慢查询定位链路：

1. 开慢查询日志，找慢 SQL
2. `EXPLAIN` 分析（type 是否 ALL、key 是否 NULL、Extra 是否有 filesort/temporary）
3. 优化（加索引 / 覆盖索引 / 排序走索引 / 改写 SQL）

## 六、实测记录（2026-09-04）

- EXPLAIN 主键 vs 无索引列：`const`/`PRIMARY` vs `ALL`/`NULL` ✅
- 建索引后：`type` 从 `ALL` 变 `ref` ✅
- 最左前缀：`city` 和 `city+salary` 走索引，`salary` 跳过 `city` 变 `ALL` ✅
- 覆盖索引：`SELECT city,salary` 得 `Using index`，`SELECT *` 回表 ✅
- `ORDER BY salary`（无索引）出现 `Using filesort` ✅
