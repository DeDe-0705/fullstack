# Feature Specification: 商品下单（Product Ordering）

**Feature Branch**: `001-product-ordering`

**Created**: 2026-09-08

**Status**: Draft

**Input**: User description: "实现一个简化的商品下单功能：用户可以查看商品列表和单个商品的库存；用户可以提交订单购买商品，扣减对应库存；库存不足时下单必须失败，并明确提示"库存不足"；同一个请求重复提交不能重复扣库存；两个用户同时抢最后一件商品时，只能有一个成功；下单成功后能看到订单详情（商品、数量、扣减后剩余库存）。不在范围内：支付、用户登录注册、商品管理后台"

## Clarifications

### Session 2026-09-08

- Q: 未携带请求标识的下单请求如何处理？ → A: 必须拒绝并明确提示缺少请求标识；
  服务端 MUST NOT 代为生成标识（自动生成会使服务端无法区分新请求与重试，幂等失效）。
  请求标识由调用方生成（如 UUID），同一逻辑请求的重试复用同一标识，
  不同购买意图使用不同标识。
- Q: SC-001 如何以纯 API 项目的方式技术可度量？ → A: 改为"用户通过两次接口调用
  （查询商品、提交订单）即可完成购买并拿到订单详情"。
- Q: 订单详情中"剩余库存"的语义是什么？ → A: 该订单扣减完成时刻的快照值，
  不是实时库存；并发场景下不保证等于查询时刻的当前库存。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 提交订单购买商品 (Priority: P1)

用户在浏览商品后，选择一件商品和购买数量，提交订单。系统扣减对应库存，
创建订单，并向用户展示订单详情：所购商品、购买数量、扣减后的剩余库存。

**Why this priority**: 下单是整个功能存在的理由——没有下单，浏览库存、幂等、
并发控制都失去意义。仅实现这一条用户旅程，就已经是一个可用的最小产品。

**Independent Test**: 预置一件库存为 10 的商品，提交购买 3 件的订单，
验证返回订单详情（商品、数量 3、剩余库存 7），再次查看该商品库存为 7。

**Acceptance Scenarios**:

1. **Given** 商品 A 库存为 10，**When** 用户提交购买 3 件商品 A 的订单，
   **Then** 下单成功，返回订单详情（商品 A、数量 3、扣减后剩余库存 7）
2. **Given** 商品 A 库存为 3，**When** 用户提交购买 3 件商品 A 的订单，
   **Then** 下单成功（边界：恰好买空），剩余库存为 0
3. **Given** 一个已创建的订单，**When** 用户查询该订单，
   **Then** 能看到订单详情（商品、数量、下单后剩余库存）

---

### User Story 2 - 浏览商品列表与库存 (Priority: P2)

用户查看商品列表，每个商品展示当前库存数量；也可以查看单个商品的详情与库存，
以此决定购买什么、买多少。

**Why this priority**: 浏览是下单的前置动作，但下单本身可以独立测试和交付，
因此浏览排在 P2。

**Independent Test**: 预置多件不同库存的商品，请求商品列表与单个商品详情，
验证每个商品的库存数量与预置值一致。

**Acceptance Scenarios**:

1. **Given** 系统中预置了 3 件商品，**When** 用户查看商品列表，
   **Then** 看到 3 件商品及各自的当前库存
2. **Given** 商品 A 存在，**When** 用户查看商品 A 的详情，
   **Then** 看到商品 A 的当前库存数量
3. **Given** 商品 A 刚成交了一笔订单，**When** 用户再次查看商品 A，
   **Then** 看到的库存是扣减后的最新值

---

### User Story 3 - 重复提交不产生重复扣减 (Priority: P2)

用户提交订单时因双击、网络重试等原因，同一个下单请求被发送了多次。
系统识别出这是同一个请求，只处理第一次，后续重复提交直接返回首次的下单结果。

**Why this priority**: 幂等是真实网络环境下下单功能的正确性底线，
与下单主流程同等重要；但它依附于下单存在，故排 P2。

**Independent Test**: 用同一个请求标识对同一商品连续提交 3 次相同订单，
验证只创建了一个订单、库存只扣减了一次，且 3 次响应内容一致。

**Acceptance Scenarios**:

1. **Given** 商品 A 库存为 10，**When** 同一请求标识的下单请求（买 2 件）被提交 3 次，
   **Then** 只存在一个订单，商品 A 库存为 8，3 次响应均为该订单的相同详情
2. **Given** 某请求标识的首次下单已因库存不足失败，**When** 相同标识再次提交，
   **Then** 返回与首次一致的失败结果，不产生订单、不扣库存

---

### User Story 4 - 并发抢购不超卖 (Priority: P3)

两个用户同时抢最后一件商品：两个下单请求几乎同时到达，
系统保证只有库存能支撑的请求成功，其余失败，库存永不为负。

**Why this priority**: 并发超卖是低频但高严重度的问题，依赖下单主流程与
库存校验都已就位，作为独立的加固层排 P3。

**Independent Test**: 预置一件库存为 1 的商品，同时发起多个购买 1 件的订单，
验证恰好 1 个成功、其余收到"库存不足"，最终库存为 0。

**Acceptance Scenarios**:

1. **Given** 商品 A 库存为 1，**When** 两个用户同时各提交 1 件商品 A 的订单，
   **Then** 恰好一人成功，另一人收到"库存不足"，商品 A 最终库存为 0
2. **Given** 商品 A 库存为 5，**When** 10 个用户同时各提交 1 件商品 A 的订单，
   **Then** 恰好 5 人成功、5 人失败，最终库存为 0 且不为负

---

### Edge Cases

- 购买数量恰好等于当前库存：下单成功，剩余库存为 0。
- 库存为 0 时下单：失败并提示"库存不足"。
- 购买数量为 0、负数或非整数：下单失败，提示购买数量非法。
- 对不存在的商品下单或查看：失败并提示商品不存在。
- 同一请求标识的重复提交与并发同时发生（同一标识并发重复）：仍只处理一次。
- 未携带请求标识的下单请求：拒绝并提示缺少请求标识，不创建订单、不扣库存。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供商品列表，包含每个商品的当前库存数量。
- **FR-002**: 系统 MUST 提供单个商品的详情查询，包含当前库存数量；
  商品不存在时 MUST 明确提示。
- **FR-003**: 用户 MUST 能提交订单，订单指定一种商品和购买数量。
- **FR-004**: 下单成功时系统 MUST 扣减对应商品的库存；库存数量在任何代码路径下
  MUST NOT 为负数（含并发场景）。
- **FR-005**: 库存不足以满足购买数量时，下单 MUST 失败并明确提示"库存不足"，
  且库存不发生任何变化、不创建订单。
- **FR-006**: 购买数量 MUST 为正整数；非法数量的下单 MUST 失败并给出明确提示。
- **FR-007**: 每个下单请求 MUST 携带由调用方生成的唯一请求标识（如 UUID）；
  同一逻辑请求的重试复用同一标识，不同购买意图使用不同标识。
  同一标识的重复提交 MUST 返回首次请求的处理结果（成功订单或失败原因），
  MUST NOT 重复扣减库存或创建重复订单。
- **FR-008**: 多个下单请求同时竞争同一商品库存时，MUST 只有库存能支撑的请求成功，
  其余按"库存不足"失败，杜绝超卖。
- **FR-009**: 下单成功后，用户 MUST 能查看订单详情：所购商品、购买数量、
  扣减后剩余库存。其中剩余库存 MUST 为该订单扣减完成时刻的快照值，
  不是实时库存。
- **FR-010**: 未携带请求标识的下单请求 MUST 被视为非法请求并拒绝，
  明确提示缺少请求标识；系统 MUST NOT 为请求代为生成标识，
  不创建订单、不扣减库存。

### Key Entities *(include if feature involves data)*

- **商品（Product）**: 可购买的物品。关键属性：商品标识、名称、当前库存数量。
- **订单（Order）**: 一次成功购买的记录。关键属性：订单标识、请求标识（幂等键）、
  所购商品、购买数量、下单后剩余库存（扣减完成时刻的快照值，非实时库存）、创建时间。
  一个请求标识最多对应一个订单。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户通过两次接口调用（查询商品、提交订单）即可完成购买并拿到订单详情。
- **SC-002**: 库存不足的下单请求 100% 失败且提示"库存不足"，对应商品库存零变化。
- **SC-003**: 同一请求标识重复提交任意次数（≥2），库存只扣减一次、
  系统中只存在一个对应订单，且各次响应内容一致。
- **SC-004**: 100 个请求同时抢购 1 件库存时，恰好 1 个成功、99 个收到"库存不足"，
  最终库存为 0，任何时刻不出现负库存。
- **SC-005**: 下单成功响应中用户立即可见订单详情；其中剩余库存为该订单
  扣减完成时刻的快照值，与订单创建时的实际库存一致
  （并发场景下不保证等于查询时刻的实时库存）。

## Assumptions

- 单个订单只包含一种商品及其购买数量（无购物车、无多商品合并下单）。
- 下单不要求用户身份：不区分注册用户/游客（登录注册明确不在范围内）。
- 商品数据由系统预置，不提供商品的新增/修改/删除入口（管理后台不在范围内）。
- 请求标识由调用方生成（如 UUID），同一逻辑请求的重试（双击、网络重试）复用同一标识；
  不同购买意图使用不同标识；未携带标识的请求视为非法并被拒绝，服务端不代为生成。
- 练习项目：数据在服务运行期间保持一致即可，服务重启后数据可重置为预置状态。
- 支付、优惠、运费等交易环节均不在范围内，下单成功即流程终点。
