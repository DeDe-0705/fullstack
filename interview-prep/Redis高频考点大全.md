## 一、为什么 Redis 这么快 / 线程模型

这是「单线程为什么快」的标准开场，也是很多追问的起点。

### 1.1 Redis 快在哪

- **纯内存操作**：数据存在内存，单次操作微秒级。
- **高效数据结构**：SDS、跳表、哈希表等为特定场景优化。
- **单线程免锁**：命令执行是单线程串行的，无锁竞争、无上下文切换开销。
- **IO 多路复用**：基于 epoll（Linux）/ kqueue（macOS）/ select，单线程可处理上万并发 TCP 连接，把瓶颈从 CPU 转移到网络 IO。

### 1.2 「单线程」到「多线程」的演进（重要，避免踩坑）

面试官常设陷阱问「Redis 到底是不是单线程」，标准口径是：**命令执行始终是单线程的，多线程只作用于网络 IO 和部分扩展能力**。

- **Redis 6.0 之前**：网络 IO + 命令执行都在主线程，纯单线程。
- **Redis 6.0**：引入 IO 线程（`io-threads`），默认关闭。用于并行处理网络读写（解析请求、发送响应），但**命令执行仍由主线程单线程完成**。解决的是「多核 CPU 闲着、网络读写成为瓶颈」的问题。
- **Redis 8.0**：引入新的 I/O 线程实现，可配置 `io-threads` 开启，官方称吞吐量可提升 1 倍；查询引擎（Query Engine）也引入多线程查询执行，复杂查询吞吐量提升 16 倍。

> 一句话：**单线程快不是因为「单」，而是因为内存 + 多路复用 + 免锁；多线程的引入是为了压榨多核网络 IO，命令执行的串行语义没变。**

### 1.3 常见追问

- **为什么不用多线程直接并行执行命令？** 数据在内存，瓶颈是网络不是 CPU；并行执行要引入锁、破坏原子性、复杂度陡增，收益不大。真正需要并行的查询场景，8.0 才在查询引擎里局部多线程化。

## 二、底层数据结构（追问深水区）

> 面试中「数据类型」只报名字是及格线，能聊到底层编码才是区分点。以下按「你常说的数据类型 → 底层真实结构」展开。

### 2.1 String → SDS（Simple Dynamic String）

SDS 相比 C 原生字符串 `char[]`：

- **O(1) 取长度**：结构里存 `len`，C 字符串要 `strlen` 遍历到 `\0`。
- **二进制安全**：靠 `len` 判断结束而非 `\0`，可存任意二进制（图片、序列化对象）。
- **杜绝缓冲区溢出**：写入前检查并自动扩容，C 字符串 `strcat` 易越界。
- **空间预分配 + 惰性释放**：扩容时多分配冗余，缩短时暂不回收，减少频繁内存重分配。

### 2.2 List → quicklist

- Redis 3.2 前是 `linkedlist` 或 `ziplist`，3.2 起统一为 **quicklist**：一个双向链表，每个节点是一个压缩列表（后来换成 listpack），兼顾「链表增删 O(1)」和「压缩列表省内存」。
- **listpack vs ziplist**：ziplist 每个元素记录前一个元素长度，**连锁更新**（一个元素变长导致后续长度字段级联更新）是它最大的坑；Redis 7.0 用 **listpack** 替代，去掉了前置长度回溯，彻底解决连锁更新。

### 2.3 Hash → dict（哈希表）+ listpack

- 默认用哈希表（dict），元素少时用 listpack 紧凑存储。
- **渐进式 rehash**：扩容时不一次性迁移，而是「每次操作顺便搬一部分 + 定时任务搬一点」，避免大哈希表 rehash 阻塞主线程。rehash 期间两个哈希表并存。

### 2.4 Set → intset / dict

- 全整数且数量少时用 `intset`（有序整数数组，二分查找），否则退化为哈希表。

### 2.5 ZSet → skiplist（跳表）+ dict

- 跳表 + 哈希表双结构：跳表支持按分数范围查询、排序、排名；哈希表提供 O(1) 按成员定位分数。
- **跳表为什么不用红黑树**（高频追问）：
  1. 实现简单、易读、易维护，出错概率低；
  2. 天然支持**范围查询**（`ZRANGE`）和**按名次查询**（`ZRANK`），顺着索引层扫即可，红黑树要中序遍历；
  3. 层数用随机算法生成（每层 50% 概率向上），无需像平衡树那样频繁旋转调整，写入更平稳。

### 2.6 通用编码策略

- Redis 内部维护「小数据结构」的紧凑编码，达到阈值自动切换（如 `list-max-listpack-size`、`hash-max-listpack-entries`）。
- 记忆点：**「元素少用连续内存省空间，元素多换结构保性能」**，本质是时间换空间 / 空间换时间的动态权衡。

## 三、常用数据类型与使用场景

面试要求：**每个类型带一个你真实用过的场景**，一句话即可，不要只背名词。

| 类型 | 底层结构 | 典型场景 |
|---|---|---|
| String | SDS | 缓存对象、计数器（`INCR`）、分布式锁、session |
| Hash | listpack / dict | 对象字段存储，改单个字段不用整存整取（如购物车、用户信息） |
| List | quicklist | 消息队列、时间线、最新列表（`LPUSH` + `LRANGE`） |
| Set | intset / dict | 去重、共同好友（`SINTER`）、点赞用户集合 |
| ZSet | skiplist + dict | 排行榜、延时队列（分数=到期时间戳）、带权重的优先队列 |
| Bitmap | String 的位操作 | 签到、在线状态、布隆过滤器的位图基础（`SETBIT`/`BITCOUNT`） |
| HyperLogLog | 概率结构 | 超大基数去重计数（UV），12KB 误差约 0.81% |
| GEO | ZSet 封装 | 附近的人、地理围栏（`GEORADIUS`） |
| Stream | 类似日志结构 | Redis 5.0+ 的消息队列，支持消费组（`XADD`/`XREADGROUP`） |

### 3.1 高频追问

- **Hash 存对象 vs String 存 JSON**：Hash 可局部更新、省流量、无整存整取；但字段极多或需整体读时，String 存 JSON 可能更简单。看访问模式。
- **List 做消息队列的缺陷**：无消费组、无 ACK、消息无持久确认，生产用 Stream 或专业 MQ（Kafka/RocketMQ）。
- **HyperLogLog 为什么有误差**：用极小内存做概率统计，牺牲精确性换空间，UV 这种允许误差的场景才用。

## 四、持久化：RDB 与 AOF

### 4.1 RDB（快照）

- **原理**：把某一时刻的内存数据落盘成二进制快照文件 `dump.rdb`。触发方式：`save`（阻塞主线程，禁止生产用）/ `bgsave`（fork 子进程异步做）/ 配置定时。
- **fork + COW（写时复制）**：`bgsave` 时 `fork` 子进程，父子进程共享内存页，主进程继续写时触发 COW 复制页，保证子进程读到的是一致快照，且不阻塞写。
- **优缺点**：恢复快、文件紧凑；但两次快照之间宕机会**丢失最近一段时间数据**，`fork` 在大内存下也可能短暂阻塞。

### 4.2 AOF（追加日志）

- **原理**：写后日志（先执行命令、再写 AOF），记录每一条写命令，追加到 `appendonly.aof`。
- **三种刷盘策略**（`appendfsync`，高频考点）：
  - `always`：每次写命令都 fsync，最安全、最慢；
  - `everysec`（默认）：每秒 fsync 一次，折中，最多丢 1 秒数据；
  - `no`：交给操作系统决定，最快、最不可控。
- **AOF 重写（rewrite）**：文件里存的是命令，会膨胀，重写用「当前内存数据」生成一份等价的最小命令集（`bgrewriteaof`，同样 fork 子进程），瘦身且不阻塞。

### 4.3 混合持久化（Redis 4.0+）

- 重写后的 AOF 文件 = **RDB 快照头 + 增量 AOF 尾部**，兼顾「恢复快」和「丢数据少」，是生产推荐方案。

### 4.4 高频追问

- **RDB 和 AOF 怎么选**：RDB 适合做备份、冷备、快速恢复；AOF 适合要求低数据丢失。生产一般「RDB + AOF 混合」。
- **为什么 AOF 是写后日志**：先执行命令再记录，避免记录错误命令，且不需要额外校验；代价是记录前宕机丢最后一条命令。

## 五、过期删除与内存淘汰（易混淆，务必分清）

> 两个概念经常被混着问：**过期删除**针对「设置了 TTL 的 key 到期怎么删」，**内存淘汰**针对「内存满了还写新数据怎么办」。

### 5.1 过期删除策略：惰性删除 + 定期删除

- **惰性删除**：访问一个 key 时，如果已过期就删除并返回空。省 CPU，但「过期了却一直没人访问」的 key 会赖在内存里。
- **定期删除**：每隔一段时间（`activeExpireCycle`，默认 10 次/秒），随机抽取一批带 TTL 的 key，删掉其中过期的，控制单次执行时长，避免阻塞。
- **两者结合**：惰性删补定期删的漏网之鱼，定期删控制单次耗时。「key 过期了内存却没释放」的答案就在这里——它只是还没被惰性/定期删到。

### 5.2 内存淘汰策略（8 种，`maxmemory-policy`）

| 策略 | 作用范围 | 说明 |
|---|---|---|
| `noeviction`（默认） | — | 内存满时写命令直接报错，不淘汰 |
| `volatile-lru` | 带 TTL 的 key | 淘汰最近最少使用 |
| `allkeys-lru` | 所有 key | 淘汰最近最少使用（缓存常用） |
| `volatile-lfu` | 带 TTL 的 key | 淘汰最不经常使用 |
| `allkeys-lfu` | 所有 key | 淘汰最不经常使用 |
| `volatile-random` | 带 TTL 的 key | 随机淘汰 |
| `allkeys-random` | 所有 key | 随机淘汰 |
| `volatile-ttl` | 带 TTL 的 key | 淘汰剩余 TTL 最短的 |

- **LRU vs LFU**：LRU 看「最近有没有被访问」，LFU 看「历史访问频率」。热点数据长期被访问但最近一次较久，LFU 更能保住它。
- **生产怎么选**：纯缓存场景 `allkeys-lru` 或 `allkeys-lfu`；数据不能丢时 `noeviction` + 提前扩容告警。注意：设置了 TTL 但内存还有空间时，不会触发淘汰。

## 六、缓存三大问题：穿透 / 击穿 / 雪崩

> 这是 Redis 面试「送分也送命」的题。**区分三者的本质是「请求打到数据库的原因不同」**，先分清再谈方案，是高分关键。

### 6.1 缓存穿透（查不存在的数据）

- **现象**：请求查一个**数据库中根本不存在**的 key，缓存永远不命中，所有请求直接穿透到 DB。常见于恶意攻击（用随机 ID 刷）。
- **方案**：
  1. **缓存空值**：把「不存在」也缓存一个空对象/特殊值，短 TTL（如 1 分钟）。简单，但空值过多会占内存，且数据「从无到有」时有短暂不一致。
  2. **布隆过滤器**：在缓存前加一层布隆过滤器，判断 key 是否可能存在，不存在的直接拦截。省内存，但存在误判（说「可能存在」实际不存在），且删除数据要同步维护过滤器。
  3. **参数校验 + 限流**：对 ID 格式做合法性校验，配合接口限流兜底。

### 6.2 缓存击穿（热点 key 过期瞬间）

- **现象**：某个**热点 key 恰好过期**，瞬间大量并发请求同时回源数据库，把 DB 打挂。与穿透的区别：key 是真实存在的，只是「过期那一刻」并发回源。
- **方案**：
  1. **互斥锁重建缓存**：回源前先抢分布式锁，抢到的去查 DB 并写回缓存，其他请求等待后重试读缓存。缺点是加锁有等待，复杂。
  2. **逻辑过期（不删 key）**：value 里带逻辑过期时间，物理上不设置 TTL；读到时发现逻辑过期，先返回旧值，同时异步抢锁重建。避免「删了再建」的真空期，适合热点数据。
  3. **热点 key 永不过期 + 后台刷新**：对少数超级热点单独处理。

### 6.3 缓存雪崩（大批 key 同时失效 / 缓存整体故障）

- **现象**：**大量 key 在同一时间失效**，或 Redis 集群整体宕机，请求瞬间全部打到 DB。
- **方案**：
  1. **过期时间加随机值**：在基础 TTL 上叠加随机秒数，把失效时间打散。
  2. **多级缓存**：本地缓存（Caffeine）+ 分布式缓存（Redis）+ DB，逐层兜底。
  3. **限流降级**：DB 侧熔断限流，配合服务降级返回兜底数据。
  4. **高可用**：Redis 本身做主从/集群，避免单点整体宕机。

### 6.4 高频追问：三者的本质区别

- **穿透**：缓存和 DB 里都没有 → 缓存形同虚设；
- **击穿**：DB 里有，但热点 key 过期了 → 过期瞬间并发打 DB；
- **雪崩**：DB 里有，但大量 key 同时失效或缓存服务挂了 → 大批请求无缓存可挡。

> 加分话术：补一句「我项目里实际用 X 方案，为什么选它」，例如「商品详情用逻辑过期 + 互斥锁重建，因为它是强热点且容忍短时间旧数据」。

## 七、缓存与数据库一致性

字节前端岗面经里也出现「BFF 层有 Redis 缓存，怎么保证缓存和数据库一致性」，全栈岗更常问。

### 7.1 Cache Aside（旁路缓存，最常用）

- **读**：先查缓存，命中直接返回；未命中查 DB，写回缓存。
- **写**：**先更新数据库，再删除缓存**（而不是更新缓存）。

### 7.2 为什么「删缓存」而不是「更新缓存」

- 更新缓存会产生「写多读少时白更新」的浪费；
- 删缓存实现简单，下次读自然重建，天然避免并发更新导致缓存与 DB 值不一致的复杂时序；
- 更新缓存还可能引入两个写操作之间顺序竞争。

### 7.3 为什么「先更新 DB 再删缓存」比「先删缓存再更新 DB」好

- 先删缓存后更新 DB：删缓存后、DB 更新前，有读请求把旧数据写回缓存，造成较长窗口的脏数据。
- 先更新 DB 后删缓存：极端情况下（读旧值写回缓存 + 删缓存顺序颠倒）仍可能短暂不一致，但窗口更小，且可用「延迟双删」进一步收窄。

### 7.4 一致性增强手段

1. **延迟双删**：更新 DB 后删一次缓存，再延迟几百毫秒删第二次，兜住「删缓存前有旧值写回」的竞态。
2. **订阅 binlog（最终一致）**：用 Canal 等监听 MySQL binlog，DB 变更后异步删缓存/更新缓存。解耦业务代码，但引入 Canal 等组件和最终一致窗口。
3. **读写分离下的主从延迟**：写主读从时，主从同步延迟可能导致读到旧数据，需结合延迟双删或强制读主。

> 共识：**强一致要靠「分布式事务 + 串行化」，成本极高；缓存场景通常接受最终一致**，用「删缓存 + 兜底」保证短时间收敛即可。

## 八、高可用：主从复制 / 哨兵 / 集群

### 8.1 主从复制（读写分离、数据备份）

- **作用**：读扩展、数据冗余、为哨兵/集群做基础。
- **全量同步**：从节点首次连主，主 `bgsave` 生成 RDB 发给从，从加载后，主再把期间新增命令补发。
- **增量同步**：连接断开重连后，用 `psync` + 复制偏移量 `offset` 从 `repl_backlog_buffer`（环形缓冲区）补齐断线期间的增量。缓冲区不够或从太落后则退回全量同步。
- **复制方式**：Redis 2.8 前只有全量，2.8 后支持增量（`psync`）。主从默认异步复制，主挂时可能丢已同步前的那批数据。

### 8.2 哨兵 Sentinel（自动故障转移）

- **作用**：解决主从复制「主挂不能自动切换」的痛点，提供监控、故障转移、通知。
- **主观下线（SDOWN）**：单个哨兵认为某节点不可达。
- **客观下线（ODOWN）**：多数哨兵（`quorum`）都认为主下线，才判定主客观下线。
- **领导者选举**：哨兵间用类似 Raft 的投票（过半同意）选出一个 Leader 负责执行故障转移，从剩余从节点选新主（优先选偏移量最大、连接正常的从）。
- **局限**：本质还是「一主多从」，主节点仍是单写点，数据量大时单机内存撑不住。

### 8.3 集群 Cluster（数据分片）

- **哈希槽**：把数据分到 16384 个槽（slot），`slot = CRC16(key) % 16384`，每个主节点负责一部分槽。
- **请求重定向**：客户端访问的 key 不在当前节点时，节点返回 `MOVED`（槽已永久迁移到别的节点）或 `ASK`（槽正在迁移中），客户端去正确节点执行。
- **去中心化**：节点间用 **gossip 协议**交换状态、发现故障，不依赖中心协调节点。
- **高可用**：每个主节点配从节点，主挂时集群内部自动将从提升为主。
- **最少节点数**：至少 3 主 3 从（6 个节点）才能构成一个基本可用的高可用集群（3 主保证分片与投票过半，3 从保证故障转移）。

### 8.4 高频追问

- **哨兵 vs 集群的核心区别**：哨兵管「主从切换」，不管数据分片，写仍集中在一个主；集群管「数据分片 + 自动故障转移」，解决单机容量和写吞吐上限。
- **为什么是 16384 个槽**：够用（远超常见节点数）且心跳包里槽位位图更小（16384 位 = 2KB），比 65536 更省网络。

## 九、分布式锁（含 Redisson 看门狗、RedLock 争议）

### 9.1 基础版：一条命令原子加锁

```bash
# NX：不存在才设置（保证互斥）；PX 30000：30 秒过期（防止宕机死锁）
SET lock:order  {唯一标识UUID}  NX  PX  30000
```

- **value 放唯一标识**：不能放固定值，否则释放时无法判断「这把锁是不是我的」。
- **为什么释放锁必须用 Lua**：`GET` 判断 value + `DEL` 删除是两步，中间锁可能过期被别人拿到，直接 `DEL` 会误删别人的锁。用 Lua 把「判断 + 删除」做成原子操作：

```lua
-- 先校验 value 是自己的，再删，避免误删他人锁
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

### 9.2 锁过期但业务没执行完 → 看门狗（Watchdog）

- 问题：固定 TTL 下，业务耗时超过 TTL，锁提前过期，其他线程并发进入。
- **Redisson 看门狗**：调用 `lock()` 不显式传 `leaseTime` 时，默认锁 30 秒，看门狗每 10 秒（leaseTime/3）自动续期一次，把 TTL 重置为 30 秒，直到业务结束主动 `unlock()`。若显式传了 `leaseTime`，则不启用自动续期。

### 9.3 可重入：Redisson 用 Hash + HINCRBY（阿里高频题）

> 面经：阿里面试「redisson 分布式锁重入锁，为什么要有 HINCRBY 自增减一？」

- **为什么用 Hash 而非 String**：Hash 的 field 存「客户端/线程唯一标识（UUID:threadId）」，value 存重入次数，天然隔离不同线程，也支撑重入计数。
- **加锁**：`HINCRBY lock uuid:threadId 1`；**解锁**：`HINCRBY lock uuid:threadId -1`，结果归零才 `DEL` 整个 key。`HINCRBY` 是 Redis 原子命令，服务端完成计算，杜绝「先读后写」的竞态。
- **为什么不能先 GET 再 SET**：非原子，并发下计数丢失；为什么不用 `INCR on String`：所有线程共用一个计数器，无法区分谁持锁、谁重入。
- 完整加锁/解锁逻辑用 **Lua 脚本**包住，保证「判断锁归属 + 计数增减 + 过期刷新」整体原子。

### 9.4 RedLock（红锁）及其争议

- **动机**：单主从架构下，主节点宕机、锁还没同步到从，切主后可能出现「两个客户端同时拿到同一把锁」。
- **做法**：部署 N 个相互独立的主节点（无主从），客户端依次向每个主加锁，**过半（N/2+1）成功且总耗时 < 锁 TTL** 才算加锁成功。
- **争议**（Martin Kleppmann 等批评）：依赖系统时钟（NTP 跳跃可能让锁提前过期），不是真正的共识协议；极端时钟异常下安全假设不成立。所以**面试别把 RedLock 当「标准答案」吹，聊它的动机和局限更显功力**。

### 9.5 高频追问清单

- 锁的重入怎么实现？→ Hash + HINCRBY。
- 业务没执行完锁过期怎么办？→ 看门狗续期。
- 释放锁为什么用 Lua？→ 判断 + 删除原子化。
- 主从切换锁丢了怎么办？→ RedLock 动机，但注意其争议。

## 十、大 key / 热 key 与线上排查

### 10.1 大 key

- **定义**：单个 key 的 value 过大（超大 String，或几十万字段的 Hash、超长 List/Set）。
- **危害**：单线程下大 key 读写阻塞其他请求；网络传输慢；`DEL` 大 key 阻塞主线程（可用 `UNLINK` 异步删）；内存不均导致集群倾斜。
- **发现**：`redis-cli --bigkeys`（扫描慢，建议在从节点执行）、`memory usage key`、慢查询日志。
- **处理**：拆分（大 Hash 按用户 ID 分片成多个小 Hash）、压缩 value、存对象只存必要字段、`UNLINK` 异步删除、源头规范「单个 value 不超过 10KB、集合元素不超过几千」。

### 10.2 热 key

- **定义**：被极高频访问的 key（如爆款商品详情）。
- **危害**：集中在单个节点/单 key，成为性能瓶颈，甚至打爆网卡。
- **发现**：`redis-cli --hotkeys`（需提前配置）、`monitor`（性能杀手，仅短时用）、代理层/客户端埋点统计。
- **处理**：
  1. **本地缓存兜底**：Caffeine/Guava 本地缓存热点数据，减少对 Redis 的压力；
  2. **多副本**：热 key 复制多份 `hotkey_0`/`hotkey_1`/`hotkey_2`，访问时随机取一份分摊；
  3. **读写分离**：读走从节点；
  4. **二级缓存架构**：本地缓存 + Redis 集群。

### 10.3 线上内存持续增长怎么排查（压力测试题）

1. `info memory` 看内存与碎片率；
2. `redis-cli --bigkeys` 找大 key；
3. `redis-cli --hotkeys` 找热 key；
4. `info commandstats` 看命令统计；
5. 检查业务代码：是否忘了设过期时间、是否 key 设计不收敛导致无限制增长。

## 十一、其他高频：事务 / Lua / pipeline / 消息队列 / 与 Memcached 对比

### 11.1 事务、Lua、pipeline 的原子性区别（常被混问）

- **事务（MULTI/EXEC）**：命令打包顺序执行，**执行期间不被其他命令插队**（原子性），但中间某条命令出错**不会回滚**已执行的命令，是「弱事务」。`WATCH` 提供乐观锁（key 被改则放弃执行）。
- **Lua 脚本**：脚本整体在 Redis 内**原子执行**，且可做判断逻辑，比事务更灵活，常用来实现分布式锁释放、复杂原子操作。
- **pipeline 管道**：批量发送多条命令、一次读回所有结果，**只减少网络 RTT，不保证原子性**。它和事务/Lua 的本质区别是「性能优化 vs 原子性」。

### 11.2 用 Redis 做消息队列

- 简单场景用 **List**（`LPUSH` + `BRPOP` 阻塞读），但无消费组、无 ACK、消息可靠性弱。
- 更推荐 **Stream**（5.0+）：支持消费组、`XACK` 确认、`PEL` 未确认列表，接近轻量 MQ。高可靠、顺序严格、堆积量大的场景仍建议 Kafka/RocketMQ。

### 11.3 用 ZSet 做延时队列

- 分数 = 目标执行时间戳，`ZADD` 入队，消费者轮询 `ZRANGEBYSCORE 0 now` 取到期任务，处理完 `ZREM`。适合简单延时任务，量大仍需专业方案。

### 11.4 Redis 与 Memcached 对比

- **数据类型**：Redis 丰富（String/Hash/List/Set/ZSet 等），Memcached 基本只有 String。
- **持久化**：Redis 支持 RDB/AOF，Memcached 纯内存断电即失。
- **线程模型**：Redis 命令单线程 + IO 多线程，Memcached 多线程。
- **适用**：Redis 全能缓存 + 数据结构 + 分布式锁；Memcached 适合「纯 KV 缓存、大 value、多核简单读」的老场景，现基本被 Redis 取代。

## 十二、Redis 8.0 新特性（2025 新趋势，聊到即加分）

> 面试聊到「Redis 有什么新东西」时，这套内容能体现你跟进技术趋势，尤其契合「AI 工程化」的人设。

- **8 种新数据结构**：
  - **Vector Set（向量集合）**：基于 ZSet 设计理念，支持高维向量嵌入的相似性检索，面向语义搜索、推荐系统等 AI 场景；
  - **JSON**：将 JSON 文档作为值存储，支持 JSONPath 检索、原子局部更新，无需整取整改；
  - **TimeSeries（时间序列）**：面向 IoT、遥测、股票行情等带时间戳数据的场景；
  - **5 种概率结构**：Bloom Filter（是否出现过）、Cuckoo Filter（可删的布隆）、Count-min sketch（出现次数估计）、Top-k（最频繁值）、t-digest（分位数）。
- **查询引擎增强**：支持在 Hash 和 JSON 上建二级索引，支持精确匹配、范围、全文检索（词干/同义词/模糊）、向量相似搜索；多线程查询执行，吞吐提升 16 倍。
- **性能**：新 I/O 线程（`io-threads`）吞吐提升 1 倍；149 项基准中 90 个命令更快；新复制机制同步时间减少 18%。

## 十三、高频追问速记（考前扫一遍）

| 问题 | 一句话答案 |
|---|---|
| 为什么快 | 内存 + 单线程免锁 + IO 多路复用 |
| 是不是多线程 | 命令执行单线程，6.0/8.0 只多线程化网络 IO 和查询引擎 |
| String 底层 | SDS：O(1) 长度、二进制安全、防溢出 |
| List 底层 | quicklist（链表 + listpack） |
| ZSet 为什么用跳表 | 实现简单、范围/排名查询友好、无旋转 |
| Hash 底层 rehash | 渐进式 rehash，避免阻塞 |
| RDB vs AOF | RDB 快照恢复快丢数据；AOF 日志低丢失；生产用混合 |
| 过期删 key 方式 | 惰性删除 + 定期删除 |
| 内存淘汰默认 | noeviction，缓存场景用 allkeys-lru/lfu |
| 穿透/击穿/雪崩 | 布隆过滤器+空值 / 互斥锁+逻辑过期 / 随机过期+多级缓存 |
| 一致性 | Cache Aside 先更新 DB 再删缓存，延迟双删/binlog 兜底 |
| 主从 vs 哨兵 vs 集群 | 读扩展 / 自动故障转移 / 哈希槽分片 |
| 分布式锁释放为什么 Lua | 判断 + 删除原子化防误删 |
| Redisson 可重入 | Hash + HINCRBY 计数 |
| 看门狗 | 默认 30s 锁，每 10s 自动续期 |
| 大 key/热 key | --bigkeys/--hotkeys 定位，拆分/多副本/本地缓存 |
