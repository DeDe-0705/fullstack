# 浏览器存储与缓存

---

## 一、浏览器缓存层级（从快到慢）

```
Service Worker Cache  (代码控制，可拦截请求)
       ↓ 未命中
Memory Cache  (内存缓存，Tab关闭即释放)
       ↓ 未命中
Disk Cache  (硬盘缓存，持久化)
       ↓ 未命中
Push Cache  (HTTP/2 推送，会话级别，基本淘汰)
       ↓ 未命中
网络请求 → 走 HTTP 缓存策略（强缓存/协商缓存）
```

### Memory Cache vs Disk Cache

| 维度 | Memory Cache | Disk Cache |
|------|-------------|------------|
| 存储位置 | 内存 | 硬盘 |
| 速度 | 极快 | 较快 |
| 容量 | 小 | 大 |
| 生命周期 | Tab 关闭即释放 | 持久化，直到过期或被清理 |
| 典型资源 | 当前页面频繁访问的 JS/CSS/图片 | 大文件、不常用资源 |

**浏览器如何决定？** 通常：当前页面刚加载的资源进 Memory Cache，后续请求命中率低的降级到 Disk Cache。`base64` 内嵌图片不走缓存（因为嵌在 HTML/CSS 里）。

### Service Worker Cache

```js
// 注册
navigator.serviceWorker.register("/sw.js");

// sw.js — 拦截请求，自定义缓存策略
self.addEventListener("fetch", (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => {
      // 缓存优先策略
      return cached || fetch(event.request).then((res) => {
        return caches.open("v1").then((cache) => {
          cache.put(event.request, res.clone());
          return res;
        });
      });
    })
  );
});
```

SW 缓存完全由 JS 控制，可以实现离线访问、更精细的缓存策略。

## 二、客户端存储全景对比

| 特性 | Cookie | localStorage | sessionStorage | IndexedDB |
|------|--------|-------------|----------------|-----------|
| 容量 | ~4KB | ~5-10MB | ~5-10MB | 通常无上限（取决于磁盘） |
| 生命周期 | 可设过期时间 | 永久（除非手动清除） | Tab 关闭即清除 | 永久 |
| 作用域 | 同源 + Path | 同源 | 同源 + 同 Tab | 同源 |
| 随请求发送？ | 是（自动带在 Header） | 否 | 否 | 否 |
| API 类型 | 字符串读写 | 同步 key-value | 同步 key-value | 异步，支持索引和事务 |
| 存储类型 | 字符串 | 字符串 | 字符串 | 任意 JS 类型（结构化克隆） |
| 同源限制 | 是 | 是 | 是 | 是 |

## 三、Cookie 深入

### 核心属性

```
Set-Cookie: token=abc123; 
            Domain=.example.com;    -- 作用域（可跨子域）
            Path=/;                 -- 路径限制
            Max-Age=3600;           -- 相对过期秒数（优先于 Expires）
            Expires=Wed, 21 Jul 2026 00:00:00 GMT;  -- 绝对过期时间
            HttpOnly;               -- JS 无法读取（防 XSS）
            Secure;                 -- 仅 HTTPS 传输
            SameSite=Strict;        -- 跨站请求控制（Strict/Lax/None）
```

### SameSite 三种模式

| 值 | 行为 | 场景 |
|----|------|------|
| `Strict` | 完全禁止跨站发送 Cookie | 银行等极高安全需求 |
| `Lax` (默认) | 允许跨站 GET 导航（如点击链接）发送 Cookie | 推荐默认值 |
| `None` | 允许跨站发送，但必须同时设置 `Secure` | 第三方嵌入场景 |

### Cookie 的面试追问

**Q: 为什么 Cookie 要设 HttpOnly？**

防止 XSS 攻击中通过 `document.cookie` 窃取 token。HttpOnly 的 Cookie JS 完全读不到。

**Q: Cookie 和 Session 的关系？**

Cookie 是客户端存储机制，Session 是服务端存储。常见模式：Cookie 里存 sessionId，服务端据此查 Session 数据。JWT 则可以完全替代这个模式（Token 自包含信息，服务端不存）。

**Q: 同源策略对 Cookie 的限制？**

Cookie 的"源"只看 Domain + Path，不看协议和端口。`http://a.com` 和 `https://a.com` 的 Cookie 可能共享（如果没有 Secure 限制）。

## 四、localStorage vs sessionStorage

### 相同点

- 同源策略：每个域名独立存储
- API 相同：`setItem` / `getItem` / `removeItem` / `clear`
- 仅存储字符串（对象需 `JSON.stringify`）
- 同步 API（注意：大操作可能阻塞主线程）

### 差异

```js
// localStorage — 永久存储，跨 Tab 共享
localStorage.setItem("theme", "dark");
window.addEventListener("storage", (e) => {
  // 其他 Tab 修改 localStorage 时触发（本 Tab 不触发）
  console.log(e.key, e.oldValue, e.newValue);
});

// sessionStorage — Tab 级隔离
sessionStorage.setItem("temp", "data");
// 新开 Tab（即使同 URL）也拿不到这个数据
// 关闭 Tab 自动清除
```

**面试重点：** `storage` 事件只在**其他**同源页面修改 localStorage 时触发，本页面不触发。

## 五、IndexedDB

### 核心概念

```
数据库 (Database)
  └── 对象仓库 (Object Store)  ← 类似 SQL 的表
        └── 索引 (Index)       ← 加速查询
              └── 记录 (Record) ← 结构化克隆存储
```

所有操作都是**异步**的，基于事务（Transaction）。

### 基础用法

```js
// 打开/创建数据库
const request = indexedDB.open("MyDB", 1);

request.onupgradeneeded = (e) => {
  const db = e.target.result;
  // 创建对象仓库 + 索引（只能在 onupgradeneeded 里操作）
  const store = db.createObjectStore("users", { keyPath: "id" });
  store.createIndex("name", "name", { unique: false });
  store.createIndex("email", "email", { unique: true });
};

request.onsuccess = (e) => {
  const db = e.target.result;

  // 写操作：创建事务
  const tx = db.transaction("users", "readwrite");
  const store = tx.objectStore("users");
  store.add({ id: 1, name: "Alice", email: "alice@example.com" });

  tx.oncomplete = () => console.log("写入完成");

  // 读操作
  const readTx = db.transaction("users", "readonly");
  const readStore = readTx.objectStore("users");
  const getReq = readStore.get(1);
  getReq.onsuccess = () => console.log(getReq.result);

  // 索引查询
  const idx = readStore.index("email");
  idx.get("alice@example.com").onsuccess = (e) => console.log(e.target.result);
};
```

### 为什么不用 localStorage 存大量数据？

1. **容量**：localStorage 只有 5-10MB，IndexedDB 几乎无限制
2. **性能**：localStorage 同步 API 阻塞主线程；IndexedDB 异步
3. **查询**：localStorage 只能全量读取再过滤；IndexedDB 支持索引查询
4. **类型**：localStorage 只能存字符串；IndexedDB 支持结构化克隆（对象、File、Blob 等）

## 六、容量限制和清除策略

| 存储 | 容量限制 | 清除时机 |
|------|----------|----------|
| Cookie | ~4KB / 域名，~50条 / 域名 | 过期时间或手动清除 |
| localStorage | ~5-10MB / 域名 | 手动清除或浏览器"清除数据" |
| sessionStorage | ~5-10MB / 域名 | 关闭 Tab |
| IndexedDB | 磁盘可用空间（浏览器可能限制占比） | 手动清除或浏览器"清除数据"，Chrome 可能在存储压力下清除"最久未用" |
| Cache API (SW) | 磁盘可用空间 | 手动或 LRU 淘汰 |

## 七、实战场景选型

| 场景 | 推荐 | 原因 |
|------|------|------|
| 用户登录 Token | Cookie (HttpOnly + Secure + SameSite) | 自动发送，防 XSS |
| 主题/语言偏好 | localStorage | 永久存储，不随请求发送 |
| 表单草稿 | sessionStorage | Tab 关闭自动清除，避免残留 |
| 用户配置（跨 Tab 同步） | localStorage + storage 事件 | 一 Tab 修改，其他 Tab 感知 |
| 离线数据/大量结构化数据 | IndexedDB | 大容量、索引查询、异步 |
| 离线页面资源 | Service Worker Cache | 拦截请求，离线可用 |
| 临时跨页面数据 | sessionStorage（同 Tab）/ localStorage（跨 Tab） | 按需选择 |
| 第三方追踪 | Cookie (SameSite=None + Secure) | 跨站携带 |
