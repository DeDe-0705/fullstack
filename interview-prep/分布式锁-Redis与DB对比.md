# 分布式锁：Redis 与 DB 对比

> 解决「并发下如何互斥」的两条路径。核心结论一句话：
>
> **分布式锁是「性能优化手段」，不是「数据正确性保障」；数据正确性最终靠 DB 唯一约束 / 乐观锁 / 条件更新兜底。**

---

## 一、本质：两个层面

- **DB 锁** = 数据层的并发控制，锁的是「数据本身」，靠 MySQL 自带的行锁 / 事务 / 约束实现。
- **Redis 锁** = 业务层的互斥，锁的是「业务流程 / 动作」，靠 Redis 原子命令实现跨实例互斥。

判断口诀：**锁「数据」用 DB，锁「流程」用 Redis。**

---

## 二、DB 的锁是什么

### 2.1 行锁 / 表锁（悲观锁）

```sql
-- 显式加行锁：锁住要改的那一行
SELECT * FROM account WHERE id = 1 FOR UPDATE;
UPDATE account SET balance = balance - 100 WHERE id = 1;
```

细节：InnoDB 的 `FOR UPDATE` **只有通过索引检索时才走行级锁，否则退化成表级锁**。

### 2.2 事务 + 隔离级别

保证一组操作的 ACID，多个实例连同一个 DB，所以行锁/事务对所有实例天然生效——本质上是「分布式」的。

### 2.3 唯一约束（防重复）

```typescript
@Unique(['userId', 'date'])   // 从根上防重复插入
```

### 2.4 乐观锁（防并发覆盖）

```typescript
@VersionColumn() version: number;
await repo.update({ id, version }, { balance: newBalance });
// version 不匹配 → 被并发改过，抛错重试
```

## 三、Redis 的分布式锁是什么

### 3.1 加锁 / 解锁

```bash
# 加锁：NX 表示 key 不存在才成功，EX 10 表示 10 秒自动过期
SET lock:order:123 唯一请求id EX 10 NX
```

```typescript
const ok = await redis.set(`lock:order:${id}`, myId, 'EX', 10, 'NX');
if (!ok) return '系统繁忙';
try {
  // 临界区
} finally {
  // 用 Lua 保证「校验归属 + 删除」原子，防止误删别人的锁
  const lua = `
    if redis.call('get', KEYS[1]) == ARGV[1] then
      return redis.call('del', KEYS[1])
    else return 0 end`;
  await redis.eval(lua, 1, `lock:order:${id}`, myId);
}
```

### 3.2 合格锁的 4 要素

1. **互斥**：同一时刻只有一个能持有；
2. **原子加锁**：`SET NX EX` 一条命令完成；
3. **超时释放**：持锁方崩溃不永久占锁；
4. **锁归属**：只有加锁的人能解锁（value 存唯一标识 + Lua 校验）。

### 3.3 看门狗（Watchdog）续期

锁快过期但业务没跑完怎么办？后台定时续期。Redisson 默认 30s 过期，看门狗每隔 1/3 时间检查并续期，业务完成再释放。

## 四、三种分布式锁实现对比

| | 数据库（DB） | Redis | ZooKeeper |
|---|---|---|---|
| 比喻 | 登记本（简单但慢） | 抢红包（快但可能抢丢） | 排队叫号（强一致但重） |
| 性能 | 慢 | 快 | 中 |
| 可靠性 | ACID，强 | 有超时/误删/主从切换坑 | 强一致 |
| 实现 | 唯一约束 / FOR UPDATE | SET NX EX | 临时顺序节点 |
| 适用 | 核心数据、长事务 | 高并发、短事务 | 对一致性要求极高的场景 |

## 五、Redis 锁 vs DB 锁核心对比

| 维度 | DB 锁 | Redis 锁 |
|---|---|---|
| 锁的对象 | 某行/表数据 | 某个业务动作/流程 |
| 性能 | 走磁盘/事务，较重 | 纯内存，极快 |
| 可靠性 | 强（ACID、无过期风险） | 有锁过期、误删、主从切换等坑 |
| 释放 | 事务结束自动释放 | 手动 + 超时释放 |
| 审计合规 | 符合金融审计要求 | 难满足强审计 |

## 六、场景判断（重点）

### 用 DB 锁：低并发、长事务、核心数据

| 场景 | 手段 |
|---|---|
| 转账、余额变更（资金） | 事务 + `FOR UPDATE` |
| 扣库存、防超卖 | 原子 `UPDATE ... WHERE num > 0` |
| 防重复插入 | 唯一约束 |
| 防并发覆盖 | 乐观锁 `@VersionColumn` |

### 用 Redis 锁：高并发、短事务、非核心数据

| 场景 | 为什么 |
|---|---|
| 定时任务只允许一个实例跑 | 避免多副本重复执行 |
| 秒杀「抢名额」 | 扣库存前先快速失败挡流量 |
| 防重复提交 / 幂等 | 幂等键 `SET NX` |
| 调用第三方 API 的互斥限流 | 临界区不碰 DB，DB 锁管不到 |

一句话：**金融、资金这类「数据安全 > 性能」用 DB 锁；秒杀、营销这类「性能 > 少量异常容忍」用 Redis 锁。**

## 七、组合拳：秒杀扣库存「三段式」

```
第一段：Redis Lua 预扣   → 高性能扛并发，快速失败
第二段：MQ 异步          → 削峰解耦
第三段：DB 乐观锁/条件更新 → 兜底防超卖，保证数据正确
```

核心原则：**Redis 锁负责「削峰降流量」，DB 锁负责「兜底保正确」**，各司其职，不能只靠 Redis 锁保证正确性。

---

## 八、进阶坑

1. **锁提前过期**：业务没跑完锁就过期 → 看门狗续期（Redisson 默认机制）。
2. **主从切换丢锁**：主库刚加锁就挂，从库还没同步 → RedLock（多节点过半加锁）缓解，但 RedLock 有争议（依赖时钟假设，NTP 跳跃可能锁提前过期，非真正共识协议）。
3. **误删别人的锁**：锁过期后 A 删了已属于 B 的锁 → 用 value 唯一标识 + Lua 原子「校验 + 删除」。

需要强一致且不差钱的场景，可以考虑 ZooKeeper（临时顺序节点 + watch），而非硬用 Redis。

---

## 九、面试话术（直接背）

> **区别**：DB 锁是数据层并发控制（行锁/事务/唯一约束/乐观锁），锁的是数据本身；Redis 锁是业务层互斥（SET NX EX），锁的是流程动作。
>
> **选型**：核心数据、长事务、要审计用 DB 锁（`FOR UPDATE`、唯一约束）；高并发、短事务、非核心用 Redis 锁。
>
> **底线**：分布式锁只是性能优化手段，数据正确性最终靠 DB 唯一约束 / 乐观锁 / 条件更新兜底，Redis 锁不能单独保证正确性。
