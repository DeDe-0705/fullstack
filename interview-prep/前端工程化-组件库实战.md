# 前端工程化实战：组件库封装与发布全链路（ui-kit）

> 实操日期：2026-08-01 ｜ 仓库：[github.com/DeDe-0705/ui-kit](https://github.com/DeDe-0705/ui-kit) ｜ npm 包：[@king-dede/ui](https://www.npmjs.com/package/@king-dede/ui) `0.1.3`
>
> 配套理论：`前端工程化.md` 第三章（CI/CD）、第四章（组件库建设）

## 一、项目概览

**目标**：基于 Ant Design 封装业务组件，用真实项目把「组件库打包 → 版本发布 → git tag → CI/CD → npm 发布」完整跑通，作为前端工程化面试的实操弹药。

**结果**：`@king-dede/ui@0.1.3` 已成功发布到 npm（latest tag），从提交到发布全自动链路可用。

**目录结构**（pnpm workspace monorepo）：

```text
ui-kit/
├── packages/ui/          # 组件库源码（@king-dede/ui）
│   ├── src/components/   # ConfirmButton / Authorized
│   ├── src/hooks/        # useAsyncAction
│   └── tsup.config.ts    # ESM + CJS + dts 打包配置
├── apps/                 # 组件展示站（Vite + Tailwind v4 + 侧边栏导航）
├── .github/workflows/    # ci.yml + release.yml
└── package.json          # 根脚本 + standard-version 配置
```

**技术栈**：React 19 + TypeScript + Ant Design v6 + tsup + pnpm workspace + commitlint/husky + standard-version + GitHub Actions。

## 二、关键选型决策（附面试答法）

### 2.1 为什么用 antd v6 而不是 v5

antd v6（2025-11 发布）是当前稳定大版本：

- **原生支持 React 19**，不再需要 v5 的 `@ant-design/v5-patch-for-react-19` 兼容补丁
- 默认 **CSS Variables** 方案，支持 zeroRuntime 模式（构建期抽静态 CSS，运行时不再注入样式）
- 要求 React >= 18、`@ant-design/icons` >= 6，仅支持现代浏览器（放弃 IE）

> 面试答法：选型时关注"版本与主技术栈的兼容性"（React 19 原生支持）+ "架构演进"（v5 运行时 CSS-in-JS → v6 零运行时 CSS），体现持续跟进官方迁移文档的习惯。

### 2.2 打包为什么用 tsup

tsup 不是独立打包器，而是 **esbuild 的库模式封装**；rollup 是真正的 bundler（JS 实现）。组件库场景对比：

| 维度 | rollup | tsup |
| --- | --- | --- |
| 速度 | JS 实现，慢 | esbuild（Go）实现，快 4–5 倍 |
| 产物质量 | tree-shaking / code splitting 更强，复杂库更干净 | 够用，精度有限 |
| 配置 | 灵活但繁琐（dts/external/多格式要拼插件） | 一个 defineConfig 全搞定 |
| 生态 | 插件丰富 | 插件少，特殊需求用 esbuildPlugins |

2026 年趋势：Vite 8 已用 **Rolldown**（Rust 版 rollup）统一打包；tsdown 是 tsup 的 Rolldown 继任者。面试能说出"tsup 本质是 esbuild 封装，而 esbuild/rollup 正在被 Rolldown 取代"是加分项。

### 2.3 为什么 monorepo 这样分

- `packages/*` = 可发布包集合，每个包独立版本（`packages/ui`，未来可加 `packages/hooks`、`packages/utils`）
- `apps/` = 应用集合，当前展示站直接放在 `apps/` 本身
- pnpm workspace 配置：`packages/*` 通配多包，`apps` 精确指向当前应用

### 2.4 版本管理为什么先选 standard-version

- 单包场景配置简单：读 git log → 按 SemVer bump → 生成 CHANGELOG → 打 annotated tag → 自动 commit
- 升级路径：多包独立版本时迁移 changesets（每个变更一个 `.changeset` 文件，适合团队协作）
- 备选：semantic-release（全自动但黑盒，需要 GitHub App/权限配置）

### 2.5 CI 设计原则：tag 是发布触发器

不在本地 `npm publish`，而是：

```text
本地：standard-version 升版本 + 打 v* tag + push
  ↓ GitHub Actions
CI：检测 v* tag → 干净环境 install/build → npm publish（NPM_TOKEN）
```

发布动作可复现、可审计，版本号是唯一事实来源。

### 2.6 预发布（beta）通道设计

"beta 版本"包含两个层次，面试要分开讲：

- **SemVer 预发布版本号**：`0.1.4-beta.0`，语义上小于正式版 `0.1.4`
- **npm dist-tag**：`latest` / `beta` 是安装通道，`npm i pkg@beta` 才拉预发布版；**发布预发布版本必须显式 `--tag beta`，否则 npm 默认标成 latest**

落地方式（ui-kit 已实现）：

- `pnpm release:beta` = `standard-version --prerelease beta`：从当前版本生成 `x.y.z-beta.0` 并打 `v0.1.4-beta.0` tag
- `release.yml` 发布时按 tag 分流：`contains(github.ref_name, '-beta')` → `--tag beta`，否则 `latest`
- 更规范的团队方案是 changesets pre mode：`changeset pre enter beta` 进入预发布模式 → 全部走 beta 通道 → `pre exit` 统一转正

0.x 阶段可以直接发 latest（0.x 本身就有不稳定语义），1.x 且有真实使用方后 beta 通道才有明显价值。

**实测记录（2026-08-01）**：`pnpm release:beta` 生成 `0.1.4-beta.0` + `v0.1.4-beta.0` tag → CI 自动发到 beta 通道。发布后 npm 状态：`dist-tags: { latest: 0.1.3, beta: 0.1.4-beta.0 }`，即 `npm i @king-dede/ui` 装正式版、`npm i @king-dede/ui@beta` 装预发布版。

## 三、完整链路复盘（从 0 到 npm 发布）

1. **提交规范**：commitlint（conventional commits）+ husky，pre-commit 跑 lint-staged，commit-msg 校验 `feat:`/`fix:` 等
2. **打包**：tsup 产出 `dist/index.js`（ESM）+ `dist/index.cjs`（CJS）+ `.d.ts`；react/react-dom/antd 全部 external；`sideEffects: false` 支持 tree-shaking
3. **版本发布**：`pnpm release` = `standard-version && git push --follow-tags`
4. **CI 校验**：`ci.yml` 在 PR/主分支跑 lint → typecheck → build
5. **发布**：push `v*` tag 触发 `release.yml` → 构建 → `pnpm --filter @king-dede/ui publish`
6. **验证**：npm registry 确认 `dist-tags.latest = 0.1.3`

实际版本轨迹：`0.1.0`（初始）→ `0.1.1`（首次实测发布，scope 问题未发成功）→ `0.1.2`（换包名，workflow filter 漏改未发成功）→ `0.1.3`（✅ 正式版发布成功）→ `0.1.4-beta.0`（✅ beta 通道发布成功，latest 不受影响）。

## 四、踩坑记录（全部是面试素材）

### 4.1 本地能过、CI 挂掉：残留产物兜底

apps 的 tsconfig `paths` 指向 `@king-dede/ui` 源码时相对路径写错（`../../packages` 越到了工作区外）。本地 typecheck 通过是因为本地先 build 出了 `packages/ui/dist`，tsc 兜底从 node_modules 解析到了产物类型；**CI 是干净环境，dist 不存在直接报错**。

> 面试答法：CI 的价值就是暴露"本地有残留产物/缓存兜底"掩盖的问题，所以 CI 必须 `--frozen-lockfile` + 全新 checkout。

### 4.2 TypeScript 6.0 与 tsup dts 兼容

tsup 的 dts 步骤内部传入了已废弃的 `baseUrl` 选项，TS 6.0 直接报 `TS5101`。解法：tsconfig 加 `"ignoreDeprecations": "6.0"`。

### 4.3 standard-version 配置键：`infile` 不是 `changelogFile`

配错键导致 CHANGELOG 写到根目录而非 `packages/ui/CHANGELOG.md`。正确配置：

```json
{
  "standard-version": {
    "packageFiles": [{ "filename": "packages/ui/package.json", "type": "json" }],
    "bumpFiles": [{ "filename": "packages/ui/package.json", "type": "json" }],
    "infile": "packages/ui/CHANGELOG.md"
  }
}
```

### 4.4 0.x 版本下 feat 只升 patch（preMajor 规则）

standard-version 默认 `conventionalcommits` 预设：版本 < 1.0.0 时 `preMajor: true`，`feat` 从 minor **降级为 patch**。所以 `0.1.0 + feat/fix → 0.1.1` 是符合规则的；`1.0.0` 之后 `feat → minor`。面试问"为什么我 feat 了版本没升 minor"就是这个问题。

### 4.5 npm scope 会被占用：@vibe 是 monday.com 的

`@vibe` 是 monday.com 官方组织的 scope（Vibe 设计系统），任何人无法发布 `@vibe/*` 下的包。npm 返回 404（与 2FA/token 无关）。**选 scope 前先查 registry**：`curl https://registry.npmjs.org/@scope%2fpkg`。最终改用个人 scope `@king-dede/ui`。

### 4.6 npm 2026 新安全政策：GAT + bypass 2FA

- npm 强制发布者开启 2FA；CI 发布必须用 **Granular Access Token（GAT）**，勾选 **Bypass 2FA when publishing**
- 带写权限的 GAT **有效期上限 90 天**，到期要重新生成并更新 secret
- 2027-01 起 2FA-bypass token 将失去直接发布能力，改为"暂存发布 + 维护者 2FA 审批"，长期方案是 trusted publishing

> 常见报错：`E403 ... bypass 2fa enabled is required` = token 类型不对/账号未开 2FA；`E404 PUT` = scope 被占用或 GAT 未授权该包。

### 4.7 rg 默认不搜隐藏目录

批量替换包名时 `rg` 默认跳过 `.github/`，导致 `release.yml` 里 filter 还是旧包名，publish 步骤输出 `No projects matched the filters` 却静默成功（退出码 0）。全局搜索记得 `rg --hidden`。

## 五、面试考点对照 + 高频追问

| 考点 | 本项目对应实现 |
| --- | --- |
| ESM/CJS 双产物、`exports` 字段 | `packages/ui/package.json` + `tsup.config.ts` |
| 为什么 react/antd 要 external | 避免 React 多实例，库只发业务代码 |
| tree-shaking / `sideEffects: false` | package.json + tsup `treeshake` |
| 组件 API 设计（透传、受控、ref） | `ConfirmButton` props 透传 + React 19 ref-as-prop |
| Monorepo / pnpm workspace | `pnpm-workspace.yaml` |
| 语义化版本 + 自动打 tag | standard-version 配置 |
| CI/CD 发布流水线 | `.github/workflows/` 两个 workflow |
| npm 发布安全策略 | GAT + bypass 2FA（2026 新规） |

**高频追问演练**：

1. 为什么 `external` 掉 react/antd？→ 防止多实例、保持 peer 关系；否则打包体积膨胀且 React hooks 状态错乱
2. `main`/`module`/`exports` 的区别？→ exports 是现行标准，import/require 条件导出，types 优先
3. ESM 和 CJS 为什么都要？→ 老项目 require、新项目 import，Node 与浏览器场景兼顾；`type: module` + `.cjs` 后缀
4. 为什么 tag 触发发布而不是 push main？→ tag 是不可变发布点，可回滚、可审计；main 可能包含未发布变更
5. standard-version / changesets / semantic-release 怎么选？→ 单包快速起步选 standard-version；多包协作选 changesets；全自动带 changelog/通知选 semantic-release
6. 组件库如何避免过度封装？→ 只抽"跨业务重复 2 次以上"的组件；保留原生 API 透传；职责单一；用组合而非继承
