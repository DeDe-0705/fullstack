# 高并发场景综合应答主轴（NestJS + MySQL + Redis）

> 定位：把 **NestJS（应用层）+ MySQL（存储层）+ Redis（缓存层）** 串成**一条能直接背的高并发应答主线**。面试官问"怎么做高并发/高复用"时，不要单点背八股，要从**一次请求的完整链路**分层讲，把 **N+1、B+树** 挂到对应环节。

---

## 一、先定场景（开头说清，显出深度）

> "我以**高并发、读多写少**的业务为例，比如商品详情 / 热点数据。QPS 很高，**读远大于写**，所以核心是**把读扛住**，写走**事务 + 幂等**。我的技术栈是 NestJS + MySQL + Redis，按**请求从入口到存储**分层讲怎么扛。"

**一句话锚定**：高并发 = 应用层复用 + MySQL 索引与事务 + Redis 扛读与降级。

---

## 二、一次请求的分层主轴

| 层 | 高并发怎么做 | 高频痛点 / 面试挂点 |
|---|---|---|
| **入口/网关** | 限流（令牌桶）、防刷、鉴权 | 别一上来就把流量打到 DB |
| **应用层 NestJS** | **高复用**：模块化 + DI，公共逻辑抽 Service，拦截器/守卫/管道统一鉴权、日志、校验（横切复用）；**连接池**；写走事务；**幂等** | **N+1**、连接池耗尽、重复下单 |
| **MySQL** | **B+树索引**；事务隔离 RR；EXPLAIN 慢查询 | **B+树**、索引失效、深分页、MVCC |
| **Redis** | **cache-aside** 扛读；过期加随机防雪崩；分布式锁防击穿；挂了降级 | 缓存一致性、穿透/击穿/雪崩、分布式锁 |

### 2.1 应用层 NestJS：高复用

- **模块化 + 依赖注入**：把可复用逻辑抽到 Service，控制器只做编排。
- **横切复用**：用 `@UseGuards`/`@UseInterceptors`/`@UsePipes` 统一做**鉴权、日志、参数校验、统一响应格式**，避免每个接口重复写。
- **连接池**：容量公式 `connections = (core_count * 2) + effective_spindle_count`，**别开满**（默认 10 左右），否则高并发下连接池反而成为瓶颈。
- **事务 + 幂等**：写操作包事务；幂等用 **唯一约束（Duplicate entry 即重复请求）+ 幂等键 + 乐观锁版本号**，避免重复下单/超卖。

### 2.2 MySQL：读效率的根基

- **B+树聚簇索引**：主键索引叶子存整行；二级索引叶子存主键值（回表）。
- **覆盖索引**：查询列全在索引里，**避免回表**。
- **联合索引最左前缀**；**索引失效**常见：函数套列、隐式类型转换、`like '%x'`。
- **EXPLAIN** 判读：`type` 从 `const > eq_ref > ref > range > index > ALL`，`ALL` 就是全表扫描。
- **深分页**：`LIMIT 100000, 20` 会很慢，改用**基于主键/游标分页**。

## 三、两大必挂硬考点

### 3.1 N+1 查询（NestJS + TypeORM 最典型痛点）

> "高并发下最容易被 N+1 打崩。比如查文章列表，**对每篇文章再查一次作者**，100 条就是 101 次查询，DB 连接池瞬间被吃满。解法是**预加载/JOIN**：用 `relations` 或 QueryBuilder `leftJoinAndSelect` 一次查出关联；列表页用**覆盖索引**避免回表；必要时用 **DataLoader 批量**。我会用 EXPLAIN 验证执行计划，而不是凭感觉加索引。"

```ts
// 反例：N+1（循环里查库）
const posts = await postRepo.find();
for (const p of posts) p.author = await userRepo.findOne(p.authorId); // N 次查询

// 正例：预加载关联，1 次 JOIN
const posts = await postRepo.find({ relations: ['author'] });
// 或 QueryBuilder
const posts = await postRepo.createQueryBuilder('p')
  .leftJoinAndSelect('p.author', 'a')
  .getMany();
```

### 3.2 B+树（回答"为什么查询快"）

> "MySQL 高并发读能扛住，根基是 **InnoDB 聚簇索引（B+树）**：非叶子节点只存 key，**叶子节点存数据 + 双向链表**，树高 2~4 层，一次索引查询只 2~4 次磁盘 IO；叶子链表天然**支持范围查询和排序**。所以我不只说'加索引'，而是讲**联合索引最左前缀、覆盖索引避免回表、以及索引失效**（函数套列、隐式类型转换、`like '%x'`）。"

## 四、Redis 层：扛读的核心

### 4.1 缓存一致性（cache-aside + 延迟双删）

> "**读**走 Cache Aside：先查缓存，命中直接返回；miss 才回源 MySQL，再回填缓存。**写**走 DB，然后**删缓存**（而不是更缓存）。因为**并发下更新缓存会导致写覆盖**，删缓存更安全：下次读自然会拿最新值。"

**为什么不"先删缓存再更库"**：并发读可能在"删了缓存"后、"库还没更完"前把**旧值回填**进缓存 → 缓存里全是旧值。

**延迟双删**：
1. 先删缓存；
2. 更新 DB；
3. 延迟 N 毫秒**再删一次缓存**（兜掉第 1 步到第 3 步之间并发读回填的旧值）。

> **"延迟"怎么定**：取"业务读 + 回填缓存"耗时的上界（一般几百 ms~1s），确保并发读已完成。太短兜不住，太长增加窗口。

**要求强一致（不能读到旧值）怎么办**：
- **Canal 监听 binlog** 异步删/更缓存（最终一致，复杂但彻底）；
- 或**严格串行化**：核心写路径对缓存做短暂独占（如分布式锁），读完才释放；
- 或极端场景直接**绕过缓存只走 DB + 短 TTL**（把不一致窗口压到最小）。

### 4.2 缓存三兄弟

| 问题 | 现象 | 防御 |
|---|---|---|
| **穿透** | 查询**不存在**的 key，打穿到 DB | 参数校验 + **布隆过滤器** + **空值缓存**（短 TTL） |
| **击穿** | **热点 key 过期瞬间**，大量请求打 DB | **分布式锁** + **逻辑过期** + 预热 |
| **雪崩** | **大量 key 同时失效** | 过期时间**加随机值** + 多级缓存 + 熔断降级 |

### 4.3 分布式锁

> "用 **`SET key val NX EX`** 加锁：**唯一 value + Lua 脚本原子释放**（判断是自己的锁才删），配合**看门狗续期**防止业务没跑完锁就过期。多节点极端要求再考虑 **RedLock**，但要看业务是否真的需要那种级别的强一致，否则复杂度和风险不划算。"

```lua
-- 原子释放：校验 value 是自己的才删
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
else
  return 0
end
```

## 五、收尾话术（一整段背下来）

> "整体上，我把**高并发的读**交给 **Redis cache-aside**：查缓存命中直接返回，miss 才回源 MySQL 再回填，并做**缓存一致性**（写走 DB、删缓存 + 延迟双删，避免并发读到旧值），同时用**布隆过滤器/空值缓存防穿透、分布式锁/逻辑过期防热点击穿、过期时间加随机防雪崩**。**写路径**走 **NestJS 事务 + 幂等**（唯一约束 + 幂等键 + 乐观锁），避免重复下单和超卖。**MySQL 侧**靠 **B+树索引 + 覆盖索引 + 避免 N+1** 保证单条查询高效，用 EXPLAIN 验证，深分页用游标而不是大 offset。最后，**Redis 挂了要能降级**——熔断/限流保护核心写路径，而不是把流量全打到 DB。这样**读扛住、写一致、风险可控**。"

- 强一致（不能读到旧值）你怎么彻底解决？（binlog/Canal、串行化、绕过缓存短 TTL）
- 击穿和雪崩的区别？各自怎么防？

- N+1 你怎么**证明**自己解决了？（EXPLAIN / 开启 SQL 日志数查询次数）
- B+树为什么用**双向链表**、为什么不直接用 B 树/红黑树/哈希？
- 高 QPS 下连接池为什么不能开更大？
