# 组织信息管理平台 — 面试要点

> 项目时间：2023.12 - 2026.04 | 角色：项目 Owner
> 技术栈：Vue3 + TypeScript + Ant G6 + Taro + NutUI

---

## 一、项目一句话介绍

> "组织信息管理平台是理想汽车组织数字化的核心系统，面向全员提供实时个人信息查询，为管理者和 HRBP 提供团队分析工具。我主导了 PC 端（Vue3）和移动端（飞书小程序）双端建设，核心解决了 G6 可视化组织架构、人员/组织联动组件设计、细粒度权限管控三大难题。"

## 二、项目背景与双端架构

```
业务定位：
  - 全员：查看个人概览（组织架构、汇报关系、个人信息）
  - 管理者/HRBP：团队分析（人员结构、流失率、梯队建设）

技术挑战：
  1. 组织架构层级深（10+ 层），如何可视化展示？
  2. 人员详情和组织详情需要双向联动，如何设计组件？
  3. 不同角色看到的数据范围不同，如何统一管控？

双端架构：
  ┌─────────────────────────────────────┐
  │  PC 端 (Vue3 + 公司组件库，基于 Element Plus 二次开发) │
  │  - 完整功能：组织架构图、团队分析       │
  │  - 复杂交互：多维度筛选、下钻分析       │
  ├─────────────────────────────────────┤
  │      移动端 (Taro + NutUI)           │
  │  - 核心功能：个人概览、快速查询         │
  │  - 轻量交互：卡片式布局、滑动操作       │
  └─────────────────────────────────────┘
```

## 三、核心能力建设

### 3.1 G6 可视化组织架构

**问题：** 组织层级深（10+ 层）、节点多，全量加载会卡顿甚至崩溃，如何清晰展示？

**方案：** 基于 AntV G6 TreeGraph 开发，**初始只展示到二层结构，点击节点时才请求下层数据并追加到图中**（懒加载）

```typescript
// 核心思路：TreeGraph + compactBox 紧凑树布局 + 点击懒加载
const graph = new G6.TreeGraph({
  container: 'org-chart',
  layout: {
    type: 'compactBox',
    direction: 'TB',        // 从上到下
  },
  modes: {
    default: ['drag-canvas', 'zoom-canvas']  // 拖拽 + 缩放
  }
})

// 初始只加载两层：根节点 + 一级子部门
const initData = await fetchOrgTree({ depth: 2 })
graph.data(initData)
graph.render()

// 点击节点：已加载过就展开/收起，未加载就请求下层数据追加到图中
graph.on('node:click', async (evt) => {
  const item = evt.item
  const model = item.getModel()

  // 已加载过子节点：直接展开/收起
  if (model.children && model.children.length > 0) {
    graph.updateItem(item, { collapsed: !model.collapsed })
    graph.layout()
    return
  }

  // 未加载：请求下层数据，追加到图中
  const childData = await fetchSubDepartments(model.id)
  const parentData = graph.findDataById(model.id)
  parentData.children = childData   // 追加子节点数据
  graph.changeData()                // 刷新图
})

// 搜索定位：先请求目标员工的完整路径，逐级展开后聚焦高亮
async function locateEmployee(employeeId: string) {
  const path = await fetchEmployeePath(employeeId)  // 从根到目标的路径
  for (const nodeId of path) {
    const node = graph.findById(nodeId)
    if (node?.getModel().collapsed) {
      graph.updateItem(node, { collapsed: false })
    }
  }
  graph.layout()
  graph.focusItem(graph.findById(employeeId), true, { easing: 'easeCubic', duration: 500 })
}
```

**面试追问：组织架构层级很深，性能怎么优化？**

> "核心思路是**不全量渲染**：1) 数据懒加载，初始只展示二层结构，点击节点时才请求下层数据追加到图中，避免一次性渲染几千个节点导致卡顿甚至崩溃；2) 已加载的分支通过 collapsed 收起/展开，不用的分支收起来减少渲染节点数；3) 布局上选 compactBox 紧凑树布局，减少画布面积和边线交叉。G6 本身没有虚拟渲染这类能力，大数据量场景就是靠懒加载控制同时渲染的节点规模。"

### 3.2 联动式公共组件设计

**问题：** 人员详情和组织详情需要双向联动（人员→组织、组织→人员），如何设计？

**方案：** 抽成**人员详情组件**和**组织详情组件**两个独立组件，**互相递归调用**，配合导航栈支持无限下钻和返回

```
设计思路：

  ┌──────────────────────┐         ┌──────────────────────┐
  │    人员详情组件        │         │    组织详情组件        │
  │                      │         │                      │
  │  · 基本信息           │         │  · 组织信息           │
  │  · 所属组织 ──────────┼────────→│  · 上级组织           │
  │  · 下属人员 ──────────┼────┐    │  · 负责人 ────────────┼──┐
  └──────────────────────┘    │    │  · 下级组织           │  │
           ↑                  │    └──────────────────────┘  │
           │                  │              ↑               │
           └──────────────────┴──────────────┴───────────────┘
                     互相递归调用，可无限下钻

  导航栈：每次跳转把当前节点入栈，返回时出栈
  [人员A] → [组织B] → [人员C] → [组织D]   ← 支持下钻
  [人员A] ← [组织B] ← [人员C]             ← 支持逐级返回
```

**方案要点：**

1. **组件拆分**：人员详情和组织详情是两个独立组件，各自管理自己的数据获取和展示，职责清晰
2. **互相递归调用**：人员组件里点击"所属组织"渲染组织组件，组织组件里点击"负责人"渲染人员组件——两个组件互相引用，天然支持人员→组织→人员→组织的无限下钻链路
3. **导航栈管理**：每次跳转把当前节点（类型 + id）压入栈中，返回时出栈恢复上一个节点，支持逐级回退
4. **循环检测 + 深度限制**：跳转前检测目标是否已在栈中（避免 A→B→A→B 死循环），栈深超过阈值（如 20 层）提示用户

**面试追问：无限下钻会不会导致栈溢出或死循环？**

> "做了两层防护：1) 循环检测，如果导航目标已经在栈中，直接回退到已有位置而不是新增入栈，避免人员→组织→人员→组织死循环；2) 导航栈限制最大深度（比如 20 层），超过后提示用户。实际上因为组织数据本身就是树形结构，正常的下钻链路深度是有限的。"

**面试追问：为什么用组件互相递归调用，而不是一个组件内部 if-else？**

> "最开始是一个组件用 type 字段区分人员/组织两种模式，但模板里全是 v-if 分支，人员和组织的展示逻辑耦合在一起，改一个字段要动两处。拆成两个独立组件后，各自的内聚性更强——人员组件只管人员数据的展示和交互，组织组件只管组织的，互相通过 props 传递 id、通过事件通知跳转，符合单一职责。递归调用也让下钻链路天然成立，不需要额外的路由配置。"

### 3.3 细粒度权限管控

**问题：** 不同角色（普通员工 / 管理者 / HRBP）能看到的页面、能操作的按钮都不同，如何管控？

**方案：** 权限体系**依赖 Li People 的统一权限管理**，本平台不自建权限系统。职责划分是：**后端控制数据范围和操作是否允许（安全底线），前端控制页面展示和按钮显隐（体验层）**

```
职责划分：

  后端（安全底线）
    · 数据范围：接口返回前按角色过滤数据
      - 普通员工：只能查到自己的信息
      - 管理者：能查到本部门及下级部门的人员
      - HRBP：按管理的部门范围返回
    · 操作校验：每个写操作接口校验是否允许执行
      - 即使前端按钮被绕过，直接调接口也会被拦截

  前端（体验层）
    · 页面级：无权限的页面/Tab 直接不展示
    · 按钮级：无权限的操作按钮隐藏或禁用
      - 如"导出名单"只有 HRBP 可见
      - 如联系方式等敏感字段，无权限时展示"无权限查看"
```

**方案要点：**

1. **不自建权限系统**：权限数据来自 Li People 的统一权限管理，平台只消费权限结果，避免重复建设和权限口径不一致
2. **后端是底线**：数据范围在接口返回前就过滤掉，写操作接口逐个校验——前端权限只是为了体验，即使前端被绕过也不会越权
3. **前端做展示层**：拿到权限结果后，控制页面入口、Tab、操作按钮的显隐，以及敏感字段的脱敏展示

**面试追问：权限管控是前端做还是后端做？**

> "双层都做，职责不同：后端做数据权限，接口返回前过滤无权限数据、写操作逐个校验，这是安全底线；前端做展示权限，根据权限结果隐藏页面入口和操作按钮、敏感字段脱敏，这是体验层。前端权限是为了体验，后端权限是为了安全，缺一不可。我们平台的权限数据依赖 Li People 的统一权限管理，不自建权限系统，保证权限口径一致。"

## 四、移动端定制（Taro + NutUI）

**方案：** 移动端基于 NutUI 组件库，**通过统一修改样式变量完成主题定制**，对齐公司设计规范（品牌色、字号、间距、圆角等），不重写组件内部实现。

**方案要点：**

1. **样式变量定制**：NutUI 提供了一套 CSS 变量（如主题色、文字颜色、边框圆角等），通过覆盖这些变量统一调整全局样式，一次修改全局生效
2. **不重写组件**：组件的交互和结构直接用 NutUI 的，只做样式层定制——投入小、后续升级组件库成本低
3. **保证设计一致性**：PC 端（公司组件库）和移动端（NutUI 定制后）视觉风格统一，用户跨端使用无割裂感

## 五、高频面试题

### Q1: G6 组织架构图节点很多，怎么优化性能？

> "核心思路是不全量渲染：1) 数据懒加载，初始只展示二层结构，点击节点时才请求下层数据，用 findDataById 拿到数据、children 赋值后 changeData 刷新图，避免一次性渲染几千个节点卡顿甚至崩溃；2) 已加载分支通过 collapsed 收起/展开，控制同时渲染的节点规模；3) 布局选 compactBox 紧凑树布局，减少画布面积。G6 本身没有虚拟渲染能力，大数据量场景就是靠懒加载把节点规模控制在可接受范围。"

### Q2: 权限管控是前端做还是后端做？

> "双层都做，职责不同：后端做数据权限，接口返回前过滤无权限数据、写操作逐个校验，这是安全底线；前端做展示权限，根据权限结果控制页面入口和操作按钮显隐、敏感字段脱敏，这是体验层。前端权限是为了体验，后端权限是为了安全，缺一不可。我们平台的权限数据依赖 Li People 的统一权限管理，不自建权限系统，保证权限口径一致。"

### Q3: Taro 和原生小程序开发有什么区别？

> "三个区别：1) 开发范式：Taro 用 Vue/React 语法，原生用 WXML/WXSS，学习成本低；2) 跨端能力：Taro 一套代码编译到微信/支付宝/飞书等多端，原生只能单端；3) 性能：原生性能略好，但 Taro 3 的编译优化已经很小差距。我们选 Taro 是因为团队熟悉 Vue，且需要同时支持飞书和未来可能的微信端。"
