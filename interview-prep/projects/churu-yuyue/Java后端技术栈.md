# 出入预约 — Java 后端技术栈（面试速查）

> 定位：不是 Java 教程，而是你在出入预约项目里能讲清楚、能接住追问的后端知识地图。
> 技术栈：Spring Boot + Maven + MySQL + Redis + Kafka + Eureka + Feign + Apollo

---

## 一、30 秒面试版

> "出入预约后端是 Spring Boot + Maven 构建的 Java 微服务，MySQL 存预约单；人员信息统一通过 Feign 调公共服务获取，该服务内部用 Redis 做缓存。服务启动后注册到 Eureka，服务间调用走 Feign；员工离职等跨服务事件通过 Kafka 异步通知，消费后联动处理预约负责人数据；配置统一放 Apollo 配置中心，支持多环境隔离与动态刷新。"

## 二、组件定位总表

| 组件 | 一句话定位 | 在出入预约里的角色 | 面试高频追问 |
|------|-----------|-------------------|-------------|
| Spring Boot | Java 应用开发框架（Spring 生态 + 自动配置 + 内嵌服务器） | 后端主框架 | 为什么用 Spring Boot？和 Spring 什么关系？ |
| Maven | Java 构建工具：依赖管理 + 编译/测试/打包 | 管理依赖与模块版本 | 依赖版本冲突怎么解决？ |
| MySQL | 关系型数据库 | 存储预约单等业务数据 | 表怎么设计？索引、逻辑删除、分页？ |
| Redis | 内存数据库 / 分布式缓存 | 人员信息公共服务内部缓存，出入预约通过 Feign 间接受益 | 缓存一致性、穿透/击穿/雪崩 |
| Kafka | 分布式消息/事件流平台（生产/消费、异步解耦） | 消费员工离职事件，联动预约负责人数据 | 为什么用 Kafka 不用 HTTP？消费幂等？消息积压？ |
| Eureka | 服务注册与发现中心（不是微服务本身） | 服务实例注册、心跳续约、发现 | Eureka 挂了会怎样？CAP 怎么取舍？ |
| Feign | 声明式 HTTP 客户端：按服务名调用 | 获取车牌号等公共服务数据 | 和 Eureka 的分工？超时/重试怎么做？ |
| Apollo | 分布式配置中心：多环境、命名空间、动态刷新、权限审计 | 管理数据库连接、业务开关、密钥 | 密钥安全？动态刷新原理？为什么不用本地配置？ |

## 三、协作链路

### 3.1 服务启动

```
服务启动
   ├── 从 Apollo 拉取配置（数据库连接、业务开关、密钥）
   ├── 初始化数据源、消息消费者
   └── 注册到 Eureka，之后持续心跳续约
```

### 3.2 人员/车辆数据查询（Feign → 公共服务 → Redis）

```
出入预约服务需要人员信息（如预约负责人）
   │
   ▼
通过 Feign 按服务名调用人员信息公共服务（user-service）
   │
   ▼
（公共服务内部）先查 Redis 缓存
   ├── 命中 → 直接返回
   └── 未命中 → 回源数据并回填 Redis（带过期时间）
   │
   ▼
返回人员信息给出入预约服务
```

### 3.3 异步事件（Kafka）

```
人事/员工服务发布"员工离职"事件到 Kafka
   │
   ▼
出入预约服务作为消费者收到事件
   │
   ▼
联动处理预约负责人相关数据（失效或转交）
```

### 3.4 配置变更（Apollo）

```
在 Apollo 修改配置（如开关、连接串）
   │
   ▼
Apollo 推送/长轮询通知服务
   │
   ▼
服务动态刷新配置，无需重启
```

## 四、每个组件的面试追问与回答口径

### 4.1 Spring Boot

**Q: 为什么用 Spring Boot 而不是原生 Spring？**

> "Spring Boot 本质还是 Spring，但通过自动配置、起步依赖和内嵌服务器，把搭建成本降到最低——加依赖、写配置、启动即用，约定优于配置。它解决的痛点是原生 Spring 项目初始化繁琐、配置分散、部署依赖外部容器。"

### 4.2 Maven

**Q: 依赖版本冲突怎么解决？**

> "Maven 有依赖仲裁规则：路径近的优先、先声明的优先。排查用 `mvn dependency:tree`；需要强控版本时用 `dependencyManagement` 统一锁定，个别冲突用 `exclusions` 排除传递依赖。"

### 4.3 MySQL

**Q: 预约单数据怎么设计的？**

> "核心是预约单表，包含状态、车辆信息、负责人、进出时间等字段；统一带 create_time / update_time / is_deleted，删除走逻辑删除。状态和时间的筛选是高频查询，对应建索引；列表接口分页查询。"

### 4.4 Kafka

**Q: 为什么用 Kafka 而不是直接调接口？**

> "员工离职这类事件是跨服务的异步通知：发送方不关心谁在消费、对方是否在线，而且可能被多个系统消费。用 Kafka 做事件流，生产者和消费者完全解耦，还能削峰；Feign 是同步请求-响应，适合需要立即拿到结果的场景。"

**Q: 消费重复了怎么办？**

> "Kafka 是至少一次语义，消费端要自己做幂等：用业务唯一键去重，或先做状态校验再更新。比如同一个离职事件重复消费，第二次发现负责人已经处理过就直接跳过。"

**Q: 消息积压怎么处理？**

> "先保消费速度：临时扩容消费者或分区、定位慢消费原因（慢 SQL、下游依赖超时）；同时可以先把消息落库再异步处理，避免一直堆积。"

### 4.5 Eureka

**Q: Eureka 挂了对服务调用有影响吗？**

> "客户端本地会缓存服务实例列表，短时间仍能按缓存调用；Eureka 是 AP 型注册中心，优先保证可用性，牺牲强一致——注册信息短暂不一致可以接受，但服务不能因为注册中心故障而全挂。"

### 4.6 Feign

**Q: Feign 和 Eureka 的分工是什么？**

> "Eureka 管'服务在哪、有哪些实例'，Feign 管'按服务名发起 HTTP 请求'，两者配合完成服务发现和声明式调用。Feign 内部还会结合负载均衡在多个实例里选一个。"

**Q: Feign 调用失败怎么办？**

> "配置合理的超时时间；重试要谨慎，写接口必须幂等，否则重试可能重复下单；更稳的做法是加降级兜底，返回默认值或缓存。"

### 4.7 Apollo

**Q: 为什么不用本地配置文件？**

> "本地配置的问题：多环境要各维护一份、改配置要重新发版重启、没有权限和审计。Apollo 集中管理配置，支持多环境隔离、命名空间、动态刷新、灰度发布和操作审计，改配置不用重启服务。"

**Q: 密钥放 Apollo 安全吗？**

> "集中管理本身是优势，但密钥不能明文裸放：要配合加密存储、权限隔离（只有指定角色可读）和审计。面试时能主动讲出这三点，比只说'放 Apollo'更有深度。"

### 4.8 Redis

**Q: 人员信息查询为什么快？**

> "人员信息统一走公共服务查询，服务内部用 Redis 做缓存：查询频率高、数据变化不频繁，内存命中直接返回，减少源头压力。我们出入预约通过 Feign 调它，不需要自己维护缓存。"

**Q: 缓存一致性怎么保证？**

> "公共服务内部做缓存时，通用做法是 Cache-Aside：先更新源头数据，再删除缓存，避免并发写导致旧值覆盖，再配合过期时间做最终一致兜底。"

**Q: 穿透、击穿、雪崩分别是什么？**

> "穿透是查不存在的数据，缓存和源头都没有，请求直接打穿到源头——用空值缓存或布隆过滤器拦截；击穿是单个热点 key 过期瞬间大量请求打到源头——用互斥锁或逻辑过期保护；雪崩是一大批 key 同时过期或 Redis 不可用——过期时间加随机值、多级缓存/本地兜底。"

## 五、容易说错的术语（面试前校准）

- Spring Boot 是**框架**，不是"架构"
- Eureka 是**服务注册与发现中心**，不是"微服务"
- Kafka 是**消息/事件流平台**，不是数据库
- Apollo 是**分布式配置中心**，不是"配置表"
- Redis 是**内存数据库/缓存**，不是消息队列（虽然支持 Pub/Sub，但项目里跨服务事件走 Kafka）
- Feign 负责**声明式调用**，服务实例的发现靠 Eureka
