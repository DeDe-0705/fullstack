# H5 移动端场景题专题

> 2026 大厂 H5 / 跨端方向高频场景题：状态栏与刘海屏适配、软键盘弹起、100vh 视口陷阱、
> 1px 边框、点击延迟与点透、滚动穿透、WebView 通信等。
> 核心考察：不只是"知道有这个坑"，而是**坑的根因 + 方案选型 + 兼容性兜底**的工程化回答。
> 与跨端专题（Taro）、微前端专题联动，是 C 端岗位的必考模块。

---

## 〇、开场总览：移动端 H5 问题地图

移动端 H5 的坑几乎全部来自三个**和 PC 不同的环境特征**：

```
1. 视口不稳定 —— 浏览器工具栏伸缩、软键盘弹起都会改变可视区域
   → 100vh 陷阱、fixed 底栏被顶飞、键盘遮挡输入框

2. 屏幕物理形态多样 —— 刘海/Dynamic Island/Home 指示条/高 DPR
   → 安全区适配（safe-area-inset）、1px 边框变粗、图片模糊

3. 运行容器多样 —— Safari / Chrome / 微信 WebView / App 内 WebView
   → 状态栏高度无 Web 标准 API、JSBridge 通信、内核差异（iOS 强制 WebKit）
```

**60 秒总述模板（面试官问"移动端适配做过什么"时）：**

> "移动端适配我分成三层来做：**视口层**用 meta viewport + dvh/svh 新视口单位解决工具栏伸缩问题；**安全区层**用 viewport-fit=cover + env(safe-area-inset-*) 适配刘海屏，WebView 内通过 JSBridge 拿状态栏高度做沉浸式；**输入层**用 visualViewport API 监听软键盘，处理遮挡和 fixed 失效。再往上是 1px、滚动穿透、点击延迟这些经典坑的针对性方案。"

## 一、状态栏高度与刘海屏适配（开场高频）

> 面试官："移动端状态栏高度是多少？iPhone 刘海屏怎么做适配？"

### 1.1 先纠正一个认知：状态栏高度没有 Web 标准 API

- 常见机型参考值（**设计稿维度，勿硬编码**）：iPhone 无刘海 20pt、刘海屏 44pt、Dynamic Island 机型 54pt、59pt（16 Pro 系列）；Android 通常 24dp~48dp 不等
- **关键结论：Web 页面拿不到状态栏高度**——普通浏览器里网页从状态栏之下开始渲染；App WebView 沉浸式场景下，状态栏高度由**原生通过 JSBridge / URL 参数 / 注入全局变量**传给 H5

**面试话术：**
> "纯浏览器 H5 不需要关心状态栏——网页视口本来就在状态栏下面。需要关心的是两类场景：① App 内 WebView 做了沉浸式（内容延伸到状态栏底下），这时由客户端通过 JSBridge 把 `statusBarHeight` 传给 H5，H5 用它做顶部 padding；② 刘海屏浏览器全屏显示，用 CSS 安全区变量适配。"

### 1.2 刘海屏适配三件套（标准答案）

```html
<!-- ① viewport-fit=cover：让页面内容延伸到刘海/圆角区域（默认 contain 会留黑边） -->
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">
```

```css
/* ② env() 读取安全区内边距；③ constant() 兼容 iOS < 11.2 的老 Safari */
.footer-bar {
  /* 先写 constant 兜底老版本，后写 env 覆盖（CSS 层叠，后者生效） */
  padding-bottom: constant(safe-area-inset-bottom);
  padding-bottom: env(safe-area-inset-bottom);
}

.header {
  padding-top: constant(safe-area-inset-top);
  padding-top: env(safe-area-inset-top);
}

/* 进阶：安全区 + 自己的基础间距，用 max()/calc() 组合 */
.footer-bar {
  padding-bottom: calc(12px + env(safe-area-inset-bottom));
  /* 或：padding-bottom: max(12px, env(safe-area-inset-bottom)); */
}
```

**四个方向**：`safe-area-inset-top / right / bottom / left`。竖屏主要用 top/bottom；**横屏时左右两侧**也可能有刘海（left/right 生效）。

**常见误区纠正：**
- ❌ 用 `device-height - 媒体查询` 判断机型硬编码 44px → 机型碎片化，Dynamic Island 机型全错
- ❌ 只写 `env()` 不写 `constant()` → iOS 11.0~11.1 的老机器直接没有兜底间距
- ❌ 给整个 body 加安全区 padding → 正确做法是**背景延伸 + 内容避让**：页面背景色铺满全屏（含刘海区），只有内容/按钮避让安全区

### 1.3 追问：env() 拿不到值是什么情况？

- meta 标签没加 `viewport-fit=cover` → env() 全部返回 0（最常见原因）
- Android WebView 默认不支持 safe-area-inset（取决于容器是否设置 `DisplayCutout`），需要原生配合
- 兼容兜底：`padding-bottom: env(safe-area-inset-bottom, 20px)` —— env 支持第二参数作为 fallback，但注意这只能兜"不支持 env 的场景"，兜不了"返回 0 的场景"

## 二、100vh 陷阱与动态视口（2026 必考）

> 面试官："移动端设置 height: 100vh 为什么底部会被工具栏挡住？"

### 2.1 根因：vh 指的是"最大视口"，不是"当前可视区"

移动浏览器（Safari/Chrome）的地址栏 + 工具栏是**可伸缩**的：滚动时收起、反向滚动时展开。

- `100vh` = **工具栏收起后**的最大高度（large viewport）
- 页面首次加载时工具栏是展开的 → `100vh` 的元素底部被工具栏**遮住一截**
- `window.innerHeight` 会随工具栏伸缩**实时变化**，和 vh 行为不一致

### 2.2 标准解法：CSS 动态视口单位（2022 后主流浏览器全支持）

| 单位 | 含义 | 场景 |
|---|---|---|
| `100lvh` | 大视口高度（工具栏收起）≈ 旧版 100vh | 很少单独用 |
| `100svh` | 小视口高度（工具栏展开）| 首屏一屏式布局，保证工具栏展开时也不被遮 |
| `100dvh` | 动态视口高度（随工具栏伸缩实时变化）| 全屏容器、弹窗 |

```css
.fullscreen {
  height: 100vh;   /* 兜底老浏览器 */
  height: 100dvh;  /* 现代浏览器覆盖 */
}
```

**工程注意**：`dvh` 随滚动变化会触发**重排**，内部元素高度若依赖容器（如 flex 布局、百分比子元素）会在滚动时抖动。一屏式落地页用 `svh` 更稳（初始就不被遮，滚动时留白可接受）。

### 2.3 追问：不用 CSS 新单位怎么兼容老 WebView？

```js
// 经典方案：JS 计算真实视口高度，写入 CSS 变量
function setRealVh() {
  document.documentElement.style.setProperty('--real-vh', `${window.innerHeight * 0.01}px`);
}
setRealVh();
window.addEventListener('resize', setRealVh);
```

```css
.fullscreen {
  height: 100vh;
  height: calc(var(--real-vh, 1vh) * 100);
}
```

**一句话总结**：`100vh` 是静态大视口，移动端工具栏伸缩导致它大于实际可视高度；新方案用 `dvh/svh`，老环境用 `innerHeight` 写 CSS 变量兜底。

## 三、软键盘弹起（移动端场景题之王）

> 面试官："移动端输入框获取焦点软键盘弹起，页面会发生什么？底部的 fixed 按钮为什么飞了？"

### 3.1 先讲清 iOS 与 Android 的本质差异（分水岭考点）

| 维度 | Android（Chrome/WebView） | iOS（Safari/WebKit） |
|---|---|---|
| 键盘弹起对布局视口的影响 | **缩小**（默认 resize 模式）| **不缩小**，只是视觉上推（视觉视口偏移）|
| `window.resize` 事件 | ✅ 触发 | ❌ 不触发（历史版本）|
| `100vh` / 100% 高度 | 变小 | 不变 |
| `position: fixed` 底栏 | 通常贴在键盘上方 | **被推上去/漂移**，键盘收起后偶尔不回位（经典 bug）|
| `window.innerHeight` | 变小 | 不变（需用 visualViewport.height）|

> Android WebView 可通过原生设置 `softInputMode`：`adjustResize`（缩小布局）或 `adjustPan`（整体上推不缩小），H5 行为受容器配置影响。

### 3.2 现代标准方案：visualViewport API

```js
const vv = window.visualViewport;

vv.addEventListener('resize', () => {
  // 键盘高度 ≈ 布局视口高 - 可视视口高 - 偏移
  const keyboardHeight = window.innerHeight - vv.height - vv.offsetTop;

  if (keyboardHeight > 150) {
    // 阈值过滤：>150px 基本可判定为键盘弹起（排除工具栏伸缩干扰）
    document.body.classList.add('keyboard-open');
    // 把 fixed 底栏定位到可视区底部，贴住键盘上沿
    footer.style.transform = `translateY(${-keyboardHeight}px)`;
  } else {
    document.body.classList.remove('keyboard-open');
    footer.style.transform = '';
  }
});

vv.addEventListener('scroll', () => {
  // iOS 键盘弹起伴随视觉视口滚动，需要同步修正 fixed 元素位置
});
```

**兼容性**：iOS Safari 13+、Android Chrome 61+ 支持；不支持的降级方案是 `window.resize` + `document.activeElement` 判断（仅 Android 有效）。

### 3.3 三个经典子场景

**① 输入框被键盘遮挡**

```js
input.addEventListener('focus', () => {
  // 延迟等键盘弹起动画完成（iOS 约 300~500ms）
  setTimeout(() => {
    input.scrollIntoView({ behavior: 'smooth', block: 'center' });
  }, 300);
});
```

**② iOS 键盘收起后页面不回弹（fixed 元素悬空/底部留白）**

根因：键盘弹起时 WebKit 滚动了页面，收起后**没有自动滚回**。

```js
input.addEventListener('blur', () => {
  // 强制触发一次滚动复位
  window.scrollTo(0, 0);
  // 或温柔版：document.body.scrollIntoView();
});
```

**③ iOS focus 时页面自动放大**

根因：iOS 规定 **输入框字体小于 16px 时，focus 自动放大页面**（防止小字看不清）。

```css
input, textarea { font-size: 16px; } /* 治本 */
/* 或 meta 禁止缩放：maximum-scale=1, user-scalable=no（牺牲可访问性，慎用） */
```

### 3.4 追问：评论框场景怎么设计？（综合题）

> "输入框 + 发送按钮 fixed 在底部，键盘弹起时要贴在键盘上方，收起后回到底部安全区之上。"

```
方案要点（分层回答）：
1. 布局：底栏 position: fixed; bottom: 0; padding-bottom: env(safe-area-inset-bottom)
2. 键盘检测：visualViewport.resize + 阈值 150px 判定
3. 贴键盘：弹起时 transform: translateY(-keyboardHeight)，用 transform 而非改 bottom
   （transform 走合成层，不触发重排，跟手动画更流畅）
4. 收起复位：blur 时清 transform + scrollTo(0,0) 修 iOS 不回弹
5. 兜底：visualViewport 不存在时降级 window.resize（Android 有效）
```

## 四、1px 边框问题（经典中的经典）

> 面试官："为什么移动端写 border: 1px 看起来比设计稿粗？怎么解决？"

### 4.1 根因：CSS 像素 ≠ 物理像素

- `devicePixelRatio (DPR)` = 物理像素 / CSS 像素，Retina 屏 DPR = 2 或 3
- 设计稿的"1px"通常指 **1 物理像素**，但 CSS 的 `1px` 在 DPR=2 屏上渲染成 **2 物理像素** → 视觉上变粗

### 4.2 四种方案对比（选型题）

| 方案 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| **伪元素 + transform: scale(0.5)**（主流）| 伪元素画 1px，scaleY 压缩一半 | 通用、支持圆角 | 实现略繁琐 |
| **直接写 0.5px** | iOS 8+ / 现代浏览器支持小数像素 | 最简单 | Android 老机型把 0.5px 当 0 → 边框消失 |
| **viewport 缩放 initial-scale=1/dpr** | 整个页面按 DPR 缩小，1 CSS px = 1 物理像素 | 全局根治 | 影响所有 px 布局，需配合 rem；项目级侵入大 |
| **box-shadow 模拟** | `box-shadow: 0 1px 0 0 color` 替代下边框 | 简单 | 只适用于单边，颜色有渐变感 |

**主流实现（伪元素 + scale）：**

```css
.hairline-bottom {
  position: relative;
}
.hairline-bottom::after {
  content: '';
  position: absolute;
  left: 0; bottom: 0;
  width: 100%;
  height: 1px;
  background: #e5e5e5;
  transform: scaleY(0.5);   /* DPR=3 严格说应 0.333，0.5 是通用近似 */
  transform-origin: 0 100%;
}

/* 进阶：按 DPR 用媒体查询精确匹配 */
@media (-webkit-min-device-pixel-ratio: 3) {
  .hairline-bottom::after { transform: scaleY(0.3333); }
}
```

**工程实践**：组件库（Vant 等）内置 `[class*='van-hairline']` 方案；px 转 vw/rem 的 PostCSS 插件要配置 `minPixelValue` 或黑名单，**避免把 1px 也转换掉**。

## 五、点击 300ms 延迟与点透（必考历史题）

> 面试官："移动端点击为什么有 300ms 延迟？怎么解决？点透是什么？"

### 5.1 300ms 延迟的根因

早期 iPhone Safari 的**双击缩放（double-tap to zoom）**手势：浏览器收到第一次 tap 后要等 300ms，判断用户是否会再点一次（双击）才决定触发 click 还是缩放。

### 5.2 解决方案演进（按年代回答显层次）

```
1. 禁用缩放：meta viewport 加 user-scalable=no / maximum-scale=1
   → Chrome/Android 上 width=device-width 即可消除延迟（浏览器知道页面已适配移动端）
2. CSS 方案：touch-action: manipulation
   → 告诉浏览器"这里只允许平移和双指缩放，不要等双击"，现代浏览器推荐
3. JS 方案：FastClick 库（监听 touchend 主动触发 click）
   → 已过时：现代浏览器 + 正确 viewport 设置后不再需要
4. iOS 特例：Safari 在不可缩放页面下已自动去掉 300ms 延迟
```

### 5.3 点透（tap through）

**场景**：A 层（弹窗）绑 touchend 关闭，关闭瞬间 click 事件穿透到下层 B 的按钮上，误触发 B。

**根因**：`touchend` 早于 `click` 触发，A 在 touchend 里移除后，300ms 后派发的 click 落在同一坐标的下层元素上。

**方案**：① 统一只用 click（配 touch-action 消除延迟）；② touchend 里 `preventDefault()` 阻止后续 click 派发；③ 关闭动画延迟 300ms+ 再移除元素。

## 六、滚动穿透与 fixed 失效（中高频）

### 6.1 滚动穿透

**场景**：弹层滚动到底/顶部后继续滚，背景页面跟着滚。

**方案对比**：

| 方案 | 做法 | 问题 |
|---|---|---|
| body 加 `overflow: hidden`（最常用）| 弹层打开时锁 body | iOS 上 body 仍可被橡皮筋滚动；**body 回到顶部**，需先存 scrollTop、关闭后恢复 |
| 弹层 touchmove preventDefault | 阻止默认滚动 | 弹层内部的可滚区域也被禁了，需判断元素 |
| `overscroll-behavior: contain` | CSS 单行，阻止滚动链 | iOS Safari 16+ 才支持好 |
| 组合方案（生产级）| body fixed 定位 + top: -scrollTop + overscroll-behavior | 实现复杂但最稳 |

```js
// 锁 body 的正确姿势（保 scrollTop）
function lockBody() {
  const top = window.scrollY;
  document.body.style.cssText = `position: fixed; top: -${top}px; width: 100%;`;
  return () => {
    document.body.style.cssText = '';
    window.scrollTo(0, top); // 关闭时恢复原滚动位置
  };
}
```

### 6.2 fixed 失效/抖动

- 祖先元素有 `transform / filter / perspective / will-change` → fixed 的**包含块变成该祖先**而非视口（这是 CSS 规范，不是 bug！面试高频）
- iOS 橡皮筋滚动时 fixed 元素跟随抖动 → 用 `position: sticky` 重构，或接受现状
- 软键盘场景的 fixed 问题 → 见第三章

## 七、WebView 内 H5 专属问题（跨端岗位必考）

### 7.1 iOS 全系列 WebKit

Apple 强制：iOS 上**所有浏览器**（Chrome/微信/App WebView）都是 **WebKit 内核**（WKWebView）。所以 iOS 的 H5 兼容性 = Safari 兼容性，与 Android Chrome 行为差异都要单独测。

### 7.2 JSBridge 通信模型（问"H5 怎么拿状态栏高度"的延伸）

```
H5 → Native：
  - scheme 拦截：iframe.src = 'myapp://getStatusBarHeight'，原生拦截 URL 解析参数
  - API 注入：WKWebView 的 window.webkit.messageHandlers.xxx.postMessage()

Native → H5：
  - evaluateJavaScript / evaluateJavascript 执行 JS 回调
  - 注入全局对象：window.JSBridge.statusBarHeight

标准封装模式：
  - callNative(method, params) → 生成 callbackId，存 callback 映射表
  - Native 执行完回调 window.__bridgeCallback(callbackId, result)
  - Promise 化包装，支持并发调用
```

**追问要点**：callback 映射防泄漏（调用后删除）、Android 4.4 以下 addJavascriptInterface 安全漏洞、双向通信的序列化成本。

### 7.3 微信 WebView 专属坑

- 页面缓存激进：入口 HTML 必须 `Cache-Control: no-cache` 或 URL 带版本参数
- 音频/视频自动播放受限 → 需用户手势触发，或用 WeixinJSBridgeReady
- 字体放大：Android 微信会强制放大字体 → `-webkit-text-size-adjust: 100% !important`（注意别用 none 破坏可访问性）
- 返回不刷新：pageshow 事件 + `event.persisted` 检测 bfcache 恢复

## 八、其他高频散点（速查清单）

| 问题 | 一句话答案 |
|---|---|
| 图片模糊 | 按 DPR 提供 2x/3x 图（srcset），或容器宽 × DPR 选图 |
| canvas 模糊 | canvas.width = cssWidth × DPR，再 ctx.scale(dpr, dpr) |
| 1px 边框变粗 | 见第四章（伪元素 scale）|
| 橡皮筋背景露白 | body 背景延伸到 -100vh 或 fixed 背景层 |
| 长按保存图片/弹出菜单 | `-webkit-touch-callout: none` + img `pointer-events: none` |
| 禁止文本选中 | `user-select: none`（输入框除外）|
| 点击高亮灰框 | `-webkit-tap-highlight-color: transparent` |
| 输入框 font-size < 16px 页面放大 | 输入框字号 ≥16px（见 3.3③）|
| 视频内联播放 | `playsinline webkit-playsinline`（否则 iOS 强制全屏）|
| 数字变蓝色可点 | `format-detection: telephone=no`（meta）|
| iOS 日期 new Date('2026-09-06') NaN | Safari 不支持 `-` 分隔，用 `/` 或手动解析 |
| position: fixed 失效 | 祖先有 transform/filter（见 6.2，CSS 规范）|
| 横屏适配 | orientationchange / matchMedia('(orientation: landscape)') + 左右 safe-area |

## 九、面试话术模板

### 60 秒速答："移动端 H5 有哪些坑？怎么解决？"

> "我按环境差异分三类来讲。**视口类**：100vh 在移动端会被伸缩的工具栏遮挡，现代方案是 dvh/svh 视口单位，老环境用 innerHeight 写 CSS 变量兜底；**安全区类**：刘海屏用 viewport-fit=cover 配 env(safe-area-inset-*)，constant() 兜底老 iOS，原则是背景延伸、内容避让，App 内沉浸式场景状态栏高度走 JSBridge 拿；**交互类**：软键盘 iOS/Android 行为不同——Android resize 布局视口、iOS 只偏移视觉视口，所以要用 visualViewport API 做键盘检测和 fixed 贴底，iOS 还有键盘收起不回弹和 16px 字号放大两个坑要处理。剩下 1px 边框、滚动穿透、点透这些经典问题都有成熟方案：伪元素 scale、锁 body 保 scrollTop、统一 click + touch-action。"

### 选型论证句式（应对"为什么不用 xxx 方案"）

> "这个场景我不选 A 方案，因为它在 iOS 上 xxx（具体失效点）；B 方案虽然代码多一点，但覆盖到 xxx 边界情况，生产环境更稳。"
