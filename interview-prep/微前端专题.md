## 一、微前端核心概念

### 1.1 为什么需要微前端？

```
业务痛点：
  - 巨石应用：多个团队维护一个代码库，构建慢、发布互相阻塞
  - 技术栈锁定：想升级框架或引入新技术，牵一发动全身
  - 团队协作：不同业务团队需要独立开发、独立部署、独立迭代

微前端的价值：
  ✅ 独立开发 — 各团队拥有自己的代码库
  ✅ 独立部署 — 子应用发布不影响其他应用
  ✅ 技术栈无关 — 不同子应用可以用不同框架
  ✅ 增量升级 — 逐步替换老系统，不用全部重写
  ✅ 团队自治 — 降低多团队协作耦合度
```

### 1.2 微前端解决的核心问题

```
1. 路由分发 → 根据 URL 将用户导向对应的子应用
2. 应用隔离 → JS 隔离（全局变量不冲突）、CSS 隔离（样式不污染）
3. 应用通信 → 主应用与子应用、子应用之间安全通信
4. 资源共享 → 公共依赖抽离（Vue/React/工具库），避免重复加载
5. 统一鉴权 → 登录态在主应用统一管理，子应用透明接入
```

## 二、主流方案对比

| 方案 | 核心原理 | JS 隔离 | CSS 隔离 | 接入成本 | 适合场景 |
|------|---------|---------|---------|---------|---------|
| **qiankun** | single-spa 封装 + 沙箱 | Proxy/快照（同一 window） | Scope 处理，不完美 | 中高（需暴露生命周期） | 存量系统改造、社区成熟 |
| **无界 (wujie)** | iframe 物理隔离 + WebComponent 渲染 | iframe 独立 window（物理级） | iframe 独立 document（天然） | 低（几乎零改造） | 新老混合、强隔离需求 |
| **Micro-app** | WebComponent 渲染 + iframe/Proxy 沙箱 | Proxy 沙箱（严格模式用 iframe） | 样式作用域 / ShadowDOM | 低（组件式接入） | 轻量接入、类似无界 |
| **Module Federation** | Webpack 5 运行时远程加载模块 | 无 | 无 | 中（需统一构建体系） | 同技术栈、模块/依赖共享 |

### 2.1 qiankun（阿里）

```
原理：基于 single-spa，通过 JS 沙箱（快照/Proxy）实现隔离

优点：
  - 生态成熟，文档完善
  - 社区活跃，踩坑经验多

缺点：
  - JS 沙箱不是真隔离（同一 window 下操作）
  - 快照沙箱性能开销（遍历 window 属性做快照）
  - CSS 隔离不完美（需要手动加 scope）
  - 对子应用侵入性强（需要暴露 bootstrap/mount/unmount 生命周期）
```

### 2.2 无界 wujie（腾讯）

#### 2.2.1 核心架构：Shadow Component + iframe

无界的底层不是直接把子应用塞进 iframe 裸跑，而是包了一层 WebComponent（shadow-component）：

```
主应用 DOM
  └── <wujie-app>                    ← WebComponent（shadow-component）
        └── #shadow-root (open)      ← Shadow DOM
              └── iframe              ← 真正的子应用运行环境
                    └── 子应用的 html/css/js
```

**为什么要多这层 WebComponent，不直接用 iframe？**

纯 iframe 有三个致命痛点，WebComponent 刚好补上：

| iframe 痛点 | WebComponent（shadow-component）怎么解决 |
|-------------|------------------------------------------|
| 弹窗/遮罩只覆盖 iframe 内部区域 | 通过 Shadow DOM 的事件冒泡穿透 + DOM 劫持，把弹窗挂载到主应用 body 上 |
| 子应用路由和主应用不同步 | 在 Shadow DOM 层劫持 `pushState`/`replaceState`，同步到主应用 URL |
| 子应用 DOM 和主应用不在同一棵树 | Shadow DOM 提供统一挂载点，无界在这层做 DOM 代理 |

**分工总结：**

```
无界 = WebComponent 容器 + iframe 沙箱

WebComponent（shadow-component）负责"打通"：
  1. 提供隔离的 DOM 挂载点（Shadow DOM）
  2. 处理事件冒泡/穿透（子应用事件能冒到主应用）
  3. 弹窗挂载代理（劫持 document.body.appendChild 等）
  4. 路由同步代理（劫持 history.pushState）

iframe 负责"隔离"：
  1. JS 物理隔离（独立 window，互不污染）
  2. CSS 物理隔离（独立 document，样式天然隔离）

一句话：iframe 管"隔离"，WebComponent 管"打通"，两者互补缺一不可。
```

#### 2.2.2 优缺点

```
原理：iframe + WebComponent 双保险

iframe 承载子应用：
  - 天然的 JS 隔离（独立 window）
  - 天然的 CSS 隔离（独立 document）

WebComponent 解决 iframe 的痛点：
  - iframe 的弹窗/遮罩只覆盖 iframe 区域 → 通过 proxy 劫持挂载到主应用
  - iframe 路由不同步 → 劫持 iframe 内 pushState/replaceState 同步到主应用
  - DOM 不在同一棵树 → 提供 DOM 劫持方案

优点：
  - 接入成本极低（子应用几乎不用改）
  - 完美 JS/CSS 隔离（iframe 天然隔离）
  - 支持多框架混用
  - 预加载 + 保活机制
```

#### 2.2.3 面试话术

> "无界的底层是 iframe + WebComponent 双保险。iframe 提供 JS 和 CSS 的物理隔离，WebComponent 的 Shadow DOM 解决 iframe 的三大工程问题——弹窗挂载、路由同步、DOM 代理。Shadow DOM 提供统一的挂载点和事件穿透能力，iframe 提供独立的运行时环境。简单说：iframe 管隔离，WebComponent 管打通。"

### 2.3 micro-app（京东）

```
原理：基于 WebComponent 思想渲染子应用，配合 JS 沙箱做隔离

渲染机制：
  - 子应用以自定义元素 <micro-app name="xxx" url="xxx"> 方式挂载，
    组件化接入，使用体验接近 iframe，但比 iframe 更可控
  - CSS 默认通过样式作用域隔离（给子应用选择器加前缀），
    也可开启 ShadowDOM 模式

JS 隔离：
  - 默认 Proxy 沙箱（子应用 JS 仍运行在宿主 window，性能较好）
  - 严格隔离模式（strictIsolation）使用 iframe 沙箱，实现物理隔离

优点：
  - 接入简单，侵入性低，主应用改造成本极小
  - 支持多框架混用（React/Vue/Angular/原生）
  - 预加载、缓存机制完善，社区活跃（京东开源）

缺点：
  - 默认 Proxy 沙箱不是物理隔离，全局对象冲突时仍需注意
  - 严格隔离模式有性能损耗
  - 与无界相比，弹窗挂载、路由同步等 iframe 工程问题需要自行处理
```

### 2.4 Module Federation（Webpack 5 原生 + enhanced 增强）

```
原理：运行时动态加载远程模块

// 主应用 webpack.config.js
new ModuleFederationPlugin({
  name: 'host',
  remotes: {
    app1: 'app1@http://localhost:3001/remoteEntry.js',
  }
})

// 使用
const RemoteApp = React.lazy(() => import('app1/App'))

优点：
  - Webpack 原生支持，无额外依赖
  - 共享依赖，减少重复加载
  - 真正的运行时集成
  - 2025+ 增强版 @module-federation/enhanced：支持 Rspack、
    TypeScript 完善、API 现代化，生态在快速补位

缺点：
  - 无 JS/CSS 隔离（同一 window 下）
  - 仅限同技术栈（都用 Webpack 5）
  - 版本管理复杂

定位提醒：
  - 它解决的是「模块共享」而不是「应用隔离」：
    适合跨应用复用组件、共享依赖（singleton），不适合承载异构存量系统
  - 面试中把 MF 和容器框架放在同一赛道比较，会显得理解不深
```

### 2.5 选型决策框架（面试核心）

面试官要的不是"哪个最好"，而是**你如何权衡**。固定使用 5 个决策问题：

```
1. 拆分粒度：拆的是「应用」→ qiankun/wujie/micro-app；
              拆的是「模块/依赖」→ Module Federation
2. 存量 vs 绿地：存量异构系统（Vue2/3、React 混着，老代码难动）
               → wujie/micro-app 低侵入；可统一改造 → qiankun/MF 都行
3. 隔离强度：历史包袱重、样式/全局变量冲突多 → iframe 物理隔离（wujie）；
              团队规范可控 → Proxy 沙箱够用
4. 构建基建：全团队统一 Webpack 5/Rspack 且要共享依赖 → MF 优势极大；
              技术栈不统一 → 只能选容器框架
5. 维护成本：小团队快速交付 → 接入成本优先（wujie/micro-app）；
              长期演进 → 生态活跃度、二次开发能力优先
```

**结合 Li People 项目的选型推理（面试话术）：**

> 背景：4 个业务域（人事/组织/薪酬/文化），各团队迭代节奏不同，之前耦合在
> 一个代码库，发布互相阻塞；且是存量系统、技术栈异构。
>
> - 排除 qiankun：JS 沙箱非物理隔离（同一 window），快照沙箱有遍历性能
>   开销，且要求子应用暴露生命周期，对存量系统侵入性大
> - 排除 micro-app：定位和无界相近，但无界的「保活 + 预加载 + DOM 劫持」
>   方案更贴合存量多栈场景（弹窗挂载、路由同步这些纯 iframe 的坑，
>   无界已工程化解决）
> - 排除 Module Federation：它是模块共享方案而非隔离方案，且存量项目
>   技术栈不统一、不是 Webpack 5，方向不对
> - 选择无界：iframe 天然 JS/CSS 物理隔离，子应用几乎零改造；
>   路由劫持同步 URL、刷新可恢复；Props 下发 token + Bus 通信解耦
>
> 结果：各模块独立开发部署，发布不再互相阻塞。

│  ├──────────┤ ├──────────┤          │
│  │ 全局状态   │ │ 通信总线   │          │
│  ├──────────┤ ├──────────┤          │

│  ┌──────┐ ┌──────┐ ┌──────┐        │
│  │人事模块│ │组织模块│ │薪酬模块│ ...     │

### 3.2 核心能力实现

**鉴权方案：**

```js
// 主应用注入 props 给子应用
<WujieVue
  name="hr-module"
  url="//cdn.example.com/hr-module/1.0.0/index.html"
  :props="{ token: userStore.token, userInfo: userStore.info }"
/>

// 子应用接收
if (window.__POWERED_BY_WUJIE__) {
  // 从 $wujie.props 获取主应用注入的数据
  const { token, userInfo } = window.$wujie.props
}
```

**通信方案：**

```js
// Props 注入：单向数据流，适合配置下发、鉴权信息
// Bus 事件：适合跨应用事件通知
import WujieVue from 'wujie-vue2'

// 主应用监听子应用事件
bus.$on('hr-module:user-selected', (user) => { ... })

// 子应用发送事件
window.$wujie.bus.$emit('user-selected', { id: 123 })
```

**路由同步：**

```js
// 无界自动劫持子应用的路由变化
// 子应用 pushState → 主应用 URL 同步更新
// 用户刷新 → 主应用根据 URL 激活对应子应用

// 菜单权限：主应用根据角色过滤菜单，子应用只显示自己有权限的路由
```

**性能优化：**

```js
// 1. 预加载：用户还没点击就提前加载子应用
import { preloadApp } from 'wujie'
preloadApp({ name: 'hr-module', url: '//cdn.xxx/hr-module/index.html' })

// 2. 保活：切换时不销毁，保留状态
<WujieVue name="hr-module" :alive="true" />

// 3. CDN + 强缓存
// 子应用静态资源通过 CDN 分发，文件名带 hash，永久缓存
```

**部署规范：**

```
1. 子应用独立构建，产物上传 CDN
2. 通过版本号隔离（1.0.0 / 1.1.0 / latest）
3. 主应用通过配置中心管理子应用版本号
4. 灰度发布：先在少量用户上验证新版本
```

### 3.3 面试话术模板

> "在理想汽车，我主导了 Li People 门户的微前端架构落地，选型无界 wujie。核心解决了四个问题：
>
> **鉴权**：主应用通过 Props 向子应用注入 token 和用户信息，做到子应用无感接入登录态。同时通过编码控制菜单权限，不同角色看到不同模块入口。
>
> **路由**：利用无界的路由劫持能力，子应用内 pushState 自动同步到主应用 URL，刷新时主应用根据 URL 加载对应子应用。
>
> **通信**：Props 注入用于配置下发，Bus 事件总线用于跨应用业务事件。比如员工详情组件选中某人，通知其他模块联动展示。
>
> **性能**：通过 CDN 分发 + contenthash 强缓存最大化缓存命中，公共依赖抽离复用减少资源冗余。预加载高频访问的子应用，保活机制保留子应用状态。"

## 四、高频面试题速答

### Q: 微前端有哪些方案？你怎么选的？

qiankun、无界、Micro-app、Module Federation 四种。先说分类：前三个是应用级容器框架，MF 是模块级共享机制。再按 5 个决策问题走一遍（拆分粒度 → 存量/绿地 → 隔离强度 → 构建基建 → 维护成本）。我的项目是存量异构系统，隔离要求高、子应用难以改造，所以选无界：iframe 天然隔离比 JS 沙箱更安全可靠，接入成本极低（子应用几乎不用改代码），预加载和保活机制对 B 端多模块场景很友好。Module Federation 隔离性不够且不匹配我们的构建体系，qiankun 接入成本高且沙箱有性能问题。

### Q: 无界和 micro-app 怎么选？

两者都是低侵入方案，关键区别在隔离机制：
- 无界默认 iframe 承载子应用 JS，物理隔离更彻底；micro-app 默认 Proxy 沙箱（同一 window），严格模式才用 iframe
- 无界内置解决 iframe 三大工程问题（弹窗挂载、路由同步、DOM 树），micro-app 相对轻量、需要自己处理这些
- 子应用之间需要强隔离、存量系统包袱重 → 无界；项目相对干净、想要更轻的接入 → micro-app

### Q: Module Federation 适不适合做微前端？

要看目标。MF 擅长「模块级共享」：跨应用复用组件、共享依赖（singleton）、统一升级公共库。但它没有 JS/CSS 隔离，也不支持异构技术栈，所以如果目标是「多个团队独立开发部署的隔离应用」，MF 不是正确答案；如果目标是「同栈团队之间的模块复用和依赖治理」，MF 是首选。

### Q: 微前端中 CSS 隔离怎么做？

- 无界/iframe：天然隔离（独立 document）
- qiankun：Shadow DOM 或 CSS Scope（给选择器加前缀）
- CSS Modules：构建时给类名加 hash
- BEM 命名 + 父容器限定：人力约束，不可靠

### Q: 子应用之间怎么通信？

短路径用 Props 注入（配置、鉴权），松耦合用 Bus 事件（业务事件），持久化用主应用的全局 Store 或 localStorage。原则：尽可能单向数据流，避免子应用之间直接耦合。

### Q: 微前端的性能怎么保证？

1. CDN 分发 + 强缓存
2. 公共依赖外置（externals），避免重复加载
3. 预加载高频子应用
4. 保活机制避免反复初始化
5. 子应用独立构建，按需加载路由
