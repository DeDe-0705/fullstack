 # 浏览器原理

 ## 一、浏览器渲染流程

 ```
 HTML ---> DOM Tree
                        \
                          --> Render Tree --> Layout --> Paint --> Composite
                        /
 CSS  ---> CSSOM Tree
 ```

 **关键步骤：**

 | 步骤 | 做什么 | 产物 |
 |------|--------|------|
 | 解析 HTML | 词法分析 -> Token -> DOM 树 | DOM Tree |
 | 解析 CSS | 解析样式表，构建 CSSOM | CSSOM Tree |
 | 构建 Render Tree | DOM + CSSOM 合并，只包含可见节点 | Render Tree |
 | 布局 Layout | 计算每个节点的几何位置和尺寸 | 盒模型信息 |
 | 绘制 Paint | 将布局结果绘制到图层上 | 图层位图 |
 | 合成 Composite | GPU 将多个图层合成为最终画面 | 屏幕像素 |

 **CSS 阻塞渲染？** CSS 是渲染阻塞资源。浏览器必须等 CSSOM 构建完才能渲染，否则出现 FOUC（无样式内容闪烁）。

 **CSS 也阻塞 JS 执行？** 是的。因为 JS 可以通过 `getComputedStyle()` 读取元素的最终样式，如果前面的 CSS 还没加载完，JS 读到的样式就是错的。浏览器为了保证 JS 读到正确的 CSSOM，必须等 `<script>` 之前的所有 `<link>` 加载完并构建 CSSOM 后，才执行 JS。所以 CSS 不仅阻塞渲染，**也间接阻塞 JS 执行**。

 **JS 阻塞解析 — async vs defer 精确对比：**

| | 普通 `<script>` | `<script async>` | `<script defer>` |
|------|-----------|-------|-------|
| 下载过程 | 阻塞 DOM 解析 | 并行下载，不阻塞 | 并行下载，不阻塞 |
| 执行时机 | 下载完立即执行，阻塞 DOM 解析 | 下载完立即执行，暂停 DOM 解析 | 等 DOM 解析完，在 `DOMContentLoaded` 前按序执行 |
| 执行顺序 | 文档顺序 | 谁先下载完谁先执行（乱序） | 文档顺序 |
| 适用场景 | 必须立即执行的关键脚本 | 独立脚本（统计、广告） | 依赖 DOM 的脚本 |

```
async 的"执行时阻塞"细节：
  如果 async 脚本下载完的时候 DOM 还没解析完 → 暂停 DOM 解析 → 执行脚本 → 继续解析
  如果 async 脚本下载完的时候 DOM 已经解析完了 → 直接执行，不影响任何东西
```

 ## 二、回流（Reflow）与重绘（Repaint）

 | 操作 | 触发条件 | 代价 |
 |------|----------|------|
 | 回流 Reflow | 修改几何属性（尺寸、位置、布局） | 高：重新布局 + 重绘 + 可能合成 |
 | 重绘 Repaint | 修改外观属性（颜色、背景）但不影响布局 | 中：跳过 Layout |
 | 合成 Composite | 仅修改 transform / opacity | 低：跳过 Layout 和 Paint，直接 GPU 合成 |

 **触发回流：**
- 修改 width/height/margin/padding/display/top/left
- 读取 offsetHeight/getBoundingClientRect/getComputedStyle（强制同步布局）
- 增删 DOM 节点、改变字体

 **减少回流策略：**
```js
// 差：读写交替 -> 多次回流
for (let i = 0; i < items.length; i++) {
  items[i].style.width = container.offsetWidth + "px";
}

// 好：先读后写
const width = container.offsetWidth;
for (let i = 0; i < items.length; i++) {
  items[i].style.width = width + "px";
}

// 更好：DocumentFragment 批量插入
// 最好：用 CSS class 代替逐条 style；动画用 transform+opacity
```

 **优化速记：** 避免逐条改style / 批量DOM / 读写分离 / transform+opacity 做动画 / will-change / requestAnimationFrame

### 2.1 强制同步布局（Forced Synchronous Layout）— 卡顿杀手

这是"回流"最隐蔽的触发形式。浏览器正常会把多个读写操作缓冲起来批量处理，但如果你在写之后立刻读一个布局属性，浏览器被迫在中间插一次同步 Layout：

```js
// ❌ 卡顿根源：滚动中读写交替，每帧触发一次完整的 Layout
window.addEventListener('scroll', () => {
  const height = header.offsetHeight        // 读 → 立刻触发同步Layout
  header.style.top = scrollY + height + 'px'// 写
  // 每一帧：Layout → Paint → Composite，60fps 根本达不到
})

// ✅ 改法：把读操作抽到 rAF，写放到下一个 rAF
let pendingHeight = 0
window.addEventListener('scroll', () => {
  requestAnimationFrame(() => {
    pendingHeight = header.offsetHeight     // 读：在当前帧
    requestAnimationFrame(() => {
      header.style.top = scrollY + pendingHeight + 'px' // 写：在下一帧
    })
  })
})
```

**会触发强制同步布局的操作（读写交替时要警惕）：**
```
读操作：offsetTop/Left/Width/Height、scrollTop/Left/Width/Height
       clientTop/Left/Width/Height、getComputedStyle()
       getBoundingClientRect()、innerText
```

 ## 三、图层分层与 GPU 合成

 ### 3.1 渲染管线中的"分层"步骤

完整管线：
```
DOM + CSSOM → Render Tree → 分层(Layer) → Layout → Paint → Composite
                                  ↑
                            浏览器根据 CSS 属性决定哪些元素提升为独立图层
```

独立图层的 transform/opacity 变化只需要 Composite（合成线程处理），完全跳过 Layout 和 Paint。

 ### 3.2 浏览器自动分层的条件（完整版）

**HTML 元素（自动分层）：**

```html
<video>      <!-- ✅ 视频元素 -->
<canvas>     <!-- ✅ 画布 -->
<iframe>     <!-- ✅ iframe -->
```

**CSS 属性（触发分层）：**

```css
/* 1. transform 3D（立即分层） */
transform: translateZ(0);
transform: translate3d(0, 0, 0);
transform: rotateX(45deg);
perspective: 1000px;

/* 2. will-change（提前分层） */
will-change: transform;
will-change: opacity;
will-change: filter;

/* 3. position（固定/粘性定位） */
position: fixed;
position: sticky;

/* 4. filter / backdrop-filter */
filter: blur(5px);
backdrop-filter: blur(10px);

/* 5. mix-blend-mode（混合模式） */
mix-blend-mode: multiply;

/* 6. clip-path / mask */
clip-path: circle(50%);
mask: url(#mask);

/* 7. overflow: scroll（某些浏览器） */
overflow: scroll;  /* Chrome 会分层，Safari 不一定 */
```

**CSS 动画/过渡（临时分层）：**

```css
/* transition 期间临时分层 */
.element {
  transition: transform 0.3s, opacity 0.3s;
}

/* animation 期间临时分层 */
.element {
  animation: slide 1s;
}
@keyframes slide {
  from { transform: translateX(0); }
  to { transform: translateX(100px); }
}
```

**⚠️ 常见误区（面试易错）：**

```css
/* ❌ position: absolute 不会分层 */
.box {
  position: absolute;  /* 只是脱离文档流，不改变渲染流程 */
  top: 0;
  left: 0;
}

/* ❌ z-index 不会分层 */
.box {
  z-index: 999;  /* 只影响层叠顺序，不创建合成层 */
}

/* ❌ 单独的 transform 2D 不会分层 */
.box {
  transform: translateX(100px);  /* 静态变换，不分层 */
}

/* ✅ 正确的分层方式 */
.box {
  transform: translateZ(0);  /* transform 3D 立即分层 */
  /* 或 */
  will-change: transform;    /* 提前分层 */
  /* 或 */
  position: fixed;           /* 固定定位自动分层 */
}
```

**为什么 absolute 和 z-index 不分层？**
- `position: absolute` 只是改变定位上下文，元素仍在正常渲染流程中，改变 `top/left` 还是会触发 Layout
- `z-index` 只影响元素在层叠上下文（Stacking Context）中的顺序，不改变渲染管线
- 想要分层，必须配合 `transform 3D`、`filter`、`will-change` 等

**验证分层的方法（Chrome DevTools）：**

```
方法 1：Layers 面板
  DevTools → More tools → Layers
  显示图层树、每个图层的大小、内存占用、分层原因

方法 2：Layer borders
  DevTools → More tools → Rendering → 勾选 "Layer borders"
  分层的元素会显示橙色边框

方法 3：Performance 面板
  录制动画 → 查看 Main 线程的帧详情
  如果有独立图层，"Composite Layers" 步骤会很快
```

### 3.3 手动触发 GPU 加速

```css
/* 最常用的两种方式 */
.element {
  transform: translateZ(0);        /* 强制提升为独立图层 */
  will-change: transform, opacity; /* 提前告知浏览器"我要做动画了" */
}
```

### 3.4 ⚠️ will-change 的大坑——不能滥用

每个独立图层都在 GPU 显存中占据一块空间。1000 个项目每项都 `will-change` → 1000 个图层 → 显存爆炸。

```css
/* ❌ 错误：所有项都提升 */
.list-item { will-change: transform; }

/* ✅ 正确：动画开始时加，结束后移除 */
.list-item:hover { will-change: transform; }
/* 或在 JS 中：start → el.style.willChange = 'transform'; end → el.style.willChange = 'auto' */
```

 ### 3.5 三种更新路径代价对比

| 触发属性 | 经过阶段 | 代价 |
|----------|---------|------|
| width/height/left/top | Layout → Paint → Composite | ⚠️⚠️⚠️ 高 |
| color/background | Paint → Composite | ⚠️⚠️ 中 |
| transform / opacity | Composite 仅 | ⚠️ 低（合成线程处理，不阻塞主线程） |

> 面试话术："做动画优先用 transform 和 opacity。这两个属性只触发 Composite 阶段，由合成线程独立处理，JS 主线程卡住了也不会掉帧。"

 ## 四、Event Loop 事件循环

 **核心规则：**

 > JS 单线程，通过调用栈 + 任务队列 + 微任务队列协同。
 > 执行顺序：同步代码 --> 清空所有微任务 --> 取一个宏任务 --> 清空微任务 --> 循环...

| 类型 | 包含 |
|------|------|
| 微任务 Microtask | Promise.then/catch/finally、MutationObserver、queueMicrotask、await 之后 |
| 宏任务 Macrotask | setTimeout、setInterval、I/O、UI渲染、MessageChannel |

**帧调度相关 API：**

| API | 执行时机 | 用途 | 注意 |
|---|---|---|---|
| requestAnimationFrame | 重绘前，与刷新率同步（60Hz 约 16.7ms） | 动画、DOM 读写分离 | 后台标签页暂停；高刷屏频率更高 |
| requestIdleCallback | 一帧渲染完成后的空闲期 | 低优先级大任务切片、埋点、日志 | Safari 不支持；浏览器忙时可能不执行；用 `deadline.timeRemaining()` 判断剩余时间，`timeout` 兜底 |

```
宏任务 → 微任务 → rAF → Style/Layout/Paint → rIC（有空闲才执行） → 下一个宏任务
```

### 4.1 requestIdleCallback（rIC）详解

**核心作用：** 等浏览器忙完渲染、交互后，在空闲期执行低优先级任务，避免阻塞主线程。

```js
requestIdleCallback((deadline) => {
  // deadline.timeRemaining() — 当前帧剩余空闲时间(ms)，>0 才继续执行
  // deadline.didTimeout — 是否因超时被强制执行
  while (deadline.timeRemaining() > 0 && tasks.length) {
    tasks.shift()()
  }
  if (tasks.length) requestIdleCallback(arguments.callee) // 没做完下次继续
}, { timeout: 2000 }) // 兜底：最多等 2s，超时强制执行
```

**三大场景：** ① 大任务切片防阻塞渲染 ② 埋点 / 日志上报 ③ 预加载 / 预计算。

**rAF vs rIC（面试必考）：**

| | requestAnimationFrame | requestIdleCallback |
|---|---|---|
| 执行时机 | 下一帧重绘前 | 浏览器空闲时 |
| 执行保证 | 每帧都会执行（60fps） | 不保证（忙时跳过） |
| 页面隐藏 | 自动暂停 | 不执行 |
| 适用场景 | 动画、视觉更新 | 日志、预加载、大任务切片 |
| 兼容性 | 所有现代浏览器 | Safari 不支持（需 polyfill） |

**高频追问：**

1. **rIC 里能操作 DOM 吗？** 不推荐——rIC 在渲染**后**执行，此时改 DOM 会影响下一帧；正确分工是「计算放 rIC、DOM 更新放 rAF」。
2. **vs setTimeout(fn, 0)？** setTimeout 到点必执行、可能阻塞渲染；rIC 只在空闲执行、不阻塞，但浏览器一直忙时可能一直不执行（需 `timeout` 兜底）。
3. **Safari 不支持怎么办？** 用 setTimeout 模拟 polyfill，`timeRemaining` 固定给约 50ms 预算：

```js
if (!window.requestIdleCallback) {
  window.requestIdleCallback = function (callback) {
    const start = Date.now()
    return setTimeout(() => callback({
      timeRemaining: () => Math.max(0, 50 - (Date.now() - start)),
      didTimeout: false,
    }), 1)
  }
  window.cancelIdleCallback = clearTimeout
}
```

 **必考题：**
```js
console.log(1);
setTimeout(() => console.log(2), 0);
Promise.resolve().then(() => {
  console.log(3);
  setTimeout(() => console.log(4), 0);
});
new Promise((resolve) => {
  console.log(5);
  resolve();
}).then(() => console.log(6));
console.log(7);

// 输出：1 5 7 3 6 2 4
```

 **Node.js 差异：** Event Loop 分6个阶段(timers->pending->idle->poll->check->close)，每个阶段间清空微任务。process.nextTick 优先级高于 Promise.then。

 ## 五、垃圾回收（GC）

 **V8 策略：**

 | 回收器 | 区域 | 算法 |
 |--------|------|------|
 | Scavenge | 新生代(1-8MB) | Cheney 复制算法，频繁快速 |
 | Mark-Sweep/Compact | 老生代 | 标记-清除+标记-整理，全停顿 |

 **常见内存泄漏：** 全局变量、遗忘的定时器/回调、闭包引用大对象、DOM 引用未解除、事件监听未清理。

 ## 六、进程与线程

 ### 6.1 Chrome 多进程架构

```
Chrome 启动后的进程：

浏览器主进程（Browser Process） — 1 个
  → 负责 UI（地址栏、书签）、子进程管理、存储

GPU 进程 — 1 个（所有标签页共享）
  → 所有 GPU 相关操作通过它中转

网络进程（Network Process）— 1 个（所有标签页共享）
  → 所有网络请求通过它

渲染进程（Renderer Process）— 每个站点 1 个
  → 同站（same-site）标签页共享渲染进程
  → 负责 HTML/CSS/JS 的解析和渲染

插件进程 — 按需创建
扩展进程 — 按需创建
```

 ### 6.2 渲染进程内的线程

```
一个渲染进程包含：

主线程（Main Thread）：
  ├── JS 引擎线程     ← 执行 JavaScript
  ├── GUI 渲染线程    ← 解析 HTML/CSS、Layout、Paint
  ├── 事件触发线程    ← 管理事件循环
  ├── 定时器线程      ← setTimeout/setInterval
  └── 异步 HTTP 线程  ← fetch/XHR 异步请求

合成线程（Compositor Thread）：
  └── 独立于主线程，负责图层合成（Composite 阶段）
     这就是为什么 transform 动画即使 JS 卡了也不会掉帧

IO 线程、Worker 线程...
```

 ### 6.3 JS 引擎线程 与 GUI 渲染线程互斥

JS 执行过长则页面卡顿。用 Web Worker 做密集计算（不能操作DOM，靠 postMessage 通信）。

 ## 七、速查表

 | 问题 | 答案要点 |
|------|----------|
| 输入URL后发生什么？ | DNS -> TCP -> TLS -> HTTP -> 服务器 -> 解析HTML -> DOM/CSSOM -> Render Tree -> Layout -> Paint -> Composite |
| display:none vs visibility:hidden vs opacity:0 | none:不在RenderTree触发回流；hidden:占位不回流不可点击；opacity:0:占位可点击仅合成 |
| requestAnimationFrame vs setTimeout | rAF与刷新率同步后台暂停；setTimeout不保证精确 |
| async vs defer | async下载完立即执行(乱序)；defer等DOM解析完按序执行 |
| rAF vs rIC | rAF重绘前执行、每帧保证执行、做动画；rIC空闲时执行、不保证执行、做低优先级任务 |
| rIC回调里操作DOM？ | 不推荐。计算放rIC，DOM更新放rAF |
| 浏览器自动分层的条件 | video/canvas/iframe、transform 3D、will-change、position:fixed/sticky、filter、动画期间的transform/opacity |
| position:absolute会分层吗？ | 不会。只有fixed/sticky会分层，absolute只是脱离文档流 |
| z-index会触发分层吗？ | 不会。z-index只影响层叠顺序，不改变渲染管线 |
