# 性能优化体系

> 性能优化是高级前端的核心能力之一。面试官想听到的不是零散的优化技巧，而是"分层体系"——从网络到渲染，从构建到运行时，你需要有一条清晰的链路。


## 二、网络层优化

### 2.1 HTTP 缓存策略

```
强缓存（浏览器不发请求）：
  Cache-Control: max-age=31536000 → 一年内直接用缓存
  Expires → 绝对时间（已过时，用 Cache-Control 替代）

协商缓存（发请求验证）：
  ETag / If-None-Match → 基于文件内容 hash
  Last-Modified / If-Modified-Since → 基于时间

最佳实践：
  静态资源（JS/CSS/图片）→ 强缓存 + 文件名 hash
  HTML → 协商缓存或不缓存（保证能拉最新资源）
```

### 2.2 CDN 优化

```
CDN 加速原理：
  1. DNS 解析 → 返回离用户最近的 CDN 边缘节点 IP
  2. 边缘节点有缓存 → 直接返回
  3. 边缘节点无缓存 → 回源站拉取 → 缓存

你的项目场景（理想汽车 Li People）：
  "子应用部署到 CDN，通过版本号管理，实现静态资源就近加载。
   主应用 HTML 部署在源站，通过协商缓存保证实时性；
   子应用的 JS/CSS 使用强缓存 + contenthash，最大化缓存命中率。"
```

### 2.3 资源加载优化

```
1. 压缩
   - Gzip / Brotli（Brotli 比 Gzip 小 ~20%）
   - 图片压缩：WebP/AVIF 格式
   - 字体子集化（只包含用到的字符）

2. 预加载
   <link rel="preload" href="critical.css" as="style">    // 高优先级提前加载
   <link rel="prefetch" href="next-page.js" as="script">  // 低优先级空闲加载
   <link rel="dns-prefetch" href="//api.example.com">     // 提前 DNS 解析

3. 资源内联
   关键 CSS 内联到 HTML（减少一次网络请求）
   小图标用 SVG inline 或 Base64（避免额外请求）

4. 图片策略
   <img loading="lazy"> 原生懒加载
   <picture> + srcset 响应式图片
```

## 三、构建层优化

### 3.1 代码分割 (Code Splitting)

```js
// 路由级分割（最常用的）

// 组件级分割（大组件单独拆包）
```

```bash

# Webpack
```

- 公共 vendor 大小

## 四、渲染层优化

### 4.1 回流 (Reflow) 与 重绘 (Repaint)

```
回流（Layout）：几何属性变化 → 重新计算布局 → 开销大
重绘（Paint）：非几何属性变化 → 重新绘制 → 开销较小

触发回流的操作：
  - 修改 width/height/padding/margin/border
  - 修改 display/position/float
  - 修改 font-size/font-family
  - 读取 offsetWidth/scrollTop 等（强制同步布局）
  - 增删 DOM 节点
  - 浏览器窗口 resize

只触发重绘：
  - color, background-color, visibility, box-shadow
  - outline, border-radius（不影响布局的属性）
```

**减少回流的技巧：**

```js
// ❌ 差：多次读写，强制同步布局
el.style.width = el.offsetWidth + 10 + 'px'  // 读 → 强制回流
el.style.height = el.offsetHeight + 10 + 'px' // 读 → 再次强制回流

// ✅ 好：批量读，批量写
const width = el.offsetWidth    // 读
const height = el.offsetHeight  // 读
el.style.width = width + 10 + 'px'   // 写
el.style.height = height + 10 + 'px'  // 写

// ✅ 更好：用 class 一次性修改
el.classList.add('enlarged')
```

### 4.2 虚拟列表

```
场景：渲染 10000 条数据的列表

原理：
  只渲染可视区域 + 缓冲区的 DOM 节点
  滚动时动态计算 startIndex/endIndex，替换节点内容

关键计算：
  visibleCount = Math.ceil(containerHeight / itemHeight)
  startIndex = Math.floor(scrollTop / itemHeight)
  endIndex = startIndex + visibleCount + bufferCount

  offsetY = startIndex * itemHeight  // 用 padding-top 占位
  totalHeight = total * itemHeight   // 容器总高度
```

### 4.3 GPU 加速

```css
/* 使用 transform 和 opacity 触发 GPU 加速 */
.element {
  transform: translateZ(0);        /* 强制开启 GPU 合成层 */
  will-change: transform, opacity; /* 提前告知浏览器 */
}

/* ⚠️ 不要滥用 GPU 加速：每个合成层都消耗显存 */
```

## 五、运行时优化

### 5.1 防抖 (Debounce) 与 节流 (Throttle)

```js
// 防抖：连续触发只执行最后一次
// 场景：搜索输入、窗口 resize
function debounce(fn, delay) {
  let timer = null
  return function(...args) {
    clearTimeout(timer)
    timer = setTimeout(() => fn.apply(this, args), delay)
  }
}

// 节流：固定时间间隔执行一次
// 场景：滚动事件、鼠标移动
function throttle(fn, delay) {
  let lastTime = 0
  return function(...args) {
    const now = Date.now()
    if (now - lastTime >= delay) {
      fn.apply(this, args)
      lastTime = now
    }
  }
}
```

### 5.2 Web Worker

```js
// 主线程
const worker = new Worker('/heavy-worker.js')
worker.postMessage({ data: largeArray })
worker.onmessage = (e) => {
  console.log('计算结果:', e.data)
}

// heavy-worker.js
self.onmessage = (e) => {
  const result = heavyComputation(e.data.data)
  self.postMessage(result)
}
```

### 5.3 内存管理

```
常见内存泄漏场景：
1. 全局变量（意外声明）
2. 未清除的定时器/事件监听
3. 闭包引用（尤其是 DOM 引用）
4. detached DOM（已移除但 JS 仍引用）
5. WebSocket/EventSource 未关闭

排查工具：
  - Chrome DevTools Memory 面板
  - Performance Monitor
```

## 六、Core Web Vitals（2026 标准）

> ⚠️ 2024 年 3 月起 **INP 已正式取代 FID** 成为核心交互指标。回答时还在提 FID 会被直接判定知识陈旧。

```
LCP (Largest Contentful Paint) ≤ 2.5s
  最大内容绘制，衡量感知加载速度
  位于渲染管线 Paint 阶段
  优化：缩短关键渲染路径、SSR、图片优化、CDN、字体加载策略

INP (Interaction to Next Paint) ≤ 200ms   ← 2024.3 取代 FID
  交互到下一次绘制，衡量页面全生命周期响应性（取所有交互的 P75 最差值）
  横跨整个渲染管线（JS 处理 → Style → Layout → Paint）
  优化：拆分长任务（>50ms）、Web Worker、延迟非关键 JS、
        减少事件处理器中的主线程工作、yield to main thread

CLS (Cumulative Layout Shift) ≤ 0.1
  累积布局偏移，衡量视觉稳定性
  位于渲染管线 Layout 阶段
  优化：图片/iframe 预留尺寸（aspect-ratio / width+height 属性）、
        不在已有内容上方插入内容、字体加载防 FOIT/FOUT
```

**FID vs INP 的区别（追问点）：**
- FID 只测"第一次输入"的延迟，INP 测页面整个生命周期内所有交互的响应（取 P75 最差）
- FID 只测到"事件开始处理"的延迟，INP 测到"下一帧真正绘制完成"
- INP 更能暴露长任务、重渲染等真实交互卡顿

### 6.1 指标与渲染管线的对应关系（高频追问）

```
Parse → Style → Layout → Paint → Composite
                      ↑        ↑
                     CLS      LCP
              （布局偏移在这里发生）（最大内容绘制在这里完成）

INP 横跨全链路：事件处理 JS → Style → Layout → Paint
优化越靠后的阶段，收益越大：
  transform/opacity → 只触发 Composite（最便宜）
  color/background  → 触发 Paint + Composite
  width/height/top  → 触发 Layout + Paint + Composite（最贵）
```

## 八、高频面试题速答

### Q: 从输入 URL 到页面展示，有哪些性能优化点？

DNS 预解析 → TCP 连接复用（HTTP/2 多路复用）→ CDN 就近加速 → HTTP 强缓存 → 关键资源内联 → 非关键资源懒加载 → 代码分割 → 虚拟列表 → 图片 WebP + 懒加载。

### Q: 回流和重绘的区别？怎么减少回流？

回流要重新计算布局（几何属性变化），重绘只需重新上色（外观属性变化）。减少回流：批量修改 DOM（DocumentFragment）、用 class 替代逐个 style 修改、position: absolute/fixed 脱离文档流、使用 transform 代替 left/top 动画。

### Q: 虚拟列表的实现原理？

只渲染可视区域的 DOM 节点。根据 scrollTop 计算 startIndex，根据容器高度计算 visibleCount，动态截取数据切片渲染。用 padding-top 做上方占位，保持滚动条高度正确。一般会加 buffer（上下各多渲染几个节点）保证滚动流畅。

### Q: 首屏加载优化有哪些手段？

- 构建层：代码分割、Tree Shaking、Gzip/Brotli
- 网络层：CDN、强缓存、HTTP/2、资源预加载
- 渲染层：关键 CSS 内联、非关键资源延迟、骨架屏
- 代码层：路由懒加载、组件异步加载、第三方库按需引入
- 服务端：SSR/SSG 预渲染首屏 HTML

## 九、首屏慢分层定位框架（2026 大厂标准回答）

> 8/14 模拟面试暴露的核心盲区。面试官给"LCP = 4.2s 的页面"这类场景题时，要的不是零散的优化清单，而是**分层定位 + 数据驱动的工程化闭环**。

### 9.1 标准回答框架：定指标 → 找瓶颈 → 出方案 → 拿数据

```
第一步：定指标
  "首先明确问题指标——LCP 4.2s，超出 2.5s 标准 68%。
   用 web-vitals 库做 RUM 采集，确认是普遍问题还是个别环境。"

第二步：找瓶颈（四层定位，逐层排除）
  网络层 → 资源层 → 渲染层 → 交互层

第三步：出方案（针对定位到的层，给出具体优化）

第四步：拿数据（优化后用同一套指标验证，量化收益）
```

### 9.2 四层定位详解

```
┌──────────────────────────────────────────────────────────────┐
│ 第一层：网络层                                                │
│   排查项：                                                    │
│     TTFB 是否过长（>600ms 说明服务端/网络慢）                  │
│     CDN 是否命中（看 response header 的 X-Cache / Age）        │
│     HTTP 缓存是否生效（强缓存命中 = 200 from disk cache）      │
│     压缩是否开启（Content-Encoding: gzip/br）                  │
│     HTTP/2 或 HTTP/3 是否启用（多路复用减少连接开销）           │
│   工具：Chrome DevTools Network 面板 Timing 标签页             │
│         WebPageTest 看瀑布图                                   │
│                                                               │
│ 第二层：资源层                                                │
│   排查项：                                                    │
│     首屏 JS 体积（>200KB gzipped 需要代码分割）                │
│     是否有未做 Tree Shaking 的大型依赖                          │
│     路由是否懒加载                                             │
│     第三方库是否按需引入                                        │
│     图片是否过大/格式过旧（WebP/AVIF 替代 PNG/JPEG）           │
│   工具：vite-bundle-visualizer / webpack-bundle-analyzer       │
│                                                               │
│ 第三层：渲染层                                                │
│   排查项：                                                    │
│     render-blocking CSS（外部 CSS 阻塞首次渲染）               │
│     render-blocking JS（同步 script 阻塞解析）                 │
│     LCP 元素是什么（图片？文本块？视频封面？）                  │
│     图片是否懒加载了 LCP 元素（常见错误：给首屏大图加 lazy）   │
│     长任务（Long Task >50ms）阻塞主线程                        │
│     字体加载阻塞（FOIT）                                       │
│   工具：Lighthouse / Chrome Performance 面板                   │
│         Performance Insights 直接标出 LCP 元素和长任务          │
│                                                               │
│ 第四层：交互层                                                │
│   排查项：                                                    │
│     INP 是否超标（>200ms）                                     │
│     事件处理器中是否有同步重计算                                 │
│     是否有大量 hydration 阻塞（SSR 场景）                      │
│   工具：web-vitals 库 RUM 采集 / Performance 面板 Main 线程    │
└──────────────────────────────────────────────────────────────┘
```

### 9.3 完整场景话术（LCP = 4.2s 排查）

> 面试官："给你一个 LCP = 4.2 秒的页面，你的系统性排查和优化方案是什么？"

```
"我会按四步走：

第一步定指标：LCP 4.2s，超标准 68%。先用 web-vitals 做 RUM 采集，
确认是所有用户都慢还是特定地区/设备慢——这决定了是资源问题还是网络问题。

第二步找瓶颈：用 Lighthouse 和 WebPageTest 分层定位。
- 先看 Network 瀑布图：TTFB 多少？如果 TTFB 就占了 2s，
  问题在服务端或 CDN，前端优化空间不大，需要推动后端加缓存或边缘渲染。
- 再看资源：LCP 元素是什么？假设是一张 2MB 的 hero 图，
  没压缩没 CDN 没设置 fetchpriority="high"。
- 再看渲染：有没有 render-blocking 的 CSS/JS？
  外部 CSS 文件多大？同步 script 在 head 里吗？

第三步出方案：假设定位到 LCP 元素是大图 + render-blocking CSS：
- 图片：压缩到 WebP、加 fetchpriority="high"、设置 width/height 防 CLS
- CSS：关键 CSS 内联到 HTML，非关键 CSS 用 media="print" 延迟加载
- JS：全部加 defer，第三方脚本用 async
- 网络：开启 Brotli 压缩、确认 CDN 命中

第四步拿数据：优化后重新跑 Lighthouse + 持续 RUM 监控，
LCP 从 4.2s 降到 1.8s，提升 57%。"

追问应对：
Q: "Lighthouse 分数高就代表用户体验好吗？"
A: "不一定。Lighthouse 是实验室数据（Lab Data），受本地设备和网络影响。
   真实用户在低端 Android、弱网、海外节点的表现可能差很多。
   所以要结合 RUM（Real User Monitoring）数据做判断，
   用 web-vitals 库采集真实用户的 LCP/INP/CLS。"

Q: "LCP 元素是什么？图片多大？什么格式？是网络慢还是渲染慢？"
A: 这就是分层定位的价值——先看 Network 瀑布图的 TTFB 和资源下载时间，
   判断是网络问题；再看 Performance 面板的 Main 线程，
   看 Layout/Paint 耗时，判断是渲染问题。
```

### 9.4 首屏渲染完整链路（补齐 8/14 缺失细节）

```
URL 输入
  → DNS 解析（可用 dns-prefetch / preconnect 预热）
  → TCP 三次握手（HTTP/1.1 每个域名 6 连接；HTTP/2 单连接多路复用）
  → TLS 握手（TLS 1.3 只需 1-RTT，比 1.2 快一倍；0-RTT 会话复用）
  → HTTP 请求（先走强缓存判断 → 协商缓存判断 → 真正发请求）
  → 服务器响应（TTFB 是第一个字节到达时间，>600ms 就需要关注）
  → HTML 解析（增量解析，边下载边解析）
    → 遇到 CSS：阻塞渲染（CSSOM 构建不完，页面不绘制）
      ⚠️ CSS 不阻塞 HTML 解析，但阻塞渲染
    → 遇到同步 JS：阻塞解析（必须下载+执行完才继续解析 HTML）
      async：下载不阻塞解析，下载完立即执行（执行时阻塞解析）
      defer：下载不阻塞解析，HTML 解析完后按顺序执行
    → DOM 树 + CSSOM 树 → Render 树（只包含可见节点，不含 display:none）
  → Layout（计算每个节点的几何信息，回流）
  → Paint（分层绘制，栅格化）
  → Composite（GPU 合成，最终上屏）
    → FCP（首次内容绘制）→ LCP（最大内容绘制）
```

**关键纠正（8/14 暴露的错误）：**
- ❌ "async 会阻塞渲染"——不准确
- ✅ 普通 script（无 async/defer）阻塞 HTML **解析**；async 下载不阻塞、执行时阻塞解析；defer 下载和执行都不阻塞解析（解析完后执行）
- CSS 阻塞**渲染**但不阻塞**解析**（浏览器可以继续解析 HTML 构建 DOM，但不会绘制任何内容直到 CSSOM 就绪）

## 十、场景题：100+ 图表大屏 / 驾驶舱优化

> 面试原题："前端页面要渲染 100 多个图表给大老板看，你会怎么设计？从前端层面，包括构建、开发、运行时。"
>
> 这类题没有标准答案，考的是「先定目标再分层拆解」的工程思维。抓住核心：**大屏是给老板看全局的，不是给用户做深度交互的**，所以策略一定是「可见性驱动 + 按需渲染 + 可降级」。

### 10.1 开场定调（先亮思路，再进细节）

```
我会先明确场景假设：大屏/驾驶舱通常一屏展示全局，老板要的是"看得全、刷新快、稳定不崩"，
而不是 100 个图表同时做高交互。

所以核心策略是三条：
1. 可见性驱动：只渲染可视区内的图表，滚出视口就回收。
2. 按需渲染：图表进入视口才初始化/订阅数据，而不是页面加载时一次性全建。
3. 可降级：静态快照、骨架屏、单图失败兜底，保证"哪怕某张图挂了，整页不崩"。

然后从「渲染层、数据层、构建层、稳定性」四层逐一说方案。
```

### 10.2 渲染层（最关键，先讲）

- **IntersectionObserver 懒加载 + 回收**：每个图表容器用 `IntersectionObserver` 观察，进入视口才初始化实例；滚出视口后 `dispose()` 并释放 DOM/事件/定时器。实测可把初始化数量减少 70% 左右，回收后可明显降低 DOM 节点数。
- **限制同时实例数**：给一个最大并发实例数（比如 20 个），超出的排队或降级为静态快照，避免一次性实例化把主线程打爆。
- **静态快照 / 静态图降级**：对非重点图表，先用服务端出的静态图或上次渲染的 canvas 快照占位，用户 hover 或需要时再"升级"成交互式图表。
- **Canvas 优先于 SVG**：大屏上百个图表，SVG 的节点数和 DOM 开销会拖慢渲染，Canvas 更适合海量数据与频繁刷新（ECharts 默认渲染器是 Canvas）。

### 10.3 数据层

- **图表进入视口才订阅实时数据**：避免 100 个图表同时轮询/连 WebSocket，造成请求洪峰和前端重复计算。
- **服务端聚合 + Web Worker 重计算**：把统计、聚合下推到后端，前端只拿"可直接渲染"的数据；若前端还需做聚合/转换，放到 Web Worker 里做，避免阻塞主线程。
- **分批 / 按需加载**：首屏只加载可视区图表数据，其余懒加载；实时数据用"批量接口 + 增量推送"代替 100 个独立请求。

### 10.4 构建 / 工程化

- **ECharts 按需引入 + tree shaking**：用 `echarts/core`，只注册用到的图表类型、组件、渲染器，避免全量引入（全量 ECharts 体积很大）。
- **图表库单独 vendor chunk + 长效缓存/CDN**：把 ECharts 等图表依赖拆成独立 chunk，版本号做内容 hash，命中强缓存；核心依赖走 CDN。
- **抽象 ChartCard + schema 配置渲染**：不要手写 100 个图表组件，而是抽象一个 `ChartCard`，用 JSON/Schema 描述"图表类型、数据源、刷新频率、交互方式"，统一渲染、统一管理生命周期。这样新增图表只改配置，不写重复代码。
- **首屏只加载可视区 + 骨架屏**：降低 FCP/LCP，避免首屏 JS 执行时间过长。

### 10.5 稳定性 / 监控

- **统一 `dispose()` 防内存泄漏**：图表实例、定时器、事件监听在回收时必须释放，否则 100 个图表长时间运行内存持续上涨。
- **resize 防抖**：大屏通常嵌在投屏/浏览器中，窗口变化触发重算，用防抖 + `requestAnimationFrame` 合并重绘，避免频繁 resize 抖动。
- **单图错误降级兜底**：单张图表渲染失败（数据异常、渲染异常）只降级这一张，不引发整页崩溃。
- **60fps 性能监控**：用 `PerformanceObserver` 监听长任务（Long Task），统计图表初始化/刷新耗时，设置性能预算（例如首屏图表初始化 < 3s）。

### 10.6 项目关联话术（把经验挂上去）

### 10.7 高频追问与应对

**Q: 为什么用 IntersectionObserver 而不是监听 scroll 计算？**
A: `IntersectionObserver` 是浏览器原生异步回调，不阻塞主线程，且能自动处理容器滚动、嵌套滚动；手写 scroll 监听需要额外防抖节流，还容易漏算。

**Q: 100 个图表都在可视区（比如分多列大屏）怎么办？**
A: 那就不适用"滚动懒加载"，改用"限制同时实例数 + 分批初始化"：先渲染重点指标，其余用静态快照/骨架屏占位，再按帧或按时间片分批实例化，避免长任务阻塞。

**Q: dispose 之后再次进入视口怎么办？**
A: 需要缓存"图表配置 + 最近一次数据"，重新进入视口时用配置快速重建实例；或者直接用 canvas 快照占位，交互时再重建，二者结合在"性能"与"体验"间做取舍。
