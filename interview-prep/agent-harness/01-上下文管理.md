# Agent Harness 工程 · 模块一：上下文管理

> Agent Harness（智能体运行时外壳）六大模块系列之一。背景：基于 NestJS 打造企业内部 HR Agent（查个人信息、请年假、申请资产等业务操作）。本文记录模块一「上下文管理」的讨论结论（2026-09-08，基于联网检索的 2025–2026 最新实践）。

| 模块 | 在 HR Agent 里解决的问题 | 状态 |
|---|---|---|
| 上下文管理 | 给 LLM 喂什么：身份、制度文档、对话历史，怎么不爆窗口 | ✅ 本文 |
| 工具系统 | `查询个人信息`/`提交年假申请`/`申请资产` 怎么定义、注册、鉴权 | 待讨论 |
| 执行编排 | 多步任务（查余额→确认→提交→审批）怎么流转、走分支 | 待讨论 |

## 一、上下文到底由哪些部分组成

### 1.1 权威基线：Philipp Schmid（Google DeepMind）七要素

2025–2026 被引用最多的标准归纳（Anthropic 官文与各厂实践沿用）：

| # | 要素 | HR Agent 里的对应物 |
|---|---|---|
| 1 | System Instructions 系统指令 | 角色设定 + 行为边界 + 安全规则 |
| 2 | Available Tools 工具定义 | `query_employee` / `apply_leave` 的 schema + 描述 |
| 3 | Long-Term Memory 长期记忆 | 员工偏好、常用审批人（跨会话持久） |
| 4 | Conversation History 对话历史（短期记忆） | 本会话的多轮交互 |
| 5 | User Prompt 当前用户输入 | 本轮请求本身 |
| 6 | Retrieved Information 检索知识（RAG） | 年假制度、资产申领政策的检索片段 |
| 7 | Output Format 输出格式 | 结构化输出 schema（如请假表单的 JSON 约束） |

**工具执行结果的地位**：严格属于第 4 项（message 里的 tool result），但 Lance Martin（LangChain）的分类法只认三种上下文类型——**Instructions / Knowledge / Tools（工具反馈）**。实践上必须把工具结果当一等公民：它是 token 消耗大户，是压缩时最先清理的对象（tool result clearing）。

### 1.2 HR 企业级场景要额外补的四块

教科书七要素是通用模型，企业内 Agent 还差：

1. **身份/权限上下文** — `employeeId`、部门、角色、数据权限范围。**服务端注入、防伪造**（用户说"我是张三"不作数），HR 场景命门，不能混在系统提示词里。
2. **运行时/环境上下文** — 当前时间（"下周五"要解析成日期）、时区、租户、渠道（Web/IM）。
3. **任务状态/工作记忆（Scratchpad）** — 多步任务中间态：请假表单已填 2/4 项、TODO 清单、context reset 的结构化交接文档。Anthropic 称 structured note-taking，是对话历史之外的**另一种短期记忆**。
4. **技能/资源目录（渐进式披露元数据）** — 2025–2026 新成员：Agent Skills 只常驻 name+description，命中才加载正文；MCP 资源 listing 同理。制度文档正确姿势 = 注入"目录"而非全文。

### 1.3 上下文五层结构（HR Agent 设计）

```
┌─────────────────────────────────────────┐
│ L1 系统层   角色设定 + 行为规则 + 输出约束      │  固定，最高优先
│ L2 身份层   员工ID/部门/角色/权限（服务端注入）   │  每次请求动态注入，防伪造
│ L3 知识层   制度文档目录（轻量），详情现查        │  just-in-time 检索
│ L4 状态层   当前任务进度（表单 2/4 项）          │  会话内动态
│ L5 对话层   历史消息 + 工具结果（四层压缩治理）   │  最易爆，重点治理
└─────────────────────────────────────────┘
```

## 二、核心认知：上下文是有限资源，不是越多越好

- **Context Rot（上下文腐化）**：Anthropic 官方确认——token 增多，模型召回准确率下降；注意力随 n² 稀释，模型有"注意力预算"。
- **Smart Zone / Dumb Zone**：经验观察——168K 窗口用到约 **40%** 后输出质量开始下滑（Dex Horthy 提出；JavaGuide 收录时强调这是待验证的经验值，生产上应以自有评测定阈值）。
- **上下文焦虑**：Anthropic 发现模型接近上限时会犹豫、提前收工；解法是 **Context Reset + 结构化交接文档**（提取任务状态/已完成/待办，开新会话只带交接文档）。
- 指导原则一句话：**维持最小高信号 token 集**（smallest set of high-signal tokens）。

## 三、每类上下文治理策略不同（不能笼统管）

| 要素 | 治理重点 |
|---|---|
| 指令 / 工具 / 输出格式（1、2、7） | **精简**——避免超级 System Prompt 反模式 |
| 记忆 / RAG（3、6） | **检索质量** + 按需加载（just-in-time） |
| 对话历史 + 工具结果 + 任务状态（4 + scratchpad） | **压缩与生命周期**——唯三随轮次线性增长的 |

模块一的核心 = **每层注入多少 token 的预算分配**，七项要素在争夺同一块有限 RAM。

## 四、四层压缩管线（对话层治理方案）

Claude Code 实际做法，核心原则：**用廉价规则操作延迟昂贵的 LLM 调用**。

```
第1层 微压缩（规则，<1ms）   每轮自动：旧工具结果替换为 "[cleared]"，不丢语义
第2层 Session Memory 压缩（<10ms） 复用已有摘要，不调 LLM
第3层 传统压缩（5-30s）      调 LLM 生成结构化摘要（保留决策/待办，丢弃冗余）
第4层 兜底                   裁剪最旧消息
```

- 阈值触发（留 buffer），带**熔断器**：连续失败 3 次本轮不再尝试。
- Tool result clearing 已被 Anthropic 作为平台特性发布。
- 压缩的艺术在取舍：先最大化召回（不漏关键信息），再迭代提升精度（删冗余）。

## 五、Just-in-Time 检索与渐进式披露

- 传统 RAG：预检索 → 全文注入。现代做法：上下文只放**轻量标识**（目录/名称/描述），模型需要时用工具现查。
- 混合策略（Claude Code 模式）：少量常驻目录（AGENTS.md 只当目录用，约 100 行）+ 工具按需取详情。
- 对 HR Agent：制度文档不整段注入，只注入"有哪些制度可查"的目录，细节走 `query_policy` 工具。

## 六、NestJS 落地方案

- `PromptBuilderService`（组装五层上下文 → 结构化 messages）
- 身份注入：`AuthGuard` 解析 JWT → `AsyncLocalStorage` 存 EmployeeContext（2025 社区实践确认：ALS 替代 REQUEST scope，性能更好）→ PromptBuilder 从 ALS 取，LLM 看到的身份是系统给的
- `CompressionPipeline` 按层编排四层压缩 + 熔断
- `ContextStoreService` 包 Redis 存热会话；压缩摘要/交接文档落 PostgreSQL
- 横切：上下文利用率监控（每层 token 占比），作为「评估与观测」模块的数据源
