# Agent Harness 工程 · 模块二：工具系统

> 背景：基于 NestJS 的 HR Agent（查个人信息、请年假、申请资产）。本文记录模块二「工具系统」的讨论结论（2026-09-08，基于联网检索的 2025–2026 最新实践）。

## 一、能力的三层模型（MCP vs Skill 的正确关系）

**经典误区**：MCP 和 Skill 是能力的两种"形态"、二选一。
**正确认知**：两者在不同层，是互补关系。Anthropic 官方定位：**MCP 在集成层（连接问题），Skill 在知识层（能力问题）**。比喻：MCP 是"手"（够得着外部系统），Skill 是"操作手册"（教 Agent 怎么用手干活）。

```
┌────────────────────────────────────────────────────┐
│ L2 知识层：Skill（SOP/操作手册）                       │
│   "请年假"完整流程知识：查余额→校验制度→填表→提交→提醒   │
│   渐进式加载，Markdown 编写，无需改代码                  │
├────────────────────────────────────────────────────┤
│ L1 接入层：工具怎么暴露给 Agent ←「形态」选择在这层      │
│   本地 Function Tool（同进程） vs MCP Server（跨进程协议）│
├────────────────────────────────────────────────────┤
│ L0 原子能力：业务系统本身的 API/Service                │
│   人力域.queryEmployee()  考勤域.applyLeave()  资产域... │
└────────────────────────────────────────────────────┘
```

**判断口诀**：单步确定性操作 → 工具就够；多步、含制度规则、含格式要求的流程 → 工具 + Skill；跨进程/跨团队/多 Agent 复用 → 包成 MCP。

**HR Agent 形态决策（已定）**：

| 场景 | 形态 | 理由 |
|---|---|---|
| 查询个人信息 | 本地 Function Tool | 单步、确定性、同进程直接调 Service |
| 发起请假 / 申请资产 | 工具 + Skill | 工具提供原子能力；Skill 承载 SOP（查余额→校验制度→收集信息→二次确认→提交） |
| 跨团队复用（未来） | MCP Server | 考勤等独立微服务归其他团队时，天然暴露成 MCP |

2026 趋势：MCP 也引入渐进式发现，Skills 上下文效率优势在缩小；官方模式是 **MCP Server 自带 Skill**（说明书跟着工具走），两者走向融合。

## 二、场景化工具集：Tool RAG（已定为 B 档）

**问题**：静态全量绑定 = "生产毒药"。50 个工具全绑，token 消耗涨 6 倍，选错率超 25%。
**标杆数据**（Anthropic Tool Search Tool，2025-11）：按需发现替代全量加载，上下文占用 ~77K → ~8.7K（保留 95%），准确率 Opus 4 从 49%→74%、Opus 4.5 从 79.5%→88.1%。

**漏斗式选择管线**：

```
全量工具库（注册中心 ToolRegistry）
  → ① 权限硬过滤（RBAC：当前员工角色能用什么）  ← HR 场景第一步，接模块一 L2 身份层
  → ② 规则/关键词匹配（高频场景 0 错误率）
  → ③ 语义检索（向量 + BM25 混合，Rerank 精排）
  → Top 3~5 个工具交给 LLM（候选集建议 ≤ 20）
```

**三个关键细节**：

1. **示例查询嵌入**（召回率杀手锏）：不嵌工具"功能描述"（太抽象），给每个工具生成 10~20 个"典型用户问法"做嵌入，用 query 匹配 query
2. **每轮重新选择**：多轮对话切换话题后复用上轮工具集是最常见坑。LangGraph 模式：`select_tools` 节点每轮重跑，`ToolNode` 持全量负责执行，职责分离
3. **工具描述工程**是准确率上限：写清适用场景、触发词、反向排除（"不用于 XX"）

**已定方案**：权限过滤 + 语义精选 Top-K（B 档）。HR Agent 工具总量 < 30，不上重型 Tool RAG，但权限过滤 + 语义精选两层第一期就做，避免架构返工。

**权限场景示例**：`employee.get` / `leave.apply` 对所有员工开放；`employee.search`（跨人查询）、`assets.approve` 仅管理员可见——越权工具从候选集直接消失，而不是等调用时拒绝。

## 三、调用时机：自主权是个光谱，不是开关

Programmatic Tool Calling（Anthropic 2025-11）的核心思想：编排逻辑（循环/条件/数据转换）用代码表达，中间结果不进上下文。

| 档位 | 机制 | HR 场景适用 |
|---|---|---|
| 模型自主决定 | ReAct 循环，描述质量 + few-shot 驱动 | 查询类（查信息、查余额、查制度） |
| 代码编排 | 循环/条件写在代码里，中间结果不进上下文 | 批量操作（给全组查考勤） |
| 工作流硬约束 | 编排层强制顺序，模型无选择权 | 写操作（请假/资产必须走确认）→ 模块三/六 |

前沿了解：RL 学习调用时机与参数构造（阿里云工具优选+重排序，500 工具场景响应提速 7 倍、token 降 4~6 倍），商业化方向，自建不现实。

## 四、返回结果治理：三道闸门（绝不原封不动）

工具结果是上下文里增长最快的部分。

**闸门 1：返回时瘦身（工具内部）**
- 字段投影：`query_employee` 底层 50 字段 → 只返回需要的 8 个
- 引用代替全文：制度查询返回"摘要 + docId"，全文按需再取（just-in-time 闭环）
- 分页 + token 预算：每个工具定义返回上限，超出给"还有 N 条，要更多吗"

**闸门 2：错误即教学**
- 错误信息告诉 Agent 怎么改（OpenAI linter 模式：报错自带修复指令），而非 `"error: invalid params"`
- 降级路径显式设计，统一错误格式

**闸门 3：历史结果清理（运行时）**
- 模块一四层压缩管线第 1 层微压缩：N 轮前的工具结果替换为 `[cleared]`
- **工具系统与上下文管理在此闭环**

## 五、待后续模块解决的问题

- 写操作工具的幂等键 + 二次确认 → 模块六「约束与恢复」
- 多步工具链的流转与分支 → 模块三「执行编排」
- 工具调用链路追踪 → 模块五「评估与观测」
