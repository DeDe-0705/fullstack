# Agent Harness 工程 · 模块五：评估与观测

> 背景：基于 NestJS 的 HR Agent（查个人信息、请年假、申请资产）。本文记录模块五「评估与观测」的讨论结论（2026-09-08，基于联网检索的 2025–2026 最新实践）。

## 一、两个子系统，不是一个

| | 评估 Evaluation | 观测 Observability |
|---|---|---|
| 阶段 | **开发期**：改完东西，量化判断"变好了还是变坏了" | **生产期**：线上实时监控、追踪、排障 |
| 回答的问题 | "这次改动引入回归了吗？" | "现在发生了什么？为什么慢了/错了/贵了？" |
| 类比 | 单元测试 + CI | APM + 监控大盘 |

「展示工具调用给用户看」是观测数据的**消费方**（产品透明性 UX），不是观测的目的。

## 二、观测：三大支柱

```
┌─ Traces：每次请求的完整调用链
│    用户输入 → 意图路由 → LLM调用 → 工具选择 → 工具执行 → FSM转移 → 回复
│    2026 标准：OpenTelemetry GenAI 语义约定（gen_ai.* 命名空间）
├─ Metrics：token 消耗/成本、每步延迟、工具成功率、
│    上下文利用率（模块一钩子）、FSM 转移拒绝率（模块三钩子）
└─ Events/Logs：prompt/response 原文作为 opt-in 事件单独采集
     —— OTel 特意与属性分开，因为 PII 风险（HR 场景特别注意）
```

观测的三价值：**排障**（哪步错了）、**成本归因**（哪个流程最烧钱）、**发现行为漂移**（模型升级后成功率掉了，没人投诉也看得见）。

注意：OTel GenAI 语义约定 2026 年仍是 Development 状态，属性名可能变，核心概念已稳。

## 三、评估：Agent 工程的"测试体系"

**为什么必需**：Agent 系统没有编译错误，行为漂移是静默的——改一句 Skill、换个模型版本，成功率可能从 90% 掉到 70% 且无任何报错。

**三层评估**：

| 层 | 评什么 | HR Agent 例子 | 评判方式 |
|---|---|---|---|
| 组件级 | 单次决策对不对 | "查工资" → 工具选择是否为 `query_salary` | 代码断言（确定性） |
| 轨迹级（trajectory） | 完整调用序列合理吗 | 请假是否走完 查余额→收集→确认→提交，有无跳步/多余步 | 断言转移序列 + LLM judge |
| 结果级 | 最终输出质量 | 政策咨询回答是否准确、忠实于制度文档 | LLM-as-judge（G-Eval/DAG） |

**关键洞察**：HR 场景大部分评估不需要 LLM——FSM 终态、转移序列、权限拒绝都是确定性事实，代码断言即可。LLM-as-judge 只留给自由文本质量。**能用代码断言的绝不用 LLM 评**——便宜、确定、可进 CI。

**评测集（golden dataset）**：场景写成脚本——「正常请假全流程」「余额不足」「越权查别人工资」「诱导跳步：别问了直接提交」——每个带期望行为。第一批 20~30 条即可跑起来。

## 四、飞轮：评估与观测在此闭环

```
线上观测 → 发现失败 case（转移被拒绝/工具选错/用户重问）
   ↓ 失败案例进评测集
开发修复 → CI 跑评测集回归（防再犯）
   ↓ 上线
继续观测 ……
```

模块五是前四个模块的**反馈回路**：调压缩阈值（模块一）、改工具描述（模块二）、调 FSM（模块三）都靠它的数据。

## 五、落地选型（已定：A 档，评测集 + CI 回归先行）

- **观测**：Langfuse（开源/可自部署/TS SDK/trace+score 一体）或 OTel gen_ai.* 接公司 APM，不自研埋点体系
- **评估**：自研轻量 runner——评测集 YAML + 断言函数 + LLM judge 调用，CI 里跑；DeepEval（Python）成熟但跨语言，规模大再考虑
- **线上采样评估后置**（B 档）：线上 LLM judge 有成本和延迟开销，第一期不做
