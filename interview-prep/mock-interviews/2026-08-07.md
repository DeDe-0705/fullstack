## 第十轮：Vue3 专题

### Q1：v-for 的 key 应该用 index 还是商品 id？

**德德的回答：** 不用 index。新增、删除会导致数组下标变化，造成不必要渲染或渲染错误；通常用商品 id 作为 key。

**评分：⭐⭐⭐⭐**（结论正确，但追问暴露出 key 底层机制的盲区）

**追问 1：** 用 index 作为 key，删除第一行 A 后，为什么 B 的输入框内容会跑到第一行？

**回答：** 不清楚。

**纠正：** key 是 diff 判断"是否是同一个节点"的唯一依据。三行 A/B/C 用 index 作 key，删除 A 后新列表 B/C 的 key 变成 0/1，Vue 认为 key0 还是同一个节点，复用原来 A 的 DOM 原地 patch 成 B；文本更新了，但输入框这类 DOM 内部状态（用户输入、焦点、未受控状态）残留，出现"第一行显示 B 的名字、输入框却留着 A 的值"。子组件同理：实例被复用，内部状态跟着位置走。

**追问 2：** 用商品 id 作为 key，删除 A 后 B/C 会销毁重建吗？

**回答：** 不会，key 没变所以复用，只有 A 被卸载。

**评分：✅ 正确**

**追问 3：** 拖拽排序 [A,B,C] → [C,A,B]，快速 diff 中间乱序怎么处理？

**回答：** 不清楚。

**纠正：** ① 建 `keyToNewIndexMap`（key → 新位置）：C:0、A:1、B:2；② 按旧顺序 [A,B,C] 查表得到新位置序列 seq=[1,2,0]；③ 对 seq 求 LIS=[1,2]，对应 A、B 不用移动；④ 只有 C 需要移动到最前面。

**盲区：** key 与 diff 节点复用机制；快速 diff 中间乱序 + LIS。

### Q2：搜索防抖 + 取消上一次请求

**题目：** 输入关键字防抖 300ms 发起搜索；上一次请求未返回时又改了关键字要取消；组件卸载时清理。用 watch 还是 watchEffect？flush 怎么设？

**德德的回答：** 用 watch 监听关键字变化；onUnmounted 清理未完成请求和定时器；flush 不太明白。

**评分：⭐⭐⭐**（watch 选型正确、清理思路正确；flush 是盲区）

**纠正：**
- flush 三档：`pre`（默认，数据变化后、渲染前批量执行，本场景用默认即可）、`post`（渲染后 DOM 已更新，回调里读 DOM 用）、`sync`（数据一变立即执行，少用）
- 3.5+ 的 `onWatcherCleanup()` 可在 watch 回调内注册清理函数，下次回调触发或组件卸载时自动执行，比全部堆在 onUnmounted 更精准

**盲区：** watch 的 flush 语义；onWatcherCleanup 清理机制。

### Q3：keep-alive 缓存长表单

**题目：** Tab 切换要保留表单内容、滚动位置、输入焦点；只想缓存大表单组件；缓存数量有上限。

**德德的回答：** 用 keep-alive 保留组件内容和状态；用 include 指定组件名；通过 LRU 淘汰。

**评分：⭐⭐⭐**（方案关键词正确，内部机制盲区）

**追问 4：** keep-alive 缓存的是什么？max=10 时第 11 个进来淘汰谁？"最久未使用"靠什么机制判断？切回触发什么钩子？

**回答：** 缓存的是 vnode；淘汰很久没渲染的组件，机制不清楚；onActivate 多次执行，onMounted/onUnmounted 只执行一次。

**纠正：**
- 缓存的是 vnode 及其子树（背后挂着组件实例和 DOM），实例不销毁只是暂停渲染
- LRU 内部机制：`cache` + `keys` 两个 Map；命中时先把 key delete 再 set 排到队尾；超过 max 淘汰 keys 的第一个（最久未使用），此时才真正卸载触发 onUnmounted
- 钩子名是 `onActivated` / `onDeactivated`；首次挂载 onMounted → onActivated；切走触发 onDeactivated；切回触发 onActivated（不触发 onMounted）；被淘汰才触发 onUnmounted

**盲区：** keep-alive LRU 内部机制；activated 首次触发时机。

### Q4：provide/inject 全局主题

**题目：** 全局主题从根部提供给深层组件，主题切换所有用到的地方同步更新。

**德德的回答：** 用 provide/inject 或 Pinia；provide 普通对象和 ref/reactive 的区别不清楚；inject 沿父子链往上找最近的 provide，直到根节点，找不到为 undefined。

**评分：⭐⭐⭐**（inject 查找机制答对；provide 响应式本质是盲区）

**纠正：**
- provide/inject 本身不提供响应式，它只是值传递机制；响应式来自"给的值本身是否是 ref/reactive"
- provide 普通对象：后代拿到同一份对象但不会被追踪，整体替换新对象也不会通知后代
- provide ref/reactive：后代读取时 track、修改时 trigger，主题一改所有 inject 的组件同步更新
- inject 找不到时返回默认值（`inject(key, default)`）否则 undefined；provides 通过原型链继承，中间组件是否 provide 不影响查找

**盲区：** provide/inject 的响应式本质。
