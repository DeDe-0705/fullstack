## Q1：商品详情页 6 类状态分工（⭐⭐⭐⭐）

**题目**：商品信息/选中SKU/购物车/收藏/详情展开/分享弹窗——分别放哪管理？

**回答**：1/3/4 TanStack Query，2/5 useState，6 URL。3、4 主动答出乐观更新 + 失败场景（库存不足/商品下架）✅

**纠正**：
1. **SKU 与弹窗错位**：SKU 应放 URL（分享链接/刷新/返回保留选中态，useSearchParams）；弹窗放 useState（放 URL 会污染历史记录——开关 4 次要按 4 次返回）。德德补充的"深链 ?share=1 初始打开"模式成立，但清除参数必须 `navigate(url, {replace: true})`
2. **cancelQueries 目的答错**：不是"防上一次状态覆盖"，是取消**进行中的 refetch**，防旧响应拿着服务端旧数据冲掉刚写入的乐观值
3. **快照来源答错**：不是 React state，是 `queryClient.getQueryData()` 从 **Query 缓存**拿——TanStack Query 的意义就是缓存脱离组件 state

**必须能默写的乐观更新四步**：getQueryData 拿快照 → setQueryData 乐观写 → context 传快照 → onError 回滚 + onSettled invalidate 对齐

## Q2：useOptimistic 能否替代 Query 乐观更新（⭐⭐，盲区，已给标准答案）

**机制对比**：useOptimistic = React 内部临时覆盖，只在 transition pending 期间生效、结束自动回落、作用域当前组件树；Query 乐观更新 = setQueryData 真写缓存、持久、全局共享、需快照回滚。
**结论**：购物车选 Query（多组件共享 + 需与服务端对齐）；useOptimistic 适合单组件短生命周期场景（点赞/IM 消息上屏/todo 勾选）。
**为什么必须在 transition 里触发**：React 需要乐观值的生命周期边界——pending 开始生效、action 完成回落；同步 setState 没有 pending 窗口。
**记忆锚点**：乐观值是"租来的"，transition 是"租期"。

## Q3：搜索页竞态 + 输入卡顿（⭐⭐⭐）

**bug① 竞态**：✅ 知道不用手写取消，提到 AbortController；❌ 漏掉核心机制——**queryKey 隔离**：每个关键词是独立缓存槽位，旧响应写旧槽位，组件只订阅当前 key，错乱在数据结构上不存在。signal 传给 fetch 即可，Query 自动 abort——但作用是省带宽，不是防错乱。

**bug② 输入卡顿**：✅ 选对 useDeferredValue。纠正表达：debounce 是"延迟执行"减少次数、不解决单次渲染耗时；useDeferredValue 包**值**、useTransition 包 **setState 动作**，底层同为**并发渲染优先级调度**——不减少工作量，让紧急更新先渲染、昂贵更新可中断让路。

**③ 防闪烁**：不会。答案 `placeholderData: keepPreviousData`（v5；v4 为 keepPreviousData: true）。placeholderData 是占位不写缓存，区别于 initialData。

## Q4：Zustand 订阅与重渲染（⭐⭐）

1. 病灶：`useStore()` 不传 selector 订阅整个 store ✅ 方向对；❌ 术语纠偏：Zustand 是 selector 参数，useSelector 是 react-redux 的
2. 多字段坑：selector 返回新对象 → Object.is 必不等 → 每次重渲染。❌ 德德答"把 theme 提 Context"（过度设计且答偏）。正解 **useShallow**（zustand/react/shallow 浅比较）。机理链：store 变 → selector 重跑 → 返回值 Object.is 比较 → 不等才重渲
3. 机理盲区：无 Provider = 模块级单例外部 store；底层 **useSyncExternalStore**；解决并发模式 **tearing**（渲染中途外部 store 变化导致同次提交 UI 不一致）→ getSnapshot + 提交前重检，变了丢弃重渲

## Q5：Redux 不可变性与 immer（⭐⭐）

1. state.count++ 不矛盾：✅ 说出 immer 名字；❌ 原理不会。三件套必背：**Proxy 拦截 draft 写操作 + copy-on-write 只复制被改路径 + 结构共享**（draft 未改直接返回原 state）
2. 不可变的根：**useSelector/connect 用 === 引用比较做变化检测**——改原对象引用不变 → UI 不更新（Redux 最常见 bug）。time-travel/memo 都建立在"引用变=内容变"上
3. ✅ 答对 extraReducers；❌ 原因不会：三态是 thunk 运行时自动 dispatch 的外部 action；reducers 只收本 slice 同步 action；reducer 必须同步纯函数，异步归 action 层

## Q6：IM 聊天窗口综合设计（未作答，归档标准答案）

**① 状态分工**：原则——**服务端状态唯一真源，不复制进 Zustand**（复制=双数据源同步问题）。历史消息 `useInfiniteQuery(['messages', cid])`；SSE 新消息在 onmessage 里 `queryClient.setQueryData` 追加到最后一页，订阅者自动更新；Zustand 只管纯客户端状态（当前会话、草稿、对方正在输入、未读角标本地标记）。

**② 乐观发送**：选 Query 乐观更新（非 useOptimistic——消息列表多组件共享且需持久）。**临时 id**：`crypto.randomUUID()` 生成 tempId + status:'sending' 乐观上屏；成功后用真消息**按 tempId 替换**（不是追加，防重复）；失败**不删除**（用户内容不能丢）标 status:'failed' + 重发按钮。

**③ 滚动性能**：虚拟列表（视口±overscan）+ IM 特有难点：
- **反向滚动锚定**：向上 prepend 旧消息时记录第一个可见消息 key+offset，插入后恢复滚动位置（CSS overflow-anchor 在虚拟列表里不够，要自己算）
- **动态高度**：图片消息加载后变高 → 预估高度占位 + 实测后校正偏移（Map<id, height> 缓存）
- **新消息策略**：用户不在底部时不自动滚动，出"有新消息"浮标；在底部才顺滑滚到底
- 消息项 memo（key=消息 id）
