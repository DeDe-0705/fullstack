## Q1：setState 批处理代码诊断

**题目**：三次 `setCount(count + 1)`，render 打印几次？count 是几？换函数式更新呢？

**回答**：「最终是 1，函数式更新为 3，每次 c 是上一次 hook 计算的最新结果。」

**纠正**（2 处）：

1. 漏答"打印几次"——**只打印 1 次**，考点是 React 18 `createRoot` 的**自动批处理**：同一事件处理器内多次 setState 合并为一次渲染
2. 术语纠偏：不是"上一次 hook 计算的结果"，而是"**同一批次内，前一个更新在队列处理阶段的计算结果**"——更新发生在 render 之前的队列处理，不是 hook 逐次计算

**追问**：`setTimeout` 里三次 setState，React 18 / 17 各渲染几次？
**回答**：「18 一次，17 三次」✅ 全对。补充：18 批处理覆盖所有场景（合成事件 / setTimeout / Promise / 原生事件）；反向 API `flushSync` 可强制同步。

**评分**：⭐⭐⭐⭐⭐（追问满分，主回答漏一小问扣在审题）

## Q2：Fiber 架构解决什么问题？Fiber 让 React 更快了吗？

**回答**：讲了链表结构（return/child/sibling）、lanes 优先级、memoizedState 存 hooks 链、双缓存树 + alternate、bailout 跳过、commit 阶段。最后判断「Fiber 是让 React 变得更快了」。

**纠正**（2 处）：

1. **核心判断错误**：Fiber 不是更快，是**可中断、可调度**；拆分 + 调度有额外开销，吞吐甚至略降——**用同步渲染的确定性换交互流畅感**
2. 漏答动机：React 15 递归渲染不可中断，树深时长时间占用主线程 → 输入/动画掉帧。答题结构应"先抛问题再给方案"

**追问**：中断/恢复工程上怎么实现？为什么不用 requestIdleCallback？
**回答**：「while 循环逐个执行 Fiber 单元，shouldYield 判断让出，MessageChannel 切片；rIC 有 Safari 兼容问题、时机不可控」✅ 核心全对。
**补充**：shouldYield 基于**时间预算（默认 5ms）**；选 MessageChannel 而非 setTimeout 是因为 setTimeout 嵌套有 **4ms 最小延迟**。

**评分**：⭐⭐⭐⭐（追问 4.5，主回答核心陷阱答错）

## Q3：Hooks 为什么不能写在条件里？+ 手写极简 useState

**第一问回答**：「hooks 链按顺序链接，if/循环会导致取错 hook 节点的状态值。」
**纠正**：方向对但机理说反——对应关系在 **render 阶段**由游标沿链表取 memoizedState 时建立，不是"执行更新时才取"。一句话：**Hook 没有名字，只有序号**。

**第二问手写**：交了仿源码风格版本（mountWorkInProgressHook / processUpdateQueue / requestUpdateLane / scheduleUpdateOnFiber）。
**评价**：源码概念记得牢（加分），但——

1. 不可运行，把源码函数名当占位符
2. `dispatch` 每次 render 新建是 bug：真实实现 mount 时 `bind` 绑死 fiber + queue，存入 `queue.dispatch`，是稳定引用
3. 没回答"setState 为什么不串"：**闭包捕获槽位 index**（极简版 = hooks 数组 + cursor 游标）
4. mount/update 应由两套 dispatcher 区分

**评分**：⭐⭐⭐⭐

## Q4：场景题 — React.memo 包裹仍重渲染

**题目**：`UserAvatar` 包了 memo，但搜索框每输入一个字就重渲染。为什么？怎么修？theme 字段多且要响应切换时方案变不变？

**回答**：「currentUser 和 theme 每次 render 重建，引用变化触发重渲染。currentUser 提 Redux 或 useMemo；theme 提 Context。」

**纠正**（3 处）：

1. 审题：`currentUser` 来源未明，唯一确定的问题源是 `theme` 字面量——先区分"确定的"和"存疑的"
2. 最简方案漏了：**静态对象提到组件外做模块常量**，零成本；useMemo 次选；Redux 杀鸡用牛刀
3. Context 方案的坑：Provider `value` 若每次 render 新建对象，所有 consumer 照样重渲染 → value 必须 useMemo 缓存 / 拆分 Context

**评分**：⭐⭐⭐⭐

## Q5：场景题 — 大列表过滤卡顿，并发特性怎么救

**题目**：5000 条列表过滤渲染 200ms+，输入卡顿掉字。useTransition 还是 useDeferredValue？过滤计算本身 200ms 能救吗？

**回答**：「useDeferredValue 包裹 query 降低列表渲染优先级；useTransition 不适合过滤场景；改完列表等输入结束才渲染；并发救不了计算问题。」

**纠正**（3 处）：

1. "useTransition 不适合"**错误**——两者作用对象不同：useTransition 标记**一次 setState 更新**，useDeferredValue 标记**一个值的使用**（值来自父组件/第三方时）；本题两者都能用
2. "等输入结束才渲染"是**防抖**的描述！并发渲染：输入立即响应（高优），列表渲染可中断，停顿片刻即跟上，期间 stale UI + `isPending` 提示。**并发 ≠ 防抖**，高频扣分点
3. 第三问补机理：Fiber 中断粒度是**组件级**，单组件 render 内同步 200ms 计算不可中断 → Web Worker / 算法优化 / 服务端过滤

**评分**：⭐⭐⭐⭐

## Q6：代码题 — useEffect stale closure

**题目**：`setInterval(() => setCount(count + 1), 1000)` + 空依赖，数字怎么变？两种修复？

**回答**：「变为 1 后不再变，闭包捕获了 count=0 且 effect 不监听变化。修复一：函数式更新。修复二想不出来。」

**纠正**：修复二是教科书标配——**count 进依赖数组**。优选函数式更新的理由：依赖数组方案每 tick 销毁重建定时器（开销 + 计时漂移）；函数式更新让 effect 不依赖 count，定时器只建一次，由 React 处理更新队列时传最新 state——"能不依赖就不依赖"。

**评分**：⭐⭐⭐⭐

# 第二轮：React 19 + 合成事件 + 受控组件（同日 12:00-13:15）

> 前置：已补搜 2026 React 19 考点（RSC 边界 / Actions / useOptimistic / Compiler / hydration）

## Q1：合成事件 + stopPropagation 穿透（⭐⭐⭐⭐）

**回答**：定义对；stopPropagation 阻止合成事件冒泡对；"body clicked 不会打印"结论对但机理错；多 root 干扰对。

**纠正**：

- 核心考点答错：合成事件的 `stopPropagation` **内部同时调用 `nativeEvent.stopPropagation()`**。React 17 监听点在 root 容器（body 之下），事件冒泡到 root 时 React 模拟派发、content 的 handler 阻止冒泡 → 真实冒泡终止 → body 收不到
- React 16 委托在 document，body 原生监听先于 React 处理执行 → 会打印。17 vs 16 行为差异是高级岗区分点
- 话术：遇"X 会不会执行"题，按"事件流路径 → 处理点位置 → 拦截是否穿透"三步拆

## Q2：受控 vs 非受控（⭐⭐⭐，本轮最低）

**回答**：定义对、"卡不成立"判断对但理由弱；金额输入框需求选非受控；Vue 对比答偏。

**纠正**：

1. 反驳要打中要害：单 input 受控重渲成本极低，卡在被牵连的大子树 → 状态下放/拆组件，不是抛弃受控。"受控导致卡"是症状当病因
2. **选型错误**："输入中限制 + 失焦格式化"就是受控的定义场景（程序化干预显示值）。非受控直接改 `el.value` 有 **value tracker 深坑**（绕过 React 改值 → tracker 不更新 → 后续更新被跳过）。非受控适用：file 上传、第三方 DOM 库
3. Vue 对比一句话：v-model 是双向绑定语法糖；React 受控是显式单向数据流，环路由开发者显式闭合

## Q3：RSC vs Client Component（⭐⭐，明确盲区）

**回答**：第 1 问摸到边，2、3 问空白。

**补录要点**：

- 本质区别是执行环境决定能力集：SC 永不在浏览器运行 → 无 hooks/事件，可直接 await 数据库、async 组件；bundle 减小的精确原因 = SC 代码及其依赖**不进客户端 bundle**，产出是 Flight 序列化格式
- SC 可 import CC ✅（边界尽量往叶子推）；CC 不能 import SC ❌，但可组合（children/props 传入已渲染的 SC）；跨边界 props **必须可序列化**（函数/class/Symbol 不行）
- RSC ≠ SSR：SSR 渲染的是 Client Component（全量 JS + hydrate）；RSC 零 JS 零 hydrate；两者正交可叠加

## Q4：React 19 Actions 改写评论提交（⭐⭐⭐）

**回答**：useOptimistic 自动回滚对；useActionState 形态模糊；"与 useTransition 没关系"**答错**。

**纠正**：

- `useActionState(action, initialState)` → `[state, formAction, isPending]`；action 收 `(prevState, formData)`，**返回值即新 state**；isPending 是 transition 的 pending，不是"看 reducer 同步异步"
- useOptimistic 机理：乐观值不是真实 state，只在 transition pending 期间覆盖渲染，结束即回落真实 state → 失败自动消失
- **Actions 本质 = 运行在 async transition 里的函数**：useActionState 底层就是 transition，useOptimistic 必须在 transition 内触发。React 19 是把"mutation + transition + pending + 乐观更新"正式化成 API

## Q5：React Compiler 后 memo 三件套能删吗（观点题，德德主动要求给标准答案）

**标准答案三层**：

1. Compiler 只对遵循 Rules of React 的健康代码生效，**不满足就 bailout 跳过**（动态解构、边缘 hook 写法、可变全局依赖）；且管不了"计算结果作为其他 hook 依赖"的语义场景
2. 老代码库渐进接入，手动 memo 范式长期共存，维护/排查离不开
3. 工具自动化"怎么做"，面试和排查考"为什么"——Profiler 诊断、bailout 失效分析仍靠引用相等性原理
4. 收尾句：**"可以删掉"和"可以不懂"是两回事**

## Q6：hydration mismatch 代码诊断（⭐⭐⭐⭐，收官）

**回答**：两处病灶全找对（localStorage / new Date）；定义模糊；isVip 修复答了"数据库取值"，Date 修复不会。

**纠正**：

- hydration 定义：服务端静态 HTML 先到屏 → 客户端重新执行组件绑事件；mismatch 本质 = hydrate 渲染树与服务端 HTML 不一致，无法安全复用 DOM
- 修复原则统一：**渲染期不许读"两端环境不同的值"**（浏览器 API / 当前时间 / 随机数）→ 挪到 useEffect，保证首次渲染确定性；时间戳类可用官方 `suppressHydrationWarning`
