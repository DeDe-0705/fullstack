## 第一轮：浏览器 HTTP 缓存

### Q1：从输入 URL 到页面展示，经历了哪些缓存层级？从上到下说。

**德德的回答：** Service Worker → Memory Cache → Disk Cache → HTTP缓存（强缓存/协商缓存）

**评分：⭐⭐⭐⭐**

**评价：** 顺序正确。补充细节——Memory Cache 优先级高于 Disk Cache，当前页面刚加载的资源优先进 Memory。Push Cache（HTTP/2）已基本淘汰，可以不提。

---

### Q2：强缓存/协商缓存的决策流程？no-store 什么意思？

**德德的回答：** max-age 未过期直接走强缓存，过期了走 Etag/Last-Modified 协商。no-store 走最新缓存。

**评分：⭐⭐⭐**

**纠正：** no-store 不是"走最新缓存"，是**完全不缓存**——浏览器不会把响应存入任何缓存层，每次直连服务器。另外 max-age 优先级高于 Expires，面试中主动提这点能显功底。

**正确话术：** "先判断强缓存（Cache-Control: max-age），命中直接用（200 from disk/memory）；未命中再走协商缓存（Etag → Last-Modified），304 就复用、200 就用新内容。no-store 禁用一切缓存，no-cache 是缓存但每次验证。"

---

### Q3：Service Worker 缓存和 HTTP 缓存本质区别？

**德德的回答：** SW 是业务自定义行为，HTTP 是浏览器和服务器约定的。SW 拦截所有 fetch，命中了就走 SW，HTTP 靠后。

**评价：** 对——SW 在请求链最顶端，让你完全接管网络请求。可以做到离线访问、Network First、Stale-While-Revalidate 等 HTTP 缓存做不到的策略。

---

### Q4：HTML 和 JS/CSS 分别怎么配缓存？为什么不能搞反？

**德德的回答：** HTML 用 no-cache 保证拿到最新 JS/CSS 引用；JS/CSS 文件名带 hash，走强缓存。后续理解了"搞反"的后果——HTML 被强缓存一年会导致用户一直引用旧 JS 文件，新部署后被删了就 404。

**评分：⭐⭐⭐⭐⭐**

**评价：** 实战理解到位，追问问出了本质。

---

### Q5：用户不刷新页面，怎么检测新版本？

**德德的回答：** 业务接口轮询判断是否更新 + 表单草稿保存到本地。补充后理解了 version.json 轻量轮询、Service Worker 自动检测、WebSocket 推送三种方案。

**评分：⭐⭐⭐→⭐⭐⭐⭐**（补充后提升）

**德德的关键洞察：** "SW 方案的本质也是请求一个文件看有没有变化，只是把轮询从 setInterval 换成了浏览器的原生 update 机制。"——触类旁通。

---

### 第一轮小结

| 掌握到位 | 需要加强 |
|----------|----------|
| 缓存层级顺序 | no-store 精确语义 |
| 强缓存/协商缓存决策 | max-age vs Expires 优先级 |
| HTML vs 静态资源策略 | SW 实操经验 |
| 版本更新 + 草稿兜底 | 方案纵深广度 |

## 第二轮：客户端存储

### Q1：Cookie、localStorage、sessionStorage、IndexedDB 的容量和生命周期？

**德德的回答：** 4KB（可设过期）、5MB（永久）、5MB（Tab关闭即清除）、无上限/浏览器决定（永久）

**评分：⭐⭐⭐⭐⭐**

**评价：** 数据准确。

---

### Q2：Cookie 和 localStorage 使用方式上的根本区别？

**德德的回答：** 安全性——Cookie 可以设 HttpOnly、Secure、SameSite，Storage 只有同源限制。

**评分：⭐⭐⭐**

**纠正：** 安全属性对，但最根本的区别是——**Cookie 会自动附带在 HTTP 请求头里发送给服务器，localStorage 不会**。这直接影响鉴权架构：Cookie 存 token 服务端无感鉴权，localStorage 存 token 要手动加到请求头。

---

### Q3：SameSite 怎么防 CSRF？管理后台设哪个值？

**德德的回答：** Strict，不允许跨站发送。黑客在恶意页面用 img 标签发起请求就不带 Cookie。

**评分：⭐⭐⭐**

**纠正：** CSRF 攻击机制理解正确，但选 Strict 太严格。管理后台用 **Lax**——GET 导航（点链接）可以带 Cookie，POST/iframe/img 不带。Strict 会让用户从飞书/邮件点链接过来时变成未登录，只适合银行级场景。

---

### Q4：localStorage 的 storage 事件跨 Tab 退出登录，怎么实现？有什么坑？

**德德的回答：** 监听 storage 事件，对比 key 和 value。坑暂时没想全。

**评分：⭐⭐⭐⭐**

**补充三个坑：**
1. **本页面不触发**——Tab A setItem，Tab A 自己收不到事件，退出逻辑要单独写
2. **值相同时不触发**——`setItem('a','1')` 执行两次，第二次不触发
3. **后台 Tab 事件延迟**——处理逻辑做幂等，已经跳转登录页就不要再跳

---

### Q5：localStorage 写满了怎么办？

**德德的回答：** 浏览器用 LRU 丢弃旧数据；大数据用 IndexedDB。

**评分：⭐⭐⭐**

**纠正：** localStorage **不会自动 LRU 淘汰**，`setItem` 直接抛 `QuotaExceededError`。你需要 try-catch 捕获 + 主动清理。IndexedDB 选型方向对。

---

### Q6：同步 vs 异步对页面性能的影响？

**德德的回答：** 异步不阻塞页面渲染，同步写入大数据会卡顿。

**评分：⭐⭐⭐⭐**

**评价：** 核心结论对。localStorage 同步阻止主线程，频繁写入（如 mousemove 中存拖拽位置）累积掉帧。IndexedDB 异步事务独立执行。

---

### 第二轮小结

| 掌握到位 | 需要加强 |
|----------|----------|
| 容量/生命周期数据 | Cookie "自动发送"是核心区别 |
| storage 事件 + 坑 | SameSite 选型（Strict→Lax） |
| 同步/异步性能影响 | localStorage 满→抛异常，非 LRU |

## 第三轮：SSO 单点登录 + CSP 安全策略

### Q1：Li People 微前端项目里，子应用怎么拿到登录态？

**德德的回答：** 首次登录→CAS 跳转公司用户中心→拿到 token→调 login 接口获取 accessToken + refreshToken 存 localStorage。子应用每次请求拿 accessToken，过期用 refreshToken 换新的，refreshToken 也过期就重新登录。

**评分：⭐⭐⭐⭐⭐**

**评价：** 流程完整清晰，双 Token + 静默刷新 + 独立鉴权 SDK，一听就是亲手搭过的。

---

### Q2：子应用怎么拿到 Token？直读 localStorage vs 无界 Props？

**德德的回答：** 当前方案子应用自己读 localStorage，需要自己判断过期逻辑。用无界 Props 注入则不用关心。

**评价：** 两种方案的成本理解对——Props 注入子应用零鉴权代码，但 Token 刷新期间有时序窗口（主应用刷新了 Token，子应用刚好用旧 Token 发请求→失败）。

---

### Q3：过期处理逻辑放哪？一个子应用过期，其他怎么办？

**德德的回答：** 在请求拦截器里处理，每次请求都判断。过期后整站跳登录页，包括父应用和所有子应用。

**纠正：** `window.open` 会打开新窗口，应改用 `window.location.href = '/login'` 做当前页面跳转。跳转前可存 sessionStorage 保留状态。

---

### Q4：用户填表单时 Token 过期怎么办？

**德德的回答：** 草稿保存优化 + 过期前提醒。

**评分：⭐⭐⭐⭐**

**评价：** 体验意识到位。

---

### Q5：CSP 策略——H5页面引用自家CDN的JS、调用 API、嵌入报表 iframe

**德德的回答：** 混入了 CORS 概念——说 CDN JS 正常加载、接口加跨域字段、iframe 正常渲染。

**评分：⭐⭐**

**纠正：** CSP 和 CORS 是两套独立机制：
- **CSP**：页面声明"我只信任这些来源"，在浏览器**加载资源前**拦截
- **CORS**：服务端声明"我允许这些来源读数据"，在**响应返回后**控制读取

**正确的 CSP 策略：**
```http
Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://cdn.example.com;
  connect-src 'self' https://api.example.com;
  frame-src https://report.example.com;
  img-src 'self' data: https://cdn.example.com;
  style-src 'self' 'unsafe-inline';
```

---

### Q6：CSP 怎么安全灰度上线？

**德德的回答：** 没有实操经验，主要看运维日志。

**评分：⭐⭐**

**标准流程：**
1. 先用 `Content-Security-Policy-Report-Only` 配 1-2 周——只上报不拦截
2. `report-uri /csp-violation` 收集违规数据
3. 分析日志确认无误报后，切换为正式 `Content-Security-Policy`
4. 开发调试时优先看浏览器 Console——会直接打印违规资源

## 第四轮：计算机网络

### Q1：HTTP/1.1、HTTP/2、HTTP/3 核心区别

**德德的回答：** 都是为了提高网络请求的稳定性和速度。1.1 基于 TCP 有状态长连接解决队头阻塞；2.0 一个 TCP 多个 Stream 避免并发；3.0 基于 UDP。

**评分：⭐⭐⭐**

**纠正：**
- ❌ "1.1 解决队头阻塞"——正相反，1.1 本身有队头阻塞。1.1 解决的问题是 1.0 的短连接反复握手。
- ❌ "2.0 避免 TCP 并发"——不是避免，是用多路复用替代了多连接。但 TCP 层队头阻塞仍在。
- ✅ "3.0 基于 UDP"——方向对。

**正确答案：**
| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|------|----------|--------|--------|
| 连接 | 多 TCP(6个/域名) | 单 TCP 多路复用 | QUIC(UDP) |
| 队头阻塞 | 有(HTTP层) | 解决HTTP层，TCP层仍存在 | 彻底解决 |
| 头部压缩 | 无 | HPACK | QPACK |

---

### Q2：HPACK 头部压缩原理？为什么不能用 gzip？

**德德的回答：** 不了解。

**评分：⭐**

**补课要点：**
- gzip 不行：需要连续上下文解压（HTTP/2 帧交替无法满足）+ CRIME 攻击风险
- HPACK 原理：双方维护字典表（静态61个 + 动态），重复字段传索引号
- 类比：第一次说"理想汽车 Li People"，之后说"Li People"就够了

---

### Q3：TLS 握手机制——为什么非对称和对称加密都要用？

**德德的回答：** 知道公钥私钥概念，但具体握手流程不熟。

**评分：⭐⭐⭐**

**补课要点：**
- 两段式设计：非对称加密(慢但安全)传对称密钥 → 对称加密(快)传数据
- 各取所长 = HTTPS 的设计精髓

---

### Q4：浏览器怎么验证证书？假证书为什么通不过？

**德德的回答：** 验证密钥准确性，假证书给的密钥解码不对。

**评分：⭐⭐**

**正确答案——四级关卡：**
1. 证书链验证（根CA → 中间 → 站点，逐级签名校验）
2. 有效期检查
3. 域名匹配（CN/SAN 字段）
4. 验证私钥持有（服务端用私钥签名，客户端用公钥验）

---

### Q5：Charles 抓 HTTPS 的原理？算不算中间人攻击？

**德德的回答：** 用过 Charles/Wireshark。不算攻击，因为是我授权的。

**评分：⭐⭐⭐⭐⭐**

**评价：** "我授权了所以不算"——一语道破本质。Charles 就是标准中间人代理，只是因为用户主动安装了它的根证书，浏览器信任了它。

---

### Q6：CORS 什么时候发 OPTIONS 预检？

**德德的回答：** 页面二级域名和请求的不相同会发 OPTIONS。

**评分：⭐⭐⭐**

**纠正：** 不是看域名，是看**请求是否"简单"**：
- 简单请求（GET/HEAD/POST + 标准头 + Content-Type 限三种）→ 不发 OPTIONS
- 非简单请求（PUT/DELETE/自定义头/`Content-Type: application/json`）→ 发 OPTIONS
- OPTIONS 可通过 `Access-Control-Max-Age` 缓存（Chrome 上限 7200 秒）

---

### Q7：为什么 TCP 挥手四次，不能像握手一样合并？

**德德的回答：** 服务端还有数据没处理完，要保证事务完成后再断开；客户端收到后才确认断开并告知服务端。

**评分：⭐⭐⭐⭐⭐**

**评价：** 全双工独立关闭——直击本质，今天答得最好的一题。

## 第五轮：DNS 与 CDN

### Q1：DNS 解析完整链路，经过哪些缓存层级？

**德德的回答：** OS hosts → 路由器缓存 → 根域名服务器 → 顶级域名 → 二级域名 → 层层返回 → 存储到路由表和 OS 表。

**评分：⭐⭐⭐**

**纠正：**
- ❌ 漏了浏览器自身 DNS 缓存（Chrome 有独立缓存，几十秒到几分钟）
- ❌ "存储到路由表"——DNS 缓存和路由表是两层不同的东西
- ❌ 漏了 ISP 递归查询——你问一次 ISP，ISP 替你跑完全程

**正确链路：** 浏览器缓存 → OS(hots文件) → 路由器 → ISP递归服务器 → 根→顶级→权威迭代查询 → 各级缓存存储

---

### Q2：DNS 改记录后部分用户仍访问旧 IP，为什么？

**德德的回答：** 不了解。

**评分：⭐**

**补课：** DNS 有 TTL（Time To Live），各级缓存服务器在 TTL 过期前不会重新查权威 DNS。解决：提前 24 小时降低 TTL（60秒）→ 全球旧缓存过期 → 修改记录 → 60秒内全球生效。或者新旧 IP 并存过渡。

---

### Q3：发新版，HTML 已更新但用户看到旧内容，什么原因？

**德德的回答：** HTML 被缓存了，引用的 JS 还是旧的。

**评分：⭐⭐⭐⭐**

**评价：** 精确定位到 HTML 缓存是主因。JS/CSS 文件名带 hash 了，URL 变了不怕 CDN 旧缓存。

---

### Q4：旧版 hash 文件在 CDN 上还能访问到，算问题吗？

**德德的回答：** 能访问到，但 HTML 引用的是新文件名，用户不会拿到旧的。

**评分：⭐⭐⭐⭐**

**评价：** 理解 hash 文件名的版本隔离本质——新旧 URL 互不影响。

---

### Q5：新 JS 文件 404 白屏，什么原因？

**德德的回答：** CDN 服务器没拉取到新资源，强制刷新 CDN。

**评分：⭐⭐⭐**

**纠正：** 404 意味着源站也没有这个文件，不是 CDN 没拉取。根因是**部署顺序反了**——先部署 HTML（引用新文件），后上传 JS 到 CDN。正确顺序：先推静态资源 → 验证可访问 → 再部署 HTML。

---

## 第六轮：浏览器渲染原理

### Q1：从拿到 HTML 到页面渲染完，经历了哪几个阶段？

**德德的回答：** DOM树 → CSSOM树 → Render Tree → 计算位置(Layout) → 绘制(Paint) → GPU合成(Composite)

**评分：⭐⭐⭐⭐**

**评价：** 六阶段完整，框架扎实。这是高级前端面试的"必答题"。

---

### Q2：`<script>` 怎么阻塞渲染？async 和 defer 的区别？

**德德的回答：** script 阻塞 DOM 渲染。async 下载不阻塞、渲染阻塞；defer 下载不阻塞、等 DOM 渲染完执行。

**评分：⭐⭐⭐**

**纠正：** async 是"执行时可能阻塞 DOM 解析"，不是"渲染阻塞"。defer 是等"DOM 解析完"（DOMContentLoaded 前），不是等"渲染完"。精确对比见下表：

| | 普通 | async | defer |
|------|-----|-------|-------|
| 下载 | 阻塞DOM解析 | 并行 | 并行 |
| 执行 | 立即 | 下载完立即(乱序) | DOM解析完按序 |
| DOMContentLoaded | 等 | 不保证 | 之前完成 |

---

### Q3：`<script>` 之前的 CSS 没加载完，JS 能执行吗？

**德德的回答：** 不能，浏览器按顺序加载。

**评分：⭐⭐⭐**

**补课要点：** 不仅是顺序问题。根因是 JS 可以通过 `getComputedStyle()` 读取样式，如果 CSS 没加载完 JS 执行会拿到错误结果。浏览器为保正确性，必须等前面 CSS 加载完并构建 CSSOM 后再执行 JS——**CSS 间接阻塞 JS 执行**。

---

### Q4：浏览器怎么决定元素要不要提升为独立图层？GPU 加速有什么坑？

**德德的回答：** 可能看 DOM 节点之间的关系。GPU 加速不太明白。

**评分：⭐⭐**

**补课要点：**
- 自动分层条件：3D transform、video/canvas/iframe、CSS filter、will-change
- 手动触发：`transform: translateZ(0)` 或 `will-change`
- **大坑：** 每个图层占显存，大列表每项都 `will-change` → 1000个图层 → 显存爆炸

---

### Q5：滚动列表卡顿，Performance 面板大量 Layout（强制同步布局）— 原因和解决方案？

**德德的回答：** 滚动事件用节流，加虚拟滚动。

**评分：⭐⭐⭐**

**纠正：** 虚拟滚动和节流是对的，但还有一种更隐蔽的根因——**读写交替触发强制同步布局**：

```js
// ❌ 滚动中读写交替
const h = header.offsetHeight  // 读 → 强制Layout
header.style.top = h + 'px'    // 写
// 每帧 Layout → Paint → Composite，60fps做不到
```

解法：读操作放 `requestAnimationFrame`，写操作放下一个 rAF。

---

### Q6：Chrome 打开一个网页有哪些进程？渲染进程内有哪些线程？

**德德的回答：** JS 解析线程、Worker 线程、网络请求进程、渲染进程。

**评分：⭐⭐**

**补课要点：**
- 进程：浏览器主进程（1） + GPU进程（1，共享） + 网络进程（1，共享） + 渲染进程（每站点1个）
- 渲染进程内：主线程（JS引擎/GUI渲染/事件/定时器/HTTP） + 合成线程（独立，Composite阶段） + IO线程
- JS引擎线程与GUI渲染线程互斥 → 这也是 JS 长任务导致卡顿的根本原因
