## Q1：Vue3 的依赖收集，是指收集 render、effect 吗？

**回答**：含糊地把 render 和 effect 并列当作收集对象。

**纠正**：

- 收集的是**当前活跃的副作用函数（ReactiveEffect 实例 / `activeEffect`）**，render 只是创建 effect 的一种场景
- 存储结构 `targetMap = WeakMap<target, Map<key, Set<effect>>>`
- render / watch / computed 都是 effect 来源：render 包成渲染 effect、watch 带 scheduler、computed 双重身份
- 追问点：收集时机是 effect 执行中触发 get 时（运行时动态），每次重跑前 cleanupEffect 清旧依赖

**评分**：6/10 — 大方向知道，但核心概念（收集的是 effect 而非 render）说反了层级。

## Q2：编译优化 → block tree → diff 的链路描述

**回答**：「compiler 编译模板时通过 patchFlag 打标，静态节点静态提升，预字符串缓存和事件缓存，生成 block tree，runtime 时结合 diff 遍历 block tree 完成渲染」。

**纠正**（4 处）：

1. 「预字符串缓存」术语错误 → **静态节点预字符串化**（stringifyStatic），与事件缓存是两个独立优化
2. block tree **不是编译器生成的** — 编译器只在 render 代码里埋 `openBlock` 标记，block tree 是 runtime 执行时构建
3. 「diff 遍历 block tree」说反了 — block tree 的意义是**跳过静态子树**，只 diff `dynamicChildren`
4. 补充 patchFlag 靶向更新：TEXT 只改文本、CLASS 只改 class

**评分**：7/10 — 优化点都数出来了，但编译期/运行时的边界没分清，block tree 的构建时机和作用是典型追问陷阱。

## Q3：effect 触发后，基于 compiler 结果对比新旧 vnode 完成更新？

**纠正**（2 处）：

1. 「基于 compiler 的结果」表述错误 — **编译一次，执行多次**，重渲染执行的是同一份编译产物 render 函数
2. 更新粒度是**组件级**不是页面级 — 这也是 Vue3 不需要 memo 的原因
3. 补充调度细节：effect 进微任务队列（queueJob），同步多次改数据只重渲染一次 → nextTick 的原理

**评分**：7/10 — 主链路对，但编译/运行的职责边界和更新粒度这两个加分点没说出来。

---

## Q4：block tree 是 Fragment、以组件为最小颗粒度吗？v-if/v-for 是嵌套独立 block tree 吗？

**回答**：「render 生成的 blockTree 是 fragment，以组件为最小颗粒度；dynamicChildren 是扁平化动态节点数组，v-if/v-for 在数组中再来独立 block tree」。

**纠正**（2 处 + 1 处确认）：

1. **Block ≠ Fragment** — block 是"角色"不是 vnode 类型：组件 render 根是普通元素充当 block；只有多根模板、v-for、v-if 分支才由 Fragment 充当 block
2. **颗粒度不是组件** — 混淆了两层：重渲染颗粒度是组件级（响应式层决定）；block 嵌套颗粒度在组件模板内部，由结构指令驱动，与组件边界无关
3. ✅ 嵌套结构说对了 — dynamicChildren 存动态叶子节点 + 嵌套子 block；v-if 每分支独立成 block（切换时整块卸载/挂载，不做跨分支 diff），v-for 是 KEYED_FRAGMENT 子 block（key + 最长递增子序列 diff）

**评分**：7/10 — 嵌套递归的直觉对，但 block 的本质和颗粒度归属说错了。

## Q5：渲染 effect 触发 → render 执行产出 block tree，"这时候 block 就是组件"，对比新旧 vnode 更新？

**纠正**（2 处）：

1. **「block 就是组件」概念混淆** — 组件是 component vnode + 实例（props/setup/生命周期），block 是组件 render 产物的根节点；关系是 `instance.subTree = block tree`。实际意义：父 block diff 到动态子组件走组件级更新（props 变了才重渲染子组件），diff 到普通元素 block 才是递归 dynamicChildren
2. **「某个 effect」不精确** — 组件上挂着渲染 effect、watch、computed 多个 effect，只有渲染 effect 触发才重渲染

**评分**：7/10 — 链路顺了，但「block = 组件」是同源概念混淆（和 Q4 的颗粒度混淆是同一个根：没分清组件边界和渲染产物边界）。

## Q6（讲解）：shouldUpdateComponent —— 父重渲染时子组件一定跟着重渲染吗？

应德德要求展开讲解，要点：

- 父 diff 到子组件 vnode → `updateComponent`：**实例复用**（`n2.component = n1.component`），从不重建
- `shouldUpdateComponent` 闸门：指令/transition → 更新；动态 slot（`DYNAMIC_SLOTS`）→ 更新；`FULL_PROPS` → 全量浅比较；最常见 `PROPS` → **只比 `dynamicProps` 里的 key**（编译优化的又一体现），emits 排除
- 子组件更新**两条路径**：A 父触发（闸门）+ B 自己依赖收集触发（props 是响应式的），调度器 Set 去重
- 反向坑：父传响应式对象只改深层属性 → 浅比较引用不变路径 A 关闭，但路径 B 照样触发子更新
- 结论：这是 Vue3 不需要 memo 的核心原因之一

详见 [Vue3渲染机制全链路.md](../Vue3渲染机制全链路.md) 第五节。

## Q7：diff 除了增删移还处理什么？新节点 render 生成、旧节点从内存取，对吧？

**回答**：「diff 比对新旧节点确认新增/删除/移动；新节点 render 生成，旧节点从内存取」。

**确认 + 补充**：

- ✅ 新旧来源说对了，精确化：旧树 = `instance.subTree`（上次 render 产物的对象引用），vnode 上挂 `el` 指向真实 DOM；首次挂载 `n1 = null` 不走 diff
- 盲区：diff 职责不止增删移——同节点判定（type+key 分流）、DOM/实例复用、patchFlag 靶向更新、组件闸门、卸载/挂载副作用（生命周期/指令/ref/事件/transition）、LIS 最小化移动、静态节点跳过
- 核心句：**diff 的目标是"最少 DOM 操作"，增删移只是 children 对比的三个分支，复用与靶向更新才是大头**
