## 第九轮：HTML/CSS/JS 基础

### Q1：for + var + setTimeout 循环输出？如何修复？

**德德的回答：** 输出都是 5，因为 var 不是块级作用域，循环里放进去的 i 都是同一个；改成 let 就行。

**评分：⭐⭐⭐**

**评价与纠正：**
- 结论对，但表述不精确：不是"i 都是同一个值"，而是 **var 声明的 i 是同一个变量（同一份内存绑定）**，所有回调共享引用，循环结束后 i=5。
- `let` 修复：`for (let i)` 每轮迭代创建**新的词法环境与新的 i 绑定**（新绑定继承上一轮值并执行 i++），回调闭包各捕获各的绑定。
- ❌ 严重错误：提出"var 保留时用 async/await，for 会等待异步结束再进下一轮"。**for 循环永远不会自动等待异步**，除非循环体内显式 `await` 一个 Promise。原题结构加 async/await 输出仍是 5 个 5；即使 `await sleep` 串行能输出 0-4，那也是改变执行时序，不是修复闭包捕获。
- `var` 保留时的正解：**IIFE**（每轮立即调用，形参 j 独立绑定）或 **bind 预置参数**（`fn.bind(null, i)` 把当前 i 的值快照进新函数参数列表）。
- bind 易混淆点：`bind(null, i)` 的核心是**预置参数（partial application）**，`null` 只是占位 this，回调里根本不用 this。

**盲区：** var/let 的"绑定"机制；IIFE/bind 修复原理；async/await 不改变循环语义。

### Q2：宏任务/微任务输出题 + setTimeout(0) 执行时机

```js
console.log('script start');
setTimeout(() => console.log('setTimeout'), 0);
Promise.resolve().then(() => console.log('promise1'))
  .then(() => console.log('promise2'));
console.log('script end');
```

**德德的回答：** script start、script end、promise1、setTimeout、promise2（错，promise2 应在 setTimeout 前）。setTimeout 放入宏任务队列，等当前宏任务队列开始执行才处理（表述不准）。

**评分：⭐⭐⭐**

**评价与纠正：**
- 正确顺序：`script start → script end → promise1 → promise2 → setTimeout`。
- 微任务队列在**当前宏任务结束后一次性清空**，处理每个微任务时新产生的微任务继续入队尾，直到队列为空才取下一个宏任务。promise2 是微任务，不可能被 setTimeout 插队。
- `setTimeout(fn, 0)` 不是 0ms：① 单线程下最早也是下一个宏任务（当前宏任务 + 微任务清空后）；② 浏览器有最小延迟钳制：嵌套第 5 层及以上最小 4ms，后台标签页最小 1000ms。
- 术语：定时器**从调用 setTimeout 时开始计时**，到点后回调**入队**而不是立即执行。

**盲区：** 微任务队列连续清空机制；setTimeout 最小延迟（嵌套 4ms / 后台 1s）。

### Q3：CSS 水平垂直居中的所有方案

**德德的回答：** ① flex + justify-content/align-items center；② absolute 四边设 0 + transform -50%；③ padding 设置。

**评分：⭐⭐**

**评价与纠正：**
- flex ✅。
- ② 把两套方案混了：**transform 版**是 `top: 50%; left: 50%; transform: translate(-50%, -50%)`（不需要 right/bottom，不要求知道子元素宽高，但会生成层叠上下文）；**auto margin 版**是 `top/right/bottom/left: 0 + margin: auto`（必须知道子元素宽高，让元素在拉伸区域内自动居中）。两者不能混用。
- ③ padding 不是通用居中方案：只在父容器、子元素尺寸都固定且不变时手动计算间距，一变即失效。
- 补充方案：grid `place-items: center`（注意 place-items 与 place-content 的区别）；固定宽度 + `margin: 0 auto`（只水平居中，垂直在普通流无效）；table-cell + vertical-align；单行文本 line-height = 容器高度（换行失效）。

**盲区：** 两套 absolute 居中机制的区别；margin: auto 水平有效/垂直无效；padding 的前提条件。

### Q4：HTML 语义化 + doctype / 标准模式与怪异模式

**德德的回答：** 语义化是 video/header/container/img/text 这些标签能表达功能；SEO 会筛选聚焦这些标签。无障碍、可维护性、doctype 不会，要求讲解。

**评分：⭐⭐**

**评价与纠正：**
- ❌ `<container>` 和 `<text>` **不是标准 HTML 标签**（`<text>` 只在 SVG 中存在）。正确例子：`<header> <nav> <main> <article> <section> <aside> <footer> <h1-h6> <ul/ol> <p>`。
- SEO 表述要精确：爬虫解析标签结构，理解正文/导航/标题层级，据此提取关键词评估页面，不是"筛选聚焦"。
- 语义化收益：SEO、无障碍（屏幕阅读器按文档大纲导航）、可维护性（自描述结构，CSS/JS 可挂靠语义标签）。
- `<!DOCTYPE html>`：告诉浏览器用**标准模式**渲染；缺失或写错进入**怪异模式（quirks mode）**，模拟 IE5 行为。
- 两种模式核心区别：① **盒模型**（怪异模式 width 包含 padding/border，等价全局 border-box；标准模式默认 content-box）；② 行高与行内元素垂直布局；③ 表格/百分比布局计算。

**盲区：** 标准 HTML 标签集合；doctype 与怪异模式（尤其盒模型差异）。

### Q5：async/await 输出题 + await 语义

```js
async function async1() {
  console.log('async1 start');
  await async2();
  console.log('async1 end');
}
async function async2() { console.log('async2'); }
console.log('script start');
async1();
console.log('script end');
```

**德德的回答：** 第一次顺序错（把 async2 放在 script end 后）；提示后修正为 script start → async1 start → async2 → script end → async1 end。await 理解为"把后面的函数用 Promise 包装，普通函数同步执行、fetch 等待"。

**评分：⭐⭐⭐**

**评价与纠正：**
- 关键机制：**async 函数体同步执行到第一个 await**，调用 async2() 时函数体立即同步执行，所以 async2 在 script end 之前。
- await 三处纠正：① 不是"包装后面的函数"，而是先同步求值拿到结果，后面不是 Promise 时才 `Promise.resolve()` 包装；② 后面是普通值也会把后续代码变成微任务，"普通函数同步、fetch 等待"的二分法是错的；③ 执行到 await 时 async1 立即返回让出执行权，后续代码注册为微任务，等被 await 的 Promise resolve 后、当前宏任务结束时恢复执行。

**盲区：** async 函数体同步执行语义；await 的精确转换（后续代码 = .then 回调微任务）。

### Q6：Promise.all 并发请求与错误处理

**德德的回答：** Promise.all 并发三个请求，等全部结束返回，耗时取最长；一个失败立即结束，成功的拿不到了。改成 allSettled，无论成功失败都返回。

**评分：⭐⭐⭐⭐**

**评价与纠正：**
- 基本对。补充：失败时**立即 reject、不等最慢**；其他请求**不会被取消**（fetch 默认不可取消，需 AbortController），只是结果被丢弃。
- allSettled 细节：永远等全部结束、不 reject；每项 `{ status: 'fulfilled', value }` 或 `{ status: 'rejected', reason }`；结果顺序与入参一致。
- 不用 allSettled 的思路（反射模式）：每个 Promise 手动 `.catch(() => ({ ok: false }))` 兜底，让 Promise.all 永不提前失败，再按标记渲染。

**盲区：** Promise.all 立即 reject 与请求不取消；反射模式。

### Q7：防抖/节流区别、闭包保存什么、this 的坑

**德德的回答：** 防抖解决重复点击，触发就重置计时器（表单重复提交）；节流控制触发次数（拖拽 resize）；闭包保存函数执行上下文，全局变量会被污染；setTimeout 普通函数 this 指向不明确，提前保存 this。

**评分：⭐⭐⭐**

**评价与纠正：**
- 防抖精确定义：连续触发不断重置计时器，**只有最后一次触发后等待 N 毫秒才执行**（输入联想、resize 停止后计算）。节流：**固定时间窗口内最多执行一次**（滚动、拖拽），不要说成"等这一次触发完再下一次"。
- ❌ 闭包保存的不是"上下文"（JS 中上下文专指 this/执行上下文）：防抖闭包保存 **timer 状态变量**，节流保存上次执行时间，每次调用工厂函数生成独立状态。
- 为什么不用全局变量：多个实例（如两个输入框）会**共享同一个 timer 互相干扰**，且全局状态可被任意代码修改；闭包把状态锁在私有作用域。
- this 的坑：setTimeout 普通回调非严格模式 this 指向 window、严格模式 undefined；修复用箭头函数（捕获词法 this）或提前 `const self = this`；实现时要用 `fn.apply(this, args)` 透传 this 和参数。

**盲区：** 防抖/节流一句话精确定义；闭包保存的是状态变量而非"上下文"；this 透传。
