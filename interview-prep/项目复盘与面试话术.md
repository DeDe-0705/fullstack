# 项目复盘与面试话术

> 项目经历是决定面试成败的关键。不是你做了什么，而是**你怎么讲**。本文基于你的真实项目经历，每个项目都准备了结构化的面试话术。

---

## 一、STAR 法则：面试回答的标准框架

```
S (Situation)   — 背景：业务场景是什么，遇到了什么问题
T (Task)        — 任务：你的角色和职责是什么
A (Action)      — 行动：你做了哪些具体的技术决策和实现
R (Result)      — 结果：带来了什么收益（量化最好）

❌ 差："我做了微前端，用无界搭的"
✅ 好："公司有4个业务域（人事/组织/薪酬/文化），各自有不同的迭代节奏...
       我主导了微前端架构选型，对比了 qiankun 和无界后选了无界...
       结果是子应用独立部署，发布互相不再阻塞，团队研发效率提升 30%"
```

## 二、Li People 门户（微前端架构）— 核心项目

### 2.1 浓缩版话术（1-2 分钟）

> "Li People 是公司职能 OA 平台，面向 HRBP、ER、OD 等角色，集成人事、组织管理等模块。背景是多个业务模块之前耦合在一个代码库里，不同团队发布互相阻塞。
>
> 我的角色是**项目 Owner + 架构设计**。我主导了微前端架构落地，选型**无界 wujie**（而非 qiankun），因为 iframe 天然 JS/CSS 隔离比沙箱方案更可靠，且子应用几乎零改造成本。
>
> 技术上解决了四个核心问题：
> 1. **鉴权**：主应用通过 Props 注入 token，子应用无感接入；菜单权限通过编码控制，不同角色看到不同模块入口。
> 2. **路由**：利用无界的路由劫持，子应用 pushState 同步到主应用 URL，刷新时自动恢复。
> 3. **通信**：Props 做配置下发（单向），Bus 做跨应用事件通知，避免子应用之间直接耦合。
> 4. **性能**：CDN + contenthash 强缓存、公共依赖抽离、预加载高频子应用、保活机制。
>
> 结果是各业务模块独立开发、独立部署，发布不再互相阻塞。同时封装了门户登录 SDK 和通用业务组件库，发布为 NPM 包，减少了团队重复开发。"

### 2.2 面试官可能会追问的点

**Q: 为什么不直接用 iframe，而用无界？**

"纯 iframe 有几个痛点：弹窗/遮罩只覆盖 iframe 区域、路由不同步浏览器 URL、DOM 不在同一棵树导致通信困难。无界用 iframe 做隔离容器，但通过 proxy 劫持了弹窗挂载到主应用、劫持了 pushState 同步路由、提供了 DOM 劫持方案和 Bus 通信——相当于解决了纯 iframe 的所有工程问题。"

**Q: 微前端有什么坑？**

"1. 子应用样式加载时序问题——CDN 资源偶尔加载慢导致样式闪烁，解决方案是主应用预加载关键子应用。2. 多实例冲突——同一个子应用切换 Tab 时不应该重新初始化，我们用保活(alive)机制解决。3. 调试困难——子应用在 iframe 中，需要配置 sourcemap 和 CORS。"

**Q: 为什么不选 qiankun？**

"qiankun 的沙箱是 JS 层面的（Proxy 或快照），不是真正的物理隔离。快照沙箱在遍历 window 属性时有性能开销。而且 qiankun 要求子应用暴露 bootstrap/mount/unmount 生命周期，对存量系统侵入性大。无界的 iframe 方案隔离更彻底，接入也更简单。"

## 三、理想同事（Agent + 多端 H5）— 亮点项目

### 3.1 浓缩版话术

> "理想同事是一个集成行政/财经/IT/人力的**多领域 Agent 问答 H5 应用**。员工可以在里面让 AI 帮忙请假、销假，运营人员可以分析对话数据优化场景。
>
> 技术上我做了三件事：
> 1. **动态组件架构**：业务表单抽成独立组件库，Rollup 打包后上传 CDN 按需加载。组件可以独立迭代发布，不用主应用发版。通过版本隔离保障历史消息正常渲染。
> 2. **跨应用嵌入通信**：支持 iframe 嵌入业务系统，用 postMessage 实现双向通信，同步上下文让 AI 感知业务场景（比如在考勤页打开就直接问考勤相关问题）。
> 3. **多端流式能力封装**：统一封装了流式响应处理方法（实时输出、请求重试、异常兜底），一套方案兼容 PC 和移动端。"

### 3.2 面试官可能会追问

**Q: 组件的版本隔离怎么做的？**

"组件库发布时每个版本对应独立的 CDN 目录（如 /components/1.0.0/、/components/1.1.0/）。对话消息中记录组件渲染时的版本号。打开历史消息时，主应用根据记录中的版本号加载对应版本的组件，即使组件已经迭代到新版本，历史消息也能正常渲染。"

**Q: 流式响应怎么做断线重连？**

"在流式请求中记录最后接收到的 token 偏移量。断线后重新发起请求，带上 `lastTokenIndex` 参数，服务端从该位置继续推送。前端做增量渲染，用户可以无缝看到续推的内容。"

## 四、组织信息管理平台（PC + 飞书小程序双端）— 多端项目

### 4.1 浓缩版话术

> "组织信息管理平台是公司的组织数字化基座，支撑全员查询个人信息和团队分析，同时覆盖 PC 端（Vue3）和飞书小程序（Taro）两个场景。
>
> PC 端我做了基于 Ant G6 的组织架构图，实现了数据懒加载（只渲染可视节点）、人员搜索定位、多层级的点击交互。同时抽离了人员详情和组织详情两个通用业务组件，支持双向无限下钻联动（人员→组织、组织→人员），结合权限管控数据可见范围。
>
> 小程序端我搭建了 Taro + Vue 的工程体系，对 NutUI 做了二次封装统一 UI 规范。核心挑战是 PC 和小程序共享业务逻辑但 UI 不同，我们通过逻辑层抽离 + 适配层分别实现来解决。"

### 4.2 面试官可能会追问

**Q: Ant G6 组织架构图怎么处理大组织？**

"数据懒加载：初始只加载顶层节点。点击展开时动态请求子节点。可视区域外的节点不渲染，减少 DOM 数量。关键是合理控制节点展开层级——默认展开 2 层，再深的需要手动展开。"

**Q: PC 和小程序的代码复用怎么做的？**

"业务逻辑（API 请求、数据处理、状态管理）抽离到独立的 logic 层，PC 和 小程序共享。UI 组件各自实现，通过适配层桥接。Taro 的 Vue 语法和标准 Vue 差异不大，主要的适配工作在路由和生命周期上。"

## 五、出入预约后台管理 — AI 驱动研发项目

### 5.1 浓缩版话术

> "这个项目比较特别——我是**项目 Owner，但采用了 AI 驱动的研发模式**。
>
> 我基于 Claude Code 搭建了一套研发环境：通过 Skill 文件约束前端 Vue3、权限 SDK、组件库的接入规则；通过系统提示词规范后端 JDK、Spring Boot 基线版本。同时搭建了 Sub-Agent 协同方案——前端代码生成后自动唤起测试 Agent 校验，后端接口完成后自动调用 Agent 同步生成前端接口代码和 TS 类型定义。
>
> 测试环节用 chrome-devtools-mcp 和 Playwright MCP 完成页面功能核验，通过飞书拉取需求文档。我聚焦在环境配置、部署、投产质量把控上。
>
> 结果是一套完整的出入预约业务流程——包括预约单管理、状态流转、车辆签到签退——高效落地。"

### 5.2 面试官可能会追问

**Q: AI 编码的质量怎么保证？**

"三个层面：1) 输入层面，通过 Skill 文件规范了技术栈、代码风格、组件库用法，减少 AI 的自由发挥空间。2) 校验层面，Sub-Agent 自动检查编码规范、类型正确性、边界情况。3) 测试层面，用 Playwright MCP 做 E2E 流程验证，覆盖正常流程和异常分支。"

## 六、通用系统设计题

### 6.1 设计一个前端监控系统

```
面试思路框架：

1. 数据采集层
   - 错误监控：window.onerror + unhandledrejection + 资源加载错误
   - 性能监控：Performance API (FP/FCP/LCP/FID/CLS)
   - 接口监控：拦截 XMLHttpRequest/fetch，记录耗时和状态码
   - 行为监控：PV/UV、停留时长、点击热力图

2. 数据上报层
   - navigator.sendBeacon（页面卸载时可靠上报）
   - 采样率控制（错误 100%，性能 10%，行为 1%）
   - 数据压缩和合并上报

3. 数据处理层
   - SourceMap 解析（定位源码位置）
   - 错误聚合（相同错误合并去重）
   - 数据清洗和入库

4. 可视化层
   - 错误大盘（错误率、影响用户数、趋势图）
   - 性能大盘（Core Web Vitals 趋势）
   - 告警规则（错误率突增、接口超时率 > 阈值）
```

### 6.2 设计一个组件库

```
1. 技术选型
   - 构建：Vite/Rollup，输出 ESM + CJS
   - 文档：Storybook 或 VitePress
   - 测试：Vitest + Testing Library

2. 开发规范
   - Props 类型定义 + JSDoc 注释
   - CSS Variables 主题化
   - 组件 API 设计（受控/非受控、插槽）

3. 质量保障
   - 单元测试覆盖核心逻辑
   - 视觉回归测试
   - 无障碍检查

4. 发布流程
   - changesets 管理版本
   - CI 自动构建 + npm publish
   - CHANGELOG 自动生成
```

## 七、面试准备清单

```
项目面试前建议准备：

□ 每个项目能 30 秒讲清楚（电梯演讲版）
□ 每个项目能 2 分钟深入讲（技术版）
□ 准备 3-5 个"难点/坑"的故事
□ 准备 2-3 个"如果重来一次会怎么做"的反思
□ 每个技术决策能说清楚"为什么选 A 不选 B"
□ 能量化结果的地方都量化（提升了 XX%、减少了 XX 天）
□ 准备好"你最大的技术挑战"这个通用问题
□ 准备好"你在这个项目中的角色边界"（哪些是你做的，哪些是团队做的）
```
