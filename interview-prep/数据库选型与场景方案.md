# 数据库选型与场景方案

> 面向「哪些场景选哪些方案」：数据库全景分类 + 选型决策框架 + 典型架构组合。解决面试高频题「你们项目为什么用 MySQL / Redis / ES」。

---

## 一、数据库全景分类

一句话速记：**结构化的业务数据用关系型；高频读用 Redis；要搜用 ES；要分析用 ClickHouse；AI 语义检索用向量库。**

| 类型 | 代表 | 解决什么问题 | 典型场景 | 面试关键词 |
|---|---|---|---|---|
| 关系型（SQL） | MySQL / PostgreSQL | 结构化数据 + 强事务 + 复杂关联 | 订单、用户、账户、库存 | ACID、JOIN、事务 |
| KV 缓存 | Redis | 超高频读写、扛并发 | 缓存热点、会话、计数、分布式锁 | 缓存穿透/雪崩/击穿 |
| 文档型 | MongoDB | schema 多变、嵌套结构 | 商品详情、日志、内容 | BSON、灵活 schema |
| 搜索引擎 | Elasticsearch | 全文检索、聚合分析 | 商品/帖子搜索、日志检索 | 倒排索引、分词 |
| 列式分析 | ClickHouse | 海量数据 OLAP 分析 | 报表、BI、埋点分析 | 列式存储、向量化 |
| 时序 | InfluxDB / TDengine | 时间序列数据 | 监控、IoT、传感器 | 时序压缩、降采样 |
| 图 | Neo4j | 关系网络 | 社交关系、推荐、知识图谱 | 节点、边、遍历 |
| 向量 | Milvus / pgvector | 语义相似检索 | RAG、以图搜图 | Embedding、ANN |

## 二、选型决策的 5 个维度

面试被问「为什么选它」，别只答「因为快」，落到这几个维度：

1. **数据模型** —— 规整的表（关系型）？灵活文档（MongoDB）？key-value（Redis）？
2. **一致性要求** —— 强一致 + 事务（订单/支付 → MySQL/PG），还是能接受最终一致（缓存/日志 → Redis/Mongo）？
3. **读写模式** —— 读多写少？写多？点查（主键）？范围？全文搜索？聚合分析？
4. **查询模式** —— 多表 JOIN（关系型）？文档内嵌一次取全（MongoDB）？搜索召回（ES）？
5. **扩展性** —— 垂直加机器够不够，还是要水平分片？

## 三、典型架构组合

互联网典型电商/内容系统的存储不是单点，而是组合拳：

```
MySQL（主从）  →  存业务数据，保事务一致
   ＋ Redis     →  缓存热点，扛并发、削峰
   ＋ ES        →  商品/内容搜索
   ＋（可选）ClickHouse →  埋点/报表分析
   ＋（可选）消息队列   →  解耦、异步
```

面试话术落点：**「MySQL 保证一致性，Redis 保证性能，ES 保证搜索体验」**——三句话讲清「为什么组合」，比背特性加分。

## 四、面试速答话术

**Q：你们项目为什么用 MySQL 而不是 PostgreSQL / MongoDB？**

先看数据模型和一致性要求：业务是订单、用户这类强结构化、强事务的数据，优先关系型；MySQL 生态成熟、运维资料多，团队熟悉。需要复杂 JSON、地理、全文等高级特性时再考虑 PostgreSQL。

**Q：为什么还要引入 Redis / ES，不用 MySQL 一把梭？**

MySQL 强一致但单机性能有限；Redis 内存 KV 扛高并发读、削峰；ES 倒排索引解决全文搜索（MySQL LIKE 无法索引、性能差）。各司其职，避免单点瓶颈。
