## 一、构建工具原理

### 1.1 Webpack 核心流程

```
Webpack 构建分为三个阶段：

1. 初始化 → 合并配置、初始化 Compiler、加载插件
2. 编译   → 从 Entry 出发，递归构建依赖图
3. 输出   → 根据依赖图生成 chunk，输出到文件系统
```

**构建管线：**

```
Entry → Resolve(解析路径) → Loader(转换) → Parse(AST) → 
Gather Dependencies(收集依赖) → 递归处理依赖 → 
Module Graph → Chunk → Template → Emit(输出文件)
```

### 1.2 Loader vs Plugin

```
Loader：文件级转换器
  - 本质是一个函数，接收源码返回转换后的代码
  - 单一职责，链式调用（从右到左）
  - 例：css-loader 解析 CSS，style-loader 注入 DOM

Plugin：构建流程级扩展
  - 基于 Tapable 事件机制
  - 可以访问 Compiler/Compilation 对象
  - 能在整个构建生命周期中插入逻辑
  - 例：HtmlWebpackPlugin、MiniCssExtractPlugin
```

**手写一个简单的 Loader：**

```js
// my-loader.js
module.exports = function(source) {
  // source 是文件的原始内容
  return source.replace(/console\.log\(/g, '// console.log(')
}
```

**手写一个简单的 Plugin：**

```js
class MyPlugin {
  apply(compiler) {
    // 在 emit 阶段（输出前）注入逻辑
    compiler.hooks.emit.tapAsync('MyPlugin', (compilation, callback) => {
      // compilation.assets 包含所有输出文件
      for (let filename in compilation.assets) {
        if (filename.endsWith('.js')) {
          const content = compilation.assets[filename].source()
          // 在最前面加上 banner
          compilation.assets[filename] = {
            source: () => `/* built at ${new Date()} */\n${content}`,
            size: () => content.length
          }
        }
      }
      callback()
    })
  }
}
```

### 1.3 Webpack HMR 原理

```
HMR（Hot Module Replacement）完整链路：

1. Webpack Dev Server 与浏览器建立 WebSocket 连接
2. 文件变化 → Webpack 重新编译 → 生成 hash.hot-update.json + hash.hot-update.js
3. Server 通过 WebSocket 推送 hash 给浏览器
4. HMR runtime 发起 JSONP 请求获取更新模块代码
5. 模块热替换：
   a. 旧模块执行 dispose 回调
   b. 新模块代码执行
   c. 沿模块依赖链向上通知 accept 回调
```

### 1.4 Tree Shaking

```
Tree Shaking 的先决条件：
1. ES Module 语法（import/export），CommonJS 不行
2. package.json 声明 sideEffects: false
3. 生产模式（mode: 'production'）

原理：
  - 利用 ES Module 的静态结构做依赖分析
  - 标记未使用的导出（usedExports），Terser 压缩时删除
  - sideEffects: false 告诉 Webpack"所有模块都无副作用，尽管摇"

sideEffects 配置示例：
{
  "sideEffects": [
    "*.css",      // CSS 文件有副作用（样式注入），不能摇
    "*.scss",
    "./src/polyfill.js"
  ]
}
```

### 1.5 Webpack 常用优化

```
1. 缩小搜索范围
   resolve: {
     extensions: ['.js', '.ts', '.tsx'],  // 尽可能少
     alias: { '@': path.resolve('src') }
   }
   module.rules 中用 include/exclude 限制 loader 范围

2. 代码分割（Code Splitting）
   splitChunks: {
     chunks: 'all',
     cacheGroups: {
       vendor: { test: /node_modules/, name: 'vendor' }
     }
   }

3. 持久化缓存
   cache: { type: 'filesystem' }  // Webpack 5

4. 并行构建
   thread-loader（多进程加载）
   terser-webpack-plugin 的 parallel 选项

5. 外部化（externals）
   将 React/Vue 等从 CDN 加载，不打包进去
```

### 1.6 Vite 原理

```
Vite 的核心理念：开发时不打包

开发环境：
  1. 浏览器请求 → Vite Dev Server
  2. 按需编译 ESM 模块
  3. esbuild 做预构建（将 CommonJS 转 ESM，合并小模块）
  4. 热更新极快（只失效改动的模块链）

生产环境：
  Rollup 打包（因为生产不需要按需加载几百个 ESM 模块）

快在哪？
  - 跳过打包步骤（不用递归构建依赖图）
  - esbuild 是 Go 写的，比 JS 快 10-100 倍
  - 按需编译，只处理浏览器请求的模块
  - HMR 粒度精确到模块，不受应用大小影响
```

### 1.7 Webpack vs Vite 对比

| 维度 | Webpack | Vite |
|------|---------|------|
| 开发启动 | 全量打包，慢 | 按需编译，秒启动 |
| 热更新 | 随应用变大而变慢 | 不受应用大小影响 |
| 生态 | 极丰富 | 兼容 Rollup 插件，增长中 |
| 生产构建 | Webpack | Rollup |
| 浏览器要求 | 无限制 | 需要支持 ESM |
| 适用场景 | 复杂大型项目 | 新项目优先推荐 |

## 二、模块化

### 2.1 CommonJS vs ESM

| 维度 | CommonJS | ES Module |
|------|----------|-----------|
| 加载方式 | 运行时同步加载 | 编译时静态分析 + 运行时异步加载 |
| 导出 | `module.exports` | `export` |
| 导入 | `require()` | `import` |
| 值的绑定 | 值的拷贝 | 值的只读引用（live binding） |
| 循环引用 | 返回未完成副本 | 能正确处理（动态绑定） |
| Tree Shaking | 不支持 | 支持 |

```
CommonJS 循环引用示例：
// a.js: exports.done = false; const b = require('./b'); ...
// b.js: const a = require('./a'); console.log(a.done); // false（未完成的副本）

ESM 循环引用：
// 因为 import 是 live binding，即使循环引用，export 的值也会被更新
```

### 2.2 为什么 Tree Shaking 必须用 ESM？

```js
// CommonJS：导出是动态的，无法静态分析
module.exports = { a: 1 }     // 运行时才知道导出什么
if (condition) { module.exports.b = 2 }  // 条件导出，无法静态分析

// ESM：导出是静态声明的
export const a = 1            // 编译时就能确定
export { a, b, c }             // 静态结构，可分析哪些被使用
```

#### 3.3.2 版本号怎么决定？— Conventional Commits + Git Tag

```
commit message 规范（Conventional Commits）：

fix: 修复员工详情组件头像加载失败       → patch (1.2.3 → 1.2.4)
feat: 新增人员批量导入组件               → minor (1.2.3 → 1.3.0)
feat!: 重构组件 Props 类型，移除废弃字段   → major (1.2.3 → 2.0.0)
                                            (BREAKING CHANGE / !)

CI 中自动读取 commit message：
  - 只有 fix / feat 类型的 commit 触发生成新版本
  - chore / docs / refactor 不触发生成版本（不发布）
  - 多个 commit 取最高版本变化（feat + fix = minor）
```

#### 3.3.3 Git Tag 的作用——为什么不能只靠 package.json 的版本号？

```
package.json 的 version 字段：
  "version": "1.2.3"
  → 这是当前代码声明的版本号，但它是动态的——随时会被 commit 修改

Git Tag：
  git tag v1.2.3
  → 这是一个不可变的时间锚点，指向特定 commit 的 SHA

Tag 的核心价值：

1. 可追溯
   线上出 Bug → git checkout v1.2.3 → 一秒回到发布时的代码
   不需要凭记忆搜索"上周三下午那次构建的 commit"

2. 可对比
   git diff v1.2.2..v1.2.3 -- components/
   → 精确看到 v1.2.3 相比上个版本变了哪些组件

3. 可回滚
   新版本出问题 → 消费方直接改依赖版本号回退到旧 Tag
   "app-hr": "1.2.2"  ← 锁定 Tag 对应版本

4. 版本号唯一锚点
   npm 上的包 / CDN 上的文件 / Git 里的代码 → 三者靠 Tag 对齐
   Tag v1.2.3 = NPM v1.2.3 = CDN /components/1.2.3/
```

#### 3.3.4 Git Tag 操作细节——手动 vs CI 自动

> 面试追问："git tag 一般就两步吗？"——核心对，但有三个加分细节。

##### 手动操作（本地发布场景）

```bash
# 1. 打附注标签（-a 带元信息：作者/日期/说明，发布必须用这个）
git tag -a v1.2.3 -m "feat: 新增 Table 虚拟滚动"

# 2. 推送标签到远端
git push origin v1.2.3    # ✅ 推单个标签（推荐，避免误推）
git push --tags           # ⚠️ 推所有本地标签，可能把测试标签误推上去
```

##### 轻量标签 vs 附注标签

```bash
git tag v1.2.3                    # 轻量标签 = 只是个 commit 指针，无元信息
git tag -a v1.2.3 -m "发布说明"   # 附注标签 = 有作者/日期/message

# 附注标签存储了"谁、什么时候、为什么"打的标签
# 发布场景一律用 -a，面试要说出区别
```

##### push 方式对比

```bash
git push --tags              # 推所有本地标签 → 团队协作时容易误推
git push origin v1.2.3       # 只推指定标签 → 更安全
git push --follow-tags       # 推代码的同时只推附注标签（不推轻量标签）
                             # CI 自动化场景用这个
```

##### CI 自动化场景（实际项目里的做法）

```bash
# changesets / semantic-release 内部自动完成：
git tag v1.2.3               # 自动根据 bump 后的版本号打标签
git push --follow-tags       # 推代码 + 关联的附注标签一起推

# 开发者只需要按 Conventional Commits 写 commit message
# 版本号 bump、打标签、推送全是流水线自动处理
```

##### 删除标签（打错了怎么办）

```bash
git tag -d v1.2.3                     # 删本地标签
git push origin :refs/tags/v1.2.3     # 删远端标签
```

##### 面试话术

> "手动打标签核心两步：`git tag -a v1.2.3 -m 'xxx'` 打附注标签，`git push origin v1.2.3` 推送。但实际项目里这两步是 CI 自动完成的——开发者只需按 Conventional Commits 规范写 commit，版本号 bump、打标签、推送全部由流水线处理。附注标签和轻量标签的区别在于是否有元信息，发布必须用附注标签。"

#### 3.3.5 Tag vs Commit 的区别与运用场景

> 面试高频追问："tag 和 commit 有什么区别？"

##### 本质区别

```
Commit = 代码的一次快照（动态历史）
  - 每次提交生成一个，指向代码库某个时刻的状态
  - 有父子关系，形成一条链
  - 可以被 rebase / amend / reset 修改或移动

Tag = 某个 commit 的永久标签（静态锚点）
  - 指向某个特定 commit，不会随历史变化而移动
  - 没有父子关系，就是一个名字
  - 打上之后就不应该变

一句话：Commit 是"历史的节点"，Tag 是"给某个节点起的名字"。
```

##### 类比

```
Commit 像日记的每一页：
  - 每天写一篇（每次提交）
  - 按时间顺序排列（链表）
  - 可以撕掉重写（rebase/amend）

Tag 像书签：
  - 夹在某一天的那一页
  - 写上"发布 v1.2.3"
  - 书签本身不改变日记内容，只是标记位置
```

##### 运用场景对比

| 场景 | 用 Commit | 用 Tag |
|------|-----------|--------|
| 日常开发 | ✅ 每次改动提交 | ❌ |
| 代码审查 | ✅ PR 基于 commit diff | ❌ |
| 回滚到某个版本 | 可以，但要记 SHA | ✅ `git checkout v1.2.3` 更直观 |
| 发布版本 | ❌ | ✅ 标记发布点 |
| 对比两个版本 | 可以，但 SHA 难记 | ✅ `git diff v1.2.2..v1.2.3` |
| CI 触发构建 | ✅ push commit 触发 | ✅ push tag 触发发布流程 |

##### 为什么发布要用 Tag 不用 Commit SHA

```bash
# 用 SHA（能工作，但难记难读）
git checkout a1b2c3d4e5f6
npm publish  # 这个 SHA 对应的是哪个版本？

# 用 Tag（语义化，一目了然）
git checkout v1.2.3
npm publish  # 明确知道在发布 v1.2.3
```

**Tag 的核心价值：给无意义的 SHA 赋予语义化的名字。**

#### 3.3.6 Git Tag 常见问题

##### `git tag` 默认打在哪？

```bash
git tag v1.2.3
```

**打在本地当前 HEAD 指向的 commit**，和远程没关系。

```
场景1：本地和远程同步
  本地 HEAD = 远程最新 commit → tag 打在远程最新 commit 上 ✅

场景2：本地有未推送的 commit
  本地 HEAD = 本地最新 commit（远程还没有）
  → tag 打在本地最新 commit 上
  → push tag 时会把本地 commit + tag 一起推上去

场景3：本地落后远程
  本地 HEAD = 旧 commit（远程有新 commit）
  → tag 打在旧 commit 上 ❌ 不是你想要的
```

**正确姿势：先 `git pull` 确保本地最新，再打 tag。**

##### Tag 会重名吗？

**本地不允许重名：**

```bash
git tag v1.2.3
# fatal: tag 'v1.2.3' already exists

# 想覆盖？先删再建
git tag -d v1.2.3
git tag v1.2.3
```

**远程也可能有同名 tag：**

```bash
git push origin v1.2.3
# ! [rejected]  v1.2.3 -> v1.2.3 (already exists)

# 强制覆盖远程 tag（危险，团队协作要沟通）
git push origin v1.2.3 --force
```

##### `git push` 会默认带上 tag 吗？

**不会。`git push` 默认只推 commit，不推 tag。**

```bash
git push                  # 只推 commit，不推 tag ❌
git push --follow-tags    # 推 commit + 关联的附注 tag ✅
git push --tags           # 推 commit + 所有本地 tag（不管关联不关联）
```

**对比：**

| 命令 | 推 commit | 推 tag | 推哪些 tag |
|------|-----------|--------|-----------|
| `git push` | ✅ | ❌ | 无 |
| `git push --follow-tags` | ✅ | ✅ | 只推当前分支上 commit 关联的**附注标签** |
| `git push --tags` | ✅ | ✅ | 推**所有本地 tag**（包括轻量标签） |

**`--follow-tags` 的"关联"是什么意思：**

```
本地 commit 链：
  abc123 → def456 → ghi789 (HEAD)
              ↑
           v1.2.3 (tag)

git push --follow-tags：
  - 推 abc123 → def456 → ghi789 这些 commit
  - 同时推 v1.2.3 这个 tag（因为它指向当前分支上的 commit）

如果有个 tag 指向其他分支的 commit：
  xyz789 (其他分支)
    ↑
  v9.9.9 (tag)

git push --follow-tags：
  - 不会推 v9.9.9 ❌（不在当前分支上）
```

**实际场景：**

```bash
# 场景1：本地打了 tag，直接 push
git tag -a v1.2.3 -m "release"
git push
# 结果：commit 推上去了，tag 没推 ❌ 远程看不到 v1.2.3

# 场景2：用 --follow-tags
git tag -a v1.2.3 -m "release"
git push --follow-tags
# 结果：commit + v1.2.3 都推上去了 ✅

# 场景3：先 push 了 commit，忘了带 tag，补推
git push                          # commit 已推
git push origin v1.2.3            # 单独推 tag
```

#### 3.3.7 完整 CI 配置示例（GitHub Actions）

```yaml
# .github/workflows/release.yml
name: Component Library Release

on:
  push:
    branches: [main]

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0          # 拉全量 commit 历史（计算版本号需要）

      - uses: pnpm/action-setup@v2
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          registry-url: 'https://npm.your-company.com'

      - run: pnpm install --frozen-lockfile

      # 1. 质量门禁
      - run: pnpm lint
      - run: pnpm test
      - run: pnpm build

      # 2. 自动发版（changesets 方案）
      - name: Create Release PR or Publish
        uses: changesets/action@v1
        with:
          publish: pnpm release    # 执行 npm publish
          version: pnpm changeset version  # 自动 bump 版本号
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          NPM_TOKEN: ${{ secrets.NPM_TOKEN }}

      # 3. 上传 CDN（以腾讯 COS 为例）
      - name: Upload to CDN
        run: |
          VERSION=$(node -p "require('./package.json').version")
          cos-cli upload dist/ cos://your-bucket/components/$VERSION/

      # 4. 通知团队
      - name: Notify
        uses: actions/github-script@v7
        with:
          script: |
            const version = require('./package.json').version
            // 调飞书/企微 Webhook 发通知
            fetch('https://open.feishu.cn/...', {
              method: 'POST',
              body: JSON.stringify({
                msg_type: 'text',
                content: { text: `📦 @组件库 v${version} 已发布` }
              })
            })
```

#### 3.3.5 子应用怎么消费组件库版本？

```
你的 Li People 项目中的版本管理策略：

子应用 package.json：
{
  "dependencies": {
    "@li/people-ui": "1.2.3"       // 精确锁定版本
    // 不用 ^1.2.3（不自动升级，避免意外兼容性问题）
  }
}

组件库发布 → 子应用更新流程：
1. 组件库发布 v1.3.0，CI 通知群聊
2. 子应用开发者自主决定何时升级
3. 在子应用中：
   pnpm update @li/people-ui@1.3.0
   → 跑子应用的测试 → 确认兼容 → 合并 PR
4. CDN 上也按版本号存放：
   cdn.example.com/components/1.2.3/ → 旧版本继续服务
   cdn.example.com/components/1.3.0/ → 新版本
   (子应用不升级就不受影响，版本隔离)
```

#### 3.3.6 面试话术模板

> "在理想汽车我们建设了团队的业务组件库，CI/CD 流程是：PR 合并 main → Actions 自动 lint/test/build → changesets 根据 commit message 决定版本号 → 自动生成 CHANGELOG → npm publish → 构建产物上传 CDN（带版本号目录）→ 企微通知团队。发布时自动打 Git Tag，确保 npm 上的包、CDN 上的文件、Git 里的代码三者通过版本号对齐。子应用精确锁定依赖版本，组件库升级不影响未升级的子应用。"

#### 3.3.7 常见踩坑

| 坑 | 现象 | 解决 |
|----|------|------|
| Tag 和 npm 版本不一致 | Tag v1.2.3 但 npm 上是 1.2.2 | CI 里先打 Tag 再 publish，或反过来——关键是用同一个版本号来源 |
| CI 频繁触发无意义发版 | chore/docs commit 也触发了新版本 | changeset 只对 fix/feat 生成版本入口，其他类型不生成 |
| 多人同时合并导致版本冲突 | 两个 PR 都声称从 1.2.3 → 1.2.4 | changesets 在合并时自动处理冲突，或串行合并 |
| CDN 缓存导致子应用拿到旧版 | 发布了新版本但子应用仍用旧代码 | CDN 上按版本号分目录存放，URL 变了就自动绕过缓存 |

### 4.2 组件库打包要点

```js
// rollup.config.js 关键配置
{
  input: 'src/index.ts',
  output: [
    { format: 'es', dir: 'dist/es' },     // ESM 供 tree-shaking
    { format: 'cjs', dir: 'dist/lib' }    // CommonJS 兼容旧项目

  "module": "dist/es/index.js",          // ESM 入口
  "types": "dist/types/index.d.ts",      // TS 类型入口
  "sideEffects": ["**/*.css"],           // 只标记 CSS 有副作用
}
```

## 五、Monorepo

### 5.1 Monorepo vs Multirepo

**Monorepo = 一个 Git 仓库管理多个项目/包**，对立面是 Multirepo（每个项目一个仓库）。

```
Multirepo（传统方式）：
  repo-A/     ← 管理后台
  repo-B/     ← 门户
  repo-C/     ← 组件库
  repo-D/     ← 工具函数
  问题：组件库改了，其他项目要手动升级版本号才能用上

Monorepo：
  monorepo/
  ├── apps/
  │   ├── admin/         ← 管理后台
  │   └── portal/        ← 门户
  ├── packages/
  │   ├── shared-ui/     ← 组件库
  │   ├── utils/         ← 工具函数
  │   └── eslint-config/ ← 统一规范
  └── pnpm-workspace.yaml
  好处：改了组件库，其他项目直接引用最新代码，不用发版
```

### 5.2 为什么需要 Monorepo

| 痛点 | Multirepo 的做法 | Monorepo 的做法 |
|------|-----------------|----------------|
| 组件库改了，下游要手动升级 | 发 npm 包 → 各项目改版本号 → npm install | 直接引用本地包，改了就能用 |
| 代码复用困难 | 复制粘贴 / 发 npm 包 | packages/ 目录直接共享 |
| 跨项目重构痛苦 | 改 A 再改 B 再改 C，三个 PR | 一个 PR 搞定所有引用 |

### 5.3 主流工具链：pnpm workspace + Turborepo

```bash
# pnpm workspace：负责包之间的依赖链接
# pnpm-workspace.yaml
packages:
  - 'apps/*'
  - 'packages/*'

# Turborepo：负责任务编排（构建顺序 + 缓存）
# turbo.json 定义任务依赖关系和缓存策略
```

- **pnpm workspace**：`packages/shared-ui` 改了，`apps/admin` 直接引用本地最新代码
- **Turborepo**：`turbo run build` 自动按依赖拓扑排序构建，有缓存的跳过

### 5.4 Turborepo 缓存原理

```
turbo run build：
  1. 计算每个包的 hash（源码 + 依赖 + 配置）
  2. hash 命中缓存 → 直接恢复产物，跳过构建
  3. hash miss → 执行构建，产物上传远程缓存

效果：
  - 改了 packages/utils → 只重建依赖它的包
  - 没改的包直接命中缓存，CI 时间大幅缩短
  - 团队共享远程缓存，别人构建过的你直接用
```

### 5.5 实际项目结构（结合你的场景）

```
monorepo/
├── apps/
│   ├── li-people/       ← Li People 门户
│   └── admin/           ← 管理后台
├── packages/
│   ├── ui-kit/          ← 你的组件库
│   ├── utils/           ← 公共工具
│   └── eslint-config/   ← 统一规范
├── pnpm-workspace.yaml
└── turbo.json
```

组件库改了，Li People 和其他子应用直接引用最新代码，不用走 `npm publish → 改版本号 → npm install` 的流程。

### 5.6 面试话术

> "Monorepo 是把多个项目放在同一个 Git 仓库管理，核心解决代码复用和跨项目协作的问题。我们用 pnpm workspace 做包管理，Turborepo 做任务编排——它根据依赖拓扑排序并行构建，通过 hash 缓存跳过未变更的包。比如我们的组件库放在 packages/ui-kit，改了之后所有引用它的应用直接用最新代码，不需要发版升级。"

## 六、高频面试题速答

### Q: Webpack 的热更新怎么实现的？

1. WDS 与浏览器建立 WebSocket
2. 文件变更 → 增量编译，生成 hot-update.json + hot-update.js
3. WDS 推送 hash → HMR runtime 用 JSONP 拉取更新模块
4. 模块热替换（dispose + accept 机制）

### Q: Vite 开发为什么快？

跳过打包步骤，利用浏览器原生 ESM 按需加载。开发服务器只做模块转换和转发。esbuild（Go 语言）预构建速度极快。HMR 粒度精确到模块，不受应用大小影响。

### Q: Tree Shaking 的条件是什么？

ES Module 语法 + package.json 的 sideEffects 配置 + 生产模式。CommonJS 的动态特性导致无法静态分析，所以不支持 tree shaking。

### Q: npm install 时 ^ 和 ~ 的区别？

- `^1.2.3`：>=1.2.3 <2.0.0（不改变主版本号）
- `~1.2.3`：>=1.2.3 <1.3.0（不改变次版本号）
- `1.2.3`：精确锁定
- lockfile（package-lock.json/yarn.lock/pnpm-lock.yaml）决定实际安装版本

### Q: peerDependencies 是干什么的？

声明"我依赖这个包，但希望使用方自己安装"。例如组件库声明 `peerDependencies: { vue: "^3.0" }`，表示组件库需要 Vue 但不自己安装一份，避免项目中出现多个 Vue 实例。
