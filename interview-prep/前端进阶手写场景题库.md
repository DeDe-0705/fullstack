## 一、JS 内核与异步（进阶）

### 题 1：手写真正可用的 Promise（核心状态机）

```js
class MyPromise {
  constructor(executor) {
    this._state = 'PENDING';
    this._value = undefined;
    this._handlers = [];
    const resolve = (v) => {
      if (this._state !== 'PENDING') return;
      if (v instanceof MyPromise) return v.then(resolve, reject); // ① 处理 thenable
      this._state = 'FULFILLED'; this._value = v; this._flush();
    };
    const reject = (r) => {
      if (this._state !== 'PENDING') return;
      this._state = 'REJECTED'; this._value = r; this._flush();
    };
    try { executor(resolve, reject); } catch (e) { reject(e); }
  }
  _flush() {   // ② 微任务派发，保证 then 回调异步执行
    queueMicrotask(() => {
      while (this._handlers.length) {
        const { onFul, onRej, resolve, reject } = this._handlers.shift();
        const cb = this._state === 'FULFILLED' ? onFul : onRej;
        if (typeof cb !== 'function') { (this._state === 'FULFILLED' ? resolve : reject)(this._value); continue; }
        try { resolve(cb(this._value)); } catch (e) { reject(e); }
      }
    });
  }
  then(onFul, onRej) {
    return new MyPromise((resolve, reject) => {
      this._handlers.push({ onFul, onRej, resolve, reject });
      this._flush();
    });
  }
  catch(onRej) { return this.then(null, onRej); }
}
```

**关键点**：`then` 返回**新 Promise**；`resolve` 遇到 thenable 要接续；`_flush` 用微任务派发保证异步；错误要 `try/catch` 落到 `reject`。

**追问**：`then` 回调返回普通值/返回 Promise 分别怎么处理？为什么 `then` 回调必须是**微任务**？（否则会在同步栈内执行，破坏事件循环，出现"及时执行"的 bug——经典 **Zalgo** 问题）

### 题 2：微任务竞态输出（async/await）

```js
async function f() { console.log(1); await 0; console.log(2); }
console.log(3); f(); console.log(4);
```

**输出**：`3 1 4 2`

**解析**：`async` 函数体**同步执行**到第一个 `await`；`await 0` 相当于 `Promise.resolve(0).then` 让出到**微任务**；所以 `1` 在同步段立即打，`2` 在微任务里，`3` 最先、`4` 其次。

更难一版（常考微任务内再排微任务）：

```js
console.log('a');
setTimeout(() => console.log('b'), 0);
Promise.resolve().then(() => console.log('c')).then(() => console.log('d'));
queueMicrotask(() => console.log('e'));
console.log('f');
```

**输出**：`a f c e d b`（微任务按注册顺序：c → e → d；宏任务 b 最后）。

**话术**："`await` 就是 `then` 的语法糖，会让出到微任务；微任务里再 `then` 会在**本轮微任务清空后**进入下一轮，所以 `d` 排在 `e` 后面。"

### 题 3：可取消请求 / 竞态只认最后一次

```js
// 用 AbortController 取消（fetch 原生支持）
const ctrl = new AbortController();
fetch(url, { signal: ctrl.signal });
ctrl.abort(); // 取消

// 竞态只认最后一次：用"序号"淘汰过期响应
function useLatest(fn) {
  let seq = 0;
  return async (...args) => {
    const cur = ++seq;
    const data = await fn(...args);
    if (cur !== seq) return; // 已有更新的请求发起，丢弃本次
    return data;
  };
}
```

**话术**："取消/竞态的本质是**防止过期响应覆盖新状态**。要么用 AbortController 从源头取消，要么用序号把旧请求的响应作废。搜索场景里这个尤其关键，否则用户停在旧结果上。"

**追问**：防抖和"取消竞态"区别？(`debounce` 延迟发起；可选 `combineLatest`-like 用序号淘汰)

### 题 4：LRU Cache（get/set O(1)）

```js
class LRU {
  constructor(cap) { this.cap = cap; this.map = new Map(); }
  get(k) {
    if (!this.map.has(k)) return -1;
    const v = this.map.get(k);
    this.map.delete(k); this.map.set(k, v);   // 命中 -> 移到尾部(最新)
    return v;
  }
  put(k, v) {
    if (this.map.has(k)) this.map.delete(k);
    else if (this.map.size >= this.cap) this.map.delete(this.map.keys().next().value); // 淘汰最旧(头部)
    this.map.set(k, v);
  }
}
```

**考点**：`Map` 的**迭代顺序 = 插入顺序**，删除再插入实现"最近使用放尾部"；淘汰用 `keys().next().value` 拿头部（最久未用）。

**追问**：和节流/内存缓存的关系？（缓存策略选择：LRU vs TTL vs LFU）

## 二、React 深入（进阶）

### 题 5：Fiber 为什么能"中断渲染"

**答案**：
- 把渲染拆成**可中断、可恢复**的小任务（**Fiber 单元**），任务间让出控制权；
- 用**时间切片**（`requestIdleCallback` / `MessageChannel` 模拟）判断"是否有空"再继续下一个 Fiber；
- 用**优先级 lanes** 决定哪些更新先做、哪些可被抢占（如用户输入 > 列表过滤）。

**话术**："Fiber 的核心不是虚拟 DOM，而是**把渲染切成能中断的单元 + 按优先级调度**。这样高优先级的用户输入能插队，低优先级的列表渲染可被暂停，避免长时间阻塞主线程。"

**追问**：为什么会卡？(`render` 阶段可中断，但 `commit` 阶段不可中断，需一次做完)

### 题 6：useTransition vs useDeferredValue 场景题

```js
// 场景1：搜索列表，希望"更新的状态本身"降优先级，输入不被阻塞
const [isPending, startTransition] = useTransition();
onChange = (e) => startTransition(() => setQuery(e.target.value));

// 场景2：值已经从上游变过来，但希望"消费它的组件"延迟渲染，不卡其他
const deferredQuery = useDeferredValue(query);
```

**区分（考点）**：
- `useTransition`：**自己握着 setter**，把"这次状态更新"标为低优先级（`isPending` 可显示 loading）。
- `useDeferredValue`：**不握 setter**（值来自别处），让**某个下游组件**用较低优先级渲染。

**一句话**："握 setter 用 useTransition，只拿到值想降级下游渲染用 useDeferredValue。二者都是应对**CPU 密集、非紧急**的更新，跟网络请求无关。"

### 题 7：手写迷你 useState（调度器 + 批量更新）

```js
function createStore(initial) {
  let state = initial; const subs = new Set();
  return {
    get: () => state,
    set(updater) {
      const next = typeof updater === 'function' ? updater(state) : updater;
      if (next !== state) { state = next; subs.forEach((fn) => fn()); }  // 触发重渲染
    },
    subscribe(fn) { subs.add(fn); return () => subs.delete(fn); },
  };
}
// mini setState：批处理 + 微任务调度
function schedule(fn) { queueMicrotask(fn); }
```

**考点（面试想听的）**：React 的 setState 不是同步改，而是**入队后用调度器批量处理**（legacy 微任务 / concurrent 里以优先级调度），所以会"合并多次更新、异步生效"。能说出"**更新是异步批量、按优先级调度**"就及格。

**追问**：为什么 `setCount(count+1)` 连点两次只 +1？（闭包 + 批处理）；用函数式 `setCount(c=>c+1)` 为什么 +2？

## 三、性能与排查（场景题 · 高级岗必考）

### 题 8：虚拟列表（大数据渲染）

**核心方案**：
- 外层一个**可视容器**，内层一个**撑起总高度的占位**（`height = itemHeight * total`）；
- 只渲染**可视区 + overscan（上下缓冲）** 的少量项，用**绝对定位**放到正确纵向位置；
- **动态高度**：先按估算高度渲染，用 `ResizeObserver` 实测后修正缓存 + 调整 total 高度。

**话术**："虚拟列表本质是**只渲染视口内的项 + 用占位维持滚动条**，高度固定用 `index*itemHeight` 定位，高度不固定用 `ResizeObserver` 实测并缓存修正，避免长列表内存暴涨和滚动卡顿。"

**追问**：为什么不用全量渲染？（DOM 节点数暴涨 → 布局/绘制/内存全崩）；`overscan` 为什么重要？（避免快速滚动白屏）

### 题 9：长任务卡顿定位 + 内存泄漏排查

**定位长任务**：
- **PerformanceObserver + `longtask`** 监听 >50ms 的任务；用 **INP / TBT / LCP** 度量交互与加载；
- Chrome Performance 面板看 **Long Tasks 火焰图**，定位是"同步阻塞"还是"布局/重绘/大列表"。

**内存泄漏排查**：
- **Chrome Memory → Heap snapshot**：比较两次快照，看 `Detached DOM`、`EventListener`、闭包变量是否保留；
- 常见泄漏：全局监听未移除、定时器未清理、事件绑定在组件销毁后仍引用、闭包持有大对象、循环引用。

**话术**："SSE/WebSocket 这类**连接类资源**最容易泄漏——必须按生命周期关闭；大列表、路由切换、微前端跨应用引用也是高危点。我习惯用 longtask 定位卡顿、用 heap snapshot 比对定位泄漏。"

### 题 10：SSE 流式渲染性能优化（AI 前端 · 结合本岗 JD）

**方案**：
- 用 **fetch + ReadableStream**（或 EventSource）读取流，**分批/按 token 增量**渲染，不要每次一小段都全量刷新 DOM；
- **打字机节流**：把高频到达的片段缓存，用 `requestAnimationFrame` / 定时器**合并渲染**，避免 30~60 事件/秒把 DOM 打爆；
- 处理**粘包/半包**：按协议分隔（如按换行/SSE `data:` 边界）切分完整消息，缓冲区残留跨包拼接；
- **断线重连 + 指数退避**；可取消用 AbortController；组件卸载即断开。

**话术**："流式渲染的坑不是网络，而是**高频小片段会打爆 DOM 和主线程**。我用增量 + rAF 合并渲染做打字机，按协议边界拆粘包，断线指数退避重连，卸载时 AbortController 断开——这既保流畅又防泄漏。"

## 四、扩展速查（高级/全栈）

- **手写 mini Vue 响应式**：`effect` + `WeakMap` 依赖收集 + 调度器 `nextTick`（微任务批量触发更新）。
- **微前端通信 / 样式隔离**：事件总线、`window` 挂载、`props`/`customElement`；样式用 `scoped/Shadow DOM/css 前缀/contentSecurity` 隔离。
- **状态库设计**：为什么 Zustand 不造成过度渲染——`selector` 按需订阅，避免整个 store 变化都重渲染。
- **深分页 / 游标**：大 offset 慢，改用 `WHERE id > lastId ORDER BY id LIMIT n`。
- **Node 事件循环阶段**：`timers → poll → check → close`，`setImmediate` 在 I/O 回调里必赢，`nextTick` 优先于微任务。
