# 前端性能监控与线上定位（iOS 偶发慢场景）

> 核心盲区：面试官给出「某个用户 iOS 设备偶发访问 H5 很慢」这类题时，要的不是背 LCP/TTFB，而是**可观测性思维**——把模糊现象转成「可量化、可分层、可下钻、可归因」的数据问题。

---

## 一、先给「慢」下一个可观测定义

「偶发慢」最忌讳只看平均值，必须改成看长尾和会话：

- 看 **分位数**：P50 / P75 / P95 / P99，重点盯 P95/P99，均值会被正常用户拉平。
- 按 **session 关联**：同一个用户多次访问，哪几次慢、慢在哪一次。
- 看 **慢率**：如「LCP > 2.5s 的比例」「白屏 > 1.5s 的比例」，而不是「平均加载 2s」。

结论先行：**偶发问题藏长尾，均值指标会掩盖它。**

---

## 二、指标体系：四层拆解

### 2.1 用户体验层（回答「用户感觉多慢」）

- 白屏时间（首屏关键节点出现时间，通常自定义打点）
- FCP：首次内容绘制
- LCP：最大内容绘制，首屏主内容可见，标准 ≤ 2.5s
- TTI：可交互时间（偏辅助，现代更关注 INP）
- INP：交互响应延迟，2024 年起替代 FID，标准 ≤ 200ms
- CLS：布局偏移，标准 ≤ 0.1

如果 H5 是活动页、表单、游戏这类交互型页面，除首屏外还要看 **INP** 和 **长任务（Long Task）**。

### 2.2 页面加载时序层（回答「慢在哪一段」）

核心是 `PerformanceNavigationTiming`（旧版为 `performance.timing`）：

| 阶段 | 计算方式 | 排查指向 |
|---|---|---|
| 重定向 | `redirectEnd - redirectStart` | 多余跳转 |
| DNS | `domainLookupEnd - domainLookupStart` | DNS 慢 / 劫持 |
| TCP | `connectEnd - connectStart` | 建连慢 |
| TLS | `requestStart - secureConnectionStart` | HTTPS 握手、证书 |
| 网络 TTFB | `responseStart - startTime` | 重定向 + DNS + TCP + TLS + 排队，整体「首字节前」 |
| 服务端 TTFB | `responseStart - requestStart` | 请求发出到首字节，偏后端 / 网关 / CDN |
| 文档下载 | `responseEnd - responseStart` | HTML 体积、带宽 |
| DOM 解析 | `domContentLoadedEventEnd - responseEnd` | JS 阻塞、解析慢 |
| Load | `loadEventEnd - startTime` | 整体 |

**两个 TTFB 口径是高频追问点：**

- `responseStart - startTime`：含重定向、DNS、TCP、TLS、请求排队，反映「到达首字节前的所有网络成本」。
- `responseStart - requestStart`：纯粹是服务端响应时间，更接近后端/网关能力。

### 2.3 资源与接口层（回答「具体是哪个东西慢」）

用 `PerformanceResourceTiming` 采集每个静态资源和 XHR/fetch：

- 资源耗时、体积、排队时间、连接复用情况
- `transferSize === 0` 且耗时短 → 命中强缓存，用于算**缓存命中率**
- 慢资源 TOP、慢接口 TOP、接口成功率和超时率
- 第三方脚本（统计、广告、监控 SDK）是否阻塞

前端慢常常不是页面本身，而是某张大图、字体、第三方 SDK 或某个接口。

### 2.4 环境 / 设备维度层（「iOS + 偶发」归因的关键）

指标必须带上上下文维度，否则无法归因：

- 设备：iOS 机型、系统版本
- 容器：系统 Safari 还是 App 内 WKWebView、内核版本
- 网络：WiFi / 4G / 5G、运营商、弱网标识
- 地域、接入 CDN 节点
- 时间：特定时段、发布后、灰度版本
- App 版本、H5 版本号
- 其他：低电量 / 省电模式、iCloud 私密中转、内容拦截器

注意：iOS 上 `navigator.connection` 支持有限，网络类型往往要 App 端透传，或服务端按 IP 辅助判断。

## 三、埋点平台指标观测与评估

> 浏览器 API 是「采集手段」，埋点平台才是「观测入口」。评估和定位发生在平台上：先看大盘、再切维度、再下钻 session，而不是拿着单条数据下结论。

### 3.1 平台要观测的五类指标

1. **加载类**：白屏、FCP、LCP、TTI、页面 Load
2. **体验类**：INP、长任务率、卡顿率（FPS 掉帧）
3. **稳定性类**：白屏率、JS 错误率、接口失败率 / 超时率
4. **业务类**：首屏关键模块可见率、关键接口耗时、关键路径漏斗转化
5. **网络 / 环境类**：DNS / TCP / TLS / TTFB、CDN 命中率、弱网占比、网络类型分布

关键点：平台上的指标必须同时携带「时间、维度、session」，否则只有数字、无法定位。例如同一个 LCP，必须能拆到「iOS / Safari / WiFi / 北京 / H5-v2.3 / 某个 session」。

### 3.2 平台上怎么评估（先看大盘，再切维度）

- **趋势图**：慢率、P95/P99 随时间变化，判断是新增问题还是历史问题，是否和发布、灰度对齐。
- **分位分布**：P50 / P75 / P95 / P99，重点看长尾；平均值只做参考。
- **维度下钻**：按 OS / 机型 / 容器（Safari 还是 WKWebView）/ 网络 / 地域 / H5 版本 / 渠道切片。
- **对比分析**：iOS vs Android、WiFi vs 蜂窝、某版本发布前后。
- **告警阈值**：如「LCP P95 > 4s」「慢率 > 5%」「白屏率 > 0.5%」触发告警。

评估结论示例：

- 只有 iOS 慢 → 平台上 iOS 切片的 LCP P95 明显高于 Android。
- 某地域慢 → 地域维度下钻后 P95 集中抬升，其他地域正常。

### 3.3 平台上怎么定位（从大盘下钻到单次 session）

1. **慢样本明细**：从大盘点进「慢加载 session 列表」，按 P95 或 LCP 倒序取 Top 慢样本。
2. **单次加载时序**：查看该 session 的导航拆段和资源瀑布，定位慢在哪一段、哪个资源。
3. **用户行为回放 / 录屏**：回放慢 session，看卡在白屏、某个接口，还是某个交互。
4. **关联错误与全链路**：同 session 的 JS 错误、接口错误、后端 trace id / APM 日志，端到端串联。

这样「指标观测」就落在平台动作上：指标评估在前，session 下钻在后。

## 四、采集与上报示例

```js
// 1. 采集 Core Web Vitals（web-vitals 库的底层逻辑示意）
try {
  new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
      if (entry.entryType === 'largest-contentful-paint') {
        report({
          metric: 'LCP',
          value: entry.startTime,
          element: entry.element ? entry.element.tagName : '',
        });
      }
    }
  }).observe({ type: 'largest-contentful-paint', buffered: true });
} catch (e) {
  // iOS Safari 对部分 PerformanceObserver 类型支持不稳定，降级为手动打点
}

// 2. 拆解页面导航时序
function getNavigationTiming() {
  const nav = performance.getEntriesByType('navigation')[0];
  if (!nav) return null;
  return {
    dns: nav.domainLookupEnd - nav.domainLookupStart,
    tcp: nav.connectEnd - nav.connectStart,
    // HTTP 下 secureConnectionStart 为 0
    tls: nav.secureConnectionStart
      ? nav.requestStart - nav.secureConnectionStart
      : 0,
    ttfbServer: nav.responseStart - nav.requestStart,
    ttfbNetwork: nav.responseStart - nav.startTime,
    download: nav.responseEnd - nav.responseStart,
    domParse: nav.domContentLoadedEventEnd - nav.responseEnd,
    load: nav.loadEventEnd - nav.startTime,
  };
}

// 3. 上报（页面卸载时 sendBeacon 更可靠）
function report(data) {
  const payload = JSON.stringify({
    ...data,
    page: location.pathname,
    ua: navigator.userAgent,
    at: Date.now(),
  });
  if (navigator.sendBeacon) {
    navigator.sendBeacon('/api/rum', payload);
  } else {
    fetch('/api/rum', { method: 'POST', body: payload, keepalive: true });
  }
}
```

工程要点：

- 采样上报（如 10% 用户）即可反映趋势，降低采集成本。
- 统一把设备、系统、容器、网络、版本等**维度**拼进上报体，后续才可切片。
- 指标只负责「慢」的信号，session、错误日志、录屏、trace id 才是归因证据。

## 五、定位方法：四步走

### 5.1 圈范围（先切片，别急着改代码）

按维度对比找「相对慢」的切片：

- iOS vs Android
- Safari vs App 内 WKWebView
- WiFi vs 蜂窝
- 不同 iOS 版本 / 机型
- 不同地域 / 运营商
- 不同时段 / 发布版本

典型结论：

- 只有 iOS 慢 → WebView/内核兼容、缓存、Safari 网络栈。
- iOS/Android 都慢、某时段慢 → 服务端 / 发布 / 回源。
- 只有某机型 / 系统版本慢 → 兼容性。
- 只有某地域 / 运营商慢 → DNS、CDN 节点。

### 5.2 拆段定位

对慢样本单独看导航时序：

- DNS / TLS / TCP 高 → 网络环境、DNS 劫持、证书、私密中转
- 服务端 TTFB 高 → 后端接口、网关、边缘节点、CDN 回源
- 文档下载高 → HTML 大、压缩失效、带宽低
- DOM / Load 高 → JS bundle 大、同步阻塞脚本、第三方脚本、低版本 iOS 渲染慢

### 5.3 资源 / 接口下钻

找慢样本里的 TOP 慢资源、慢接口，确认是：

- 某大图 / 字体 / 视频未优化
- 某 JS/CSS 未命中缓存
- 某接口跨地域、后端慢、超时重试

### 5.4 多维归因

把「拆段结论」和「设备 + 网络 + 地域 + 版本」交叉，基本能收敛根因。

## 六、iOS 场景特有排查点

1. **WKWebView 缓存策略**：App 内 H5 默认磁盘缓存；H5 更新频繁时可能出现旧资源不刷新，或首屏资源未命中缓存导致重复下载。用 `transferSize` 判断缓存命中。
2. **iCloud 私密中转 / 内容拦截器 / 阻止跨站跟踪**：会改变 DNS、代理、TLS 行为，偶发慢很常见。可建议关闭后对比，或看 DNS/TLS 段是否异常高。
3. **低电量模式**：限制 CPU 和网络，渲染、JS 执行都变慢，容易表现为「偶发」。
4. **冷启动 / 缓存过期 / CDN 未命中**：偶发慢很可能是首次访问、DNS 缓存过期、边缘缓存未命中回源。这也说明必须看 session 和次数。
5. **Performance API 兼容**：iOS Safari 对部分 `PerformanceObserver` 类型、`performance.measure` 支持不稳定，采集要做降级，否则「没数据 / 数据不准」会误导排查。

## 七、偶发问题归因模型（速记）

- **单个用户偶发慢** → 查该用户 session 明细 + 网络时序 + 录屏回放，大概率是用户侧网络、省电模式、私密中转、弱网。
- **某机型 / 某 iOS 版本集中慢** → 兼容性、WebView 内核、渲染能力。
- **某地域 / 运营商集中慢** → DNS、CDN 节点、边缘回源。
- **全量某个时间点偶发慢** → 服务端、发布、依赖、CDN 波动。

一句话标准回答：

> 先看分位数和维度切片确认「谁慢」，再用 Navigation Timing 拆段确认「慢在哪段」，再用 Resource Timing 和接口监控下钻「具体慢在哪个资源 / 接口」，最后结合 iOS 特有的 WebView、缓存、网络环境做归因。

## 九、高频追问与应对

**Q：TTFB 是什么？你说的两个口径有什么区别？**

网络 TTFB = `responseStart - startTime`，包含重定向、DNS、TCP、TLS、请求排队，反映「首字节前的网络总成本」；服务端 TTFB = `responseStart - requestStart`，纯粹是请求发出到收到首字节，更接近后端/网关能力。定位时一定要区分，否则会把后端慢误判成网络慢。

**Q：怎么判断一个资源是否命中缓存？**

看 `PerformanceResourceTiming`：命中强缓存时 `transferSize` 通常为 0 且耗时很短；同时可结合响应头 `X-Cache`、`Age` 判断 CDN 命中情况。

**Q：偶发慢为什么不能只看平均值？**

偶发问题藏长尾，均值会被正常用户拉平。要看 P95/P99、慢率和 session 明细，才能捕捉到少数慢样本。

**Q：iOS 上拿不到网络类型怎么办？**

iOS 对 `navigator.connection` 支持有限，可以由 App 原生侧透传网络类型/弱网标识，或服务端按出口 IP 辅助判断；埋点侧把这作为维度上报即可。

**Q：实验室数据（Lighthouse）能替代 RUM 吗？**

不能。Lighthouse 是实验室数据，受本地设备和网络影响；真实用户可能处于低端机、弱网、海外节点。定位线上问题必须依赖 RUM，用 `web-vitals` / `PerformanceObserver` 采集真实用户的 LCP、INP、CLS。

## 附录：白屏排查 SOP（生产事故高频面试题）

> 面试官："用户说页面白屏/功能报错，你们前端怎么排查？第一时间做什么？"

### 第一时间：止血优先

1. 看监控：错误平台同时段 JS 错误有没有飙升 → 是不是刚发版？
2. 是发版引入 → **先回滚/摘流，再定位**——事故响应第一原则是先恢复

### 分层排查（按命中率排序）

| 层 | 典型病灶 | 确认方式 |
|---|---|---|
| **缓存层** | HTML 被 CDN 强缓存，引用的旧 hash JS 已被发版删掉 → 404 白屏（最经典事故） | 看 JS 请求是否 404 |
| **网络层** | CDN 资源失败、接口网关挂 | Network 面板状态码 |
| **JS 层** | ChunkLoadError（懒加载 chunk 404）、低端机 SyntaxError（新语法未转译）、localStorage 脏数据 JSON.parse 炸 | 控制台 + 错误平台堆栈 |
| **数据层** | 接口异常 → undefined.map 首屏 crash（没做容错） | 复现 + 看响应 |
| **环境层** | 特定机型/WebView 内核差异（老 iOS、App 内置容器） | 监控平台按 UA/机型聚类 |

### 防护体系（主动讲，显成熟度）

- 全局兜底：window.onerror / unhandledrejection + React ErrorBoundary
- **Chunk 加载失败自动刷新重试**（发版瞬间用户在用，chunk 换 hash 加载不到 → catch 后 reload 拿新 HTML）
- 发布顺序：静态资源先上 CDN，再发 HTML
- 骨架屏：白屏变"加载中"
- 灰度发布 + 错误率告警自动回滚
