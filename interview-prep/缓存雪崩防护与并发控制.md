# 缓存雪崩防护与并发控制

> 高并发下如何保护数据库不被压垮。核心洞察一句话：
>
> **保护 DB，靠「拒」不靠「排」——拒绝（限流/熔断/降级）比排队（削峰/并发池）更有效。**

---

## 一、缓存雪崩是什么

缓存雪崩 = 海量请求**绕过缓存直接打到数据库**，导致 DB 被压垮。两种触发场景：

1. **缓存 key 集中过期**：大量 key 在同一时刻过期，请求瞬间回源 DB；
2. **Redis 整个挂掉**：缓存不可用，所有请求直达 DB。

---

## 二、防护手段分层

```text
请求 → 缓存层（多级缓存/随机TTL/互斥锁/逻辑过期）
     → 应用层（限流/熔断/降级）
     → 数据库层（连接池/读写分离/分库分表）
```

### 2.1 缓存层（防雪崩本身）

- **多级缓存**：本地缓存（进程内）+ Redis + DB 三级；
- **随机 TTL**：过期时间加随机值，避免集中过期；
- **互斥锁重建**：热点 key 过期时只让一个请求回源（防击穿）；
- **逻辑过期**：value 里存过期时间，过期后异步重建，旧值先顶着；
- **缓存预热**：提前加载热点数据。

### 2.2 数据库层（兜底）

- **连接池**：限制同时连 DB 的连接数（基础设施，本来就该有）；
- **读写分离**：主从分担读压力；
- **分库分表**：分散写压力和存储容量。

---

## 三、限流 vs 熔断 vs 降级（本质区别，面试必考）

| 手段 | 限流 | 熔断 | 降级 |
|---|---|---|---|
| 本质 | 控制请求**速率** | 错误率超阈值时**快速失败** | 牺牲非核心功能保核心 |
| 触发 | 请求量 > 阈值 | 错误率 > 阈值（如 50%） | 系统负载高 / 依赖故障 |
| 动作 | 拒绝/排队多余请求 | 直接失败，不再打下游 | 返回兜底/默认值 |
| 层 | 入口/网关 | 服务间调用 | 业务逻辑层 |

### 3.1 限流算法（4 种）

| 算法 | 特点 | 允许突发 |
|---|---|---|
| 固定窗口 | 每 N 秒最多 M 次，实现简单，边界有突刺 | 是 |
| 滑动窗口 | 平滑化固定窗口，更精确 | 是 |
| 漏桶 | 严格恒定速率输出，平滑 | 否 |
| 令牌桶 | 桶存令牌，允许一定突发 | 是（最常用） |

单机限流器不依赖 Redis，但只保单实例；**分布式限流**跨实例统一，需 Redis + Lua 实现（令牌桶/滑动窗口）。

### 3.2 熔断器三态

```text
关闭(Closed) --错误率超阈值--> 打开(Open) --超时后--> 半开(Half-Open)
    ▲                                                    │
    └──────── 半开探测成功 → 恢复关闭 ◀──────────────────┘
                     （半开探测失败 → 重新打开）
```

熔断和降级的区别：**熔断是「快速失败」避免级联故障，降级是「返回兜底」保证基本可用**，两者常配合。

---

## 四、削峰 vs 限流（BullMQ / 并发池的定位）

### 4.1 BullMQ 是「削峰排队」，不是「限流」

```typescript
@Process({ concurrency: 5 })   // 同时只处理 5 个任务
async handle(job: Job) { /* 打 DB */ }
```

`concurrency` 限制的是「**同时处理的任务数**」，请求会**排队**、迟早打过去，只是不一次性涌入。而限流是**直接拒绝**超阈值请求。排队是把压力**延后**，不是消除。

### 4.2 BullMQ 的硬伤：自己也依赖 Redis

| 雪崩原因 | Redis 状态 | BullMQ 还能用吗 |
|---|---|---|
| key 集中过期 | 活着 | ✅ 可削峰 |
| Redis 整个挂了 | 挂了 | ❌ 自身难保 |

一句话：**不能用「存在 Redis 里的队列」去保护「Redis 挂了」的场景。**

### 4.3 应用层并发池的局限

自己写信号量限制并发，有两点硬伤：

1. **只管单实例**：4 个实例各限 20，总并发 = 80，还是可能压垮 DB；跨实例总并发又需要 Redis（而它此时挂了）。
2. **连接池早就有了**：DB 连接池（TypeORM `connectionLimit`）本身就是并发池，不用自己写。

## 五、核心洞察：拒 vs 排

保护 DB 有两种思路，效果天差地别：

| 思路 | 手段 | 效果 |
|---|---|---|
| **排**（排队） | BullMQ、并发池、削峰 | 压力延后，总量不变，DB 迟早被打 |
| **拒**（拒绝） | 限流、熔断、降级 | 请求进不来，总量真正减少 |

雪崩时 DB 要的是「**少来点，甚至别来**」，而不是「排队晚点来」。所以真正可靠的兜底是「**熔断 + 降级 + 限流**」这套**不依赖 Redis**的手段。

---

## 六、Redis 挂了时的正确防护组合

```text
① 熔断器：连续失败 N 次 → 直接熔断快速失败（不依赖 Redis）
② 降级：返回兜底数据 / 默认值 / 友好错误（不依赖 Redis）
③ 单机限流器：每个实例自己限流（不依赖 Redis，但只保单实例）
④ 连接池：限制 DB 连接数（基础设施）
```

至于「跨实例全局限流」确实需要 Redis，但 Redis 都挂了，这时应该**降级保 DB**，而不是纠结全局限流。

---

## 七、面试话术（直接背）

> **区别**：限流控制速率、熔断错误率超阈值快速失败、降级牺牲非核心保核心。
>
> **削峰 vs 限流**：BullMQ/并发池是「排队」，把压力延后；限流熔断降级是「拒绝」，真正减少打到 DB 的请求。
>
> **结论**：保护 DB 靠「拒」不靠「排」；Redis 挂了时，用不依赖 Redis 的熔断 + 降级 + 单机限流兜底，而不是用依赖 Redis 的队列/分布式限流。
