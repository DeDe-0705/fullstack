# 跨端开发专题

> 你简历有"组织信息管理平台 PC + 飞书小程序双端"项目——这是跨端能力的实证。本文系统化整理跨端开发的核心概念、主流方案、工程化实践。

---

## 一、为什么需要跨端？

### 1.1 多端的现实

```
一个业务同时要上：
  Web（PC 浏览器） / H5（移动浏览器） / 微信小程序 / 飞书小程序 / App / 桌面端

每端都独立开发：
  Web → Vue/React
  小程序 → 原生 WXML 或 Taro/uni-app
  App → React Native / Flutter
  桌面 → Electron

→ 团队成本 ×6，迭代慢，bug 各端各修
```

### 1.2 跨端的核心价值

```
✅ 一套代码多端运行 — 研发成本降低 60%+
✅ 统一业务逻辑 — 不会出现"小程序有这个功能，H5 没有"
✅ 快速试错 — 一次开发，多端验证
⚠️ 平衡点：性能 vs 开发效率（跨端框架普遍比原生慢 5-15%）
```

## 二、跨端方案对比

### 2.1 主流跨端框架

| 框架 | 厂商 | 一套代码覆盖端 | 核心思路 | 你的项目场景 |
|------|------|---------------|----------|--------------|
| **Taro** | 京东 | React/Vue → 小程序/H5/RN | 编译时转换 | ✅ 组织信息管理 |
| **uni-app** | DCloud | Vue → 小程序/H5/App | DSL + 编译 | — |
| **Rax** | 阿里 | React → 多端 | 标准化组件 | — |
| **Remax** | 蚂蚁 | React → 小程序 | 运行时渲染 | — |
| **Flutter** | Google | Dart → iOS/Android/Web/桌面 | 自绘引擎 | — |
| **React Native** | Meta | JS → iOS/Android | 原生组件桥接 | — |

### 2.2 编译时 vs 运行时

```
编译时方案（Taro 3 之前、uni-app）：
  源码 → AST → 转换为目标端代码
  → React JSX → wx:for / wx:if
  ✅ 运行时性能好（无虚拟 DOM 桥接）
  ❌ 语法受限（不能完全用 React 所有特性）

运行时方案（Taro 3+、Remax）：
  源码 → 运行时 → 通过适配层调原生 API
  → 小程序的 setData → 桥接到 React 的 setState
  ✅ 语法完整支持（React/Vue 全特性）
  ❌ 性能略低（多了一层桥接）

你的项目用 Taro 3+ → 运行时方案 → 语法完整 + 略微性能损失
```

### 2.3 Taro 核心架构（你的方案）

```
┌─────────────────────────────┐
│     Taro CLI（编译）         │  → taro build --type weapp/h5
├─────────────────────────────┤
│     React/Vue 运行时         │  → 你写的 Vue3 代码
├─────────────────────────────┤
│   Taro 适配层（reconciler）  │  → 把 Vue 的渲染指令翻译成各端
├─────────────────────────────┤
│  各端原生运行时              │
│  ├── 小程序：setData         │
│  ├── H5：DOM API             │
│  └── RN：Native UI           │
└─────────────────────────────┘
```

### 3.2 API 适配层 — 屏蔽各端差异

```ts
// src/api/index.ts
export interface ApiAdapter {
  request(config: RequestConfig): Promise<Response>
  getStorage(key: string): any
  setStorage(key: string, value: any): void
  navigate(url: string): void
}

// src/api/pc.ts
export const pcAdapter: ApiAdapter = {
  request: (config) => fetch(config.url, config).then(r => r.json()),
  getStorage: (key) => localStorage.getItem(key),
  setStorage: (key, val) => localStorage.setItem(key, val),
  navigate: (url) => history.pushState(null, '', url)
}

// src/api/miniapp.ts
import Taro from '@tarojs/taro'
export const miniappAdapter: ApiAdapter = {
  request: (config) => Taro.request({ ...config }).then(r => r.data),
  getStorage: (key) => Taro.getStorageSync(key),
  setStorage: (key, val) => Taro.setStorageSync(key, val),
  navigate: (url) => Taro.navigateTo({ url })
}

// 入口根据环境选择
export const api = process.env.TARO_ENV === 'h5' ? pcAdapter : miniappAdapter
```

### 3.3 UI 适配层 — 组件级适配

```vue
<!-- 通用组件：用条件编译处理两端 UI 差异 -->
<template>
  <!-- #ifdef H5 -->
  <div class="container" @scroll="handleScroll">
    <img :src="avatar" />
    <slot />
  </div>
  <!-- #endif -->
  
  <!-- #ifdef MP-WEIXIN || MP-LARK -->
  <scroll-view class="container" scroll-y @scroll="handleScroll">
    <image :src="avatar" />
    <slot />
  </scroll-view>
  <!-- #endif -->
</template>
```

**Taro 条件编译注释：**
- `#ifdef H5` → 只在 H5 编译
- `#ifdef MP-WEIXIN` → 只在微信小程序编译
- `#ifdef MP-LARK` → 只在飞书小程序编译
- `#endif` → 结束

### 3.4 Logic 层 100% 共享

```ts
// src/logic/useOrgTree.ts — 两端完全共享
import { ref, computed } from 'vue'
import { api } from '@/api'

export function useOrgTree() {
  const tree = ref<OrgNode[]>([])
  const loading = ref(false)
  const expanded = ref<Set<string>>(new Set())

  const totalNodes = computed(() => tree.value.length)

  async function fetchRoot() {
    loading.value = true
    try {
      tree.value = await api.request({ url: '/api/org/root' })
    } finally {
      loading.value = false
    }
  }

  async function toggleExpand(nodeId: string) {
    if (expanded.value.has(nodeId)) {
      expanded.value.delete(nodeId)
    } else {
      expanded.value.add(nodeId)
      const children = await api.request({ url: `/api/org/${nodeId}/children` })
      // 挂到树上
    }
  }

  return { tree, loading, totalNodes, fetchRoot, toggleExpand }
}
```

## 四、小程序原理

### 4.1 双线程架构

```
┌─────────────────┐         ┚─────────────────┐
│   视图层线程      │   ←→   │   逻辑层线程      │
│ (WebView/渲染)   │  数据   │ (JSCore/V8)      │
│  WXML/WXSS      │  传递   │  JS 业务代码      │
└─────────────────┘  ↓ ↑  └─────────────────┘
                     │
                  Native 层
                  (原生能力)
```

**为什么双线程？**
- 防止 JS 长任务卡住渲染（隔离渲染和逻辑）
- 安全沙箱（不能直接操作 DOM，避免 XSS）
- 数据通信靠 setData（不能直接改 DOM）

### 4.2 setData 性能坑

```js
// ❌ 频繁 setData → 触发多次跨线程通信 → 卡顿
this.data.list.forEach(item => {
  this.setData({ [`list[${item.id}].checked`]: true })
})

// ✅ 合并一次 setData
const newData = {}
this.data.list.forEach(item => {
  newData[`list[${item.id}].checked`] = true
})
this.setData(newData)  // 一次通信
```

**面试话术：** "小程序双线程导致 setData 是跨线程通信，每次 setData 都有通信开销。频繁 setData 会卡顿，应该批量合并。这是小程序性能优化的核心点。"

## 五、跨端常见坑

### 5.1 样式差异

| 维度 | H5 | 小程序 |
|------|----|--------|
| 单位 | px/rem/vw | rpx（750rpx = 屏宽） |
| 容器滚动 | div + overflow | `<scroll-view>` |
| 图片 | `<img>` | `<image>` |
| 表单 | `<input>` | `<input>`（属性略不同） |
| 样式隔离 | CSS 作用域 | 默认组件样式隔离 |

### 5.2 API 差异

```js
// 网络
H5：fetch / XMLHttpRequest
小程序：Taro.request / wx.request

// 存储
H5：localStorage / sessionStorage
小程序：Taro.getStorageSync / wx.setStorageSync

// 路由
H5：history.pushState / popstate
小程序：Taro.navigateTo / wx.navigateTo

// 设备能力
H5：navigator.geolocation
小程序：Taro.getLocation
```

### 5.3 你的项目踩坑

```
1. 飞书小程序 API 差异
   飞书小程序 ≠ 微信小程序，部分 API 不同
   → 用 Taro 统一 API，少用 wx.xxx 直接调用

2. 长列表性能
   组织架构人员列表有几千人
   → PC 用虚拟列表，小程序用 recycle-view
   → 不同端用不同方案

3. 跨 Tab 通信
   H5 用 storage 事件，小程序没有这个事件
   → 用 Taro.eventCenter 替代
```

## 六、面试话术（结合组织信息管理）

> "组织信息管理平台同时部署到 PC（Vue3）和飞书小程序（Taro + Vue3）。核心设计是逻辑层 100% 共享——业务逻辑、状态管理、API 调用都在 logic 层，两端共用。UI 层各写各的，因为 PC 用 div、小程序用 view/image，组件 API 必须各自实现。API 适配层屏蔽了 fetch vs Taro.request、localStorage vs Taro.setStorage 等差异，logic 层代码完全感知不到自己在哪个端运行。"
